# SandForge for AI agents (MCP)

`sandforge mcp` gives an AI agent twenty tools over the Model Context Protocol: Seed's templates and runs, Forge's clone of a record and of the whole org -- or of a sample of it that fits the target, planned first --, the removal of a Seed, Forge or Sync run, the following and stopping of a run that goes on past its call, Checkpoints -- take, list, preview, rewind, undo, delete --, the emptying of objects or of a whole org -- preview, run, undo -- and the [environments](environments.md) a `sandforge.yaml` declares -- plan, apply, destroy. "Fill this scratch org to test the Case flow", "clone the records of this bug", "fill my dev sandbox with a sample of production that fits", "take back the last run", "rewind the org to before the tests", "empty the cases of this sandbox", "put in this sandbox the data the repository declares": each is one call, or a plan and its run, and each call runs the [command-line script](../ci-examples/README.md) of this repository that does the same, with its `--json`, so every guard of that script holds.

It is a script of this repository, as the command-line scripts are, published with them as the `sandforge` npm package and run from a checkout as well: it is not in the VSIX. **The extension itself gives the model no tool**: nothing it ships hands the model of its AI Assistant a tool or acts on a tool call, which [`product-claims.test.mjs`](product-claims.test.mjs) holds against everything the extension ships (its test "anchor: nothing shipped gives the model tools or acts on a tool call"), and `scripts/mcp-server-not-shipped.test.mjs` checks that the files vsce packages into the VSIX hold none of `cli/`.

## Add it to Claude Code

From the `sandforge` npm package, with Node.js 20.19 or later and no checkout:

```sh
claude mcp add sandforge -- npx -y sandforge mcp
```

Or from the repository root of a checkout, once `pnpm install` and `pnpm build:shared` have run:

```sh
claude mcp add sandforge -- pnpm exec tsx packages/extension/cli/sandforge-mcp.ts
```

The scope is the folder's own, where `claude mcp add` ran (`local`, Claude Code's default), and the server starts in it. It reaches the orgs as the scripts do, through the `sf` CLI: each tool names an org by its alias, as `sf alias list` shows them. With `-e SANDFORGE_JOURNAL_DIR=<dir>` before the `--`, the scripts keep their run files, journals and checkpoints in `<dir>` rather than in `~/.sandforge`, as each script's `--help` says. Any other client that starts an MCP server on stdio runs the same command, from the same folder.

## The confirm rule

A call that writes -- `seed_run` and `clone_record` unless `dryRun: true`, `clone_org`, `run_remove` unless `preview: true`, `checkpoint_rewind`, `checkpoint_undo`, `checkpoint_delete`, `empty_run`, `empty_undo`, `env_apply` and `env_destroy` -- takes `confirm`: the alias of the org it writes to (`org`, `target` for a clone of a record, the target of its plan for `clone_org`), exactly as given. Without it, or with any other value, the call is refused before any script runs, so before anything is read, and its refusal says what the call would do and where to read it first: a dry run, `clone_org_plan`, `run_remove` with `preview: true`, `checkpoint_preview`, `checkpoint_list`, `empty_preview`, `env_plan`. A dry run, a read, `clone_org_plan`, `env_plan` and `checkpoint_take` need none. `confirm` is the person's agreement, given through the agent: the alias a rewind, an undo, a delete, an apply or a destroy asks you to type on a terminal, after which the server runs the script with `--yes`, and only then; `sandforge empty` asks nothing on a terminal and is refused there without `--yes`, which the server gives it once `confirm` is.

The acceptances are the script's flags, and the person's to give too: `acceptAutomation` is `--accept-automation` (`clone_record`, `clone_org_plan`, `run_remove`, `checkpoint_rewind`, `checkpoint_undo`, `empty_preview`, `empty_run`, `empty_undo`), `acceptEmails` is `--accept-emails` (`seed_run`, `clone_record`, `clone_org_plan`, `checkpoint_rewind`, `checkpoint_undo`, `empty_preview`, `empty_run`, `empty_undo`, `env_plan`, `env_apply`), which `acceptAutomation` never stands for, `acceptNoUndo`, `acceptRecreate`, `acceptOutside` and `acceptUnseen` are `checkpoint_rewind`'s `--accept-no-undo`, `--accept-recreate`, `--accept-outside` and `--accept-unseen`, and `acceptNoUndo` is `--accept-no-undo` for `empty_preview` and `empty_run` too, whose `hardDelete`, `checkpointFirst`, `wholeOrg`, `excluded` and `resume` are `--hard-delete`, `--checkpoint-first`, `--org`, `--exclude-object` and `--resume`, `empty_undo`'s `run` being `--undo`, `acceptNoState` is `env_apply`'s `--accept-no-state`, and `includeChanged` is `env_destroy`'s `--include-changed`, as it is `run_remove`'s, whose `muteAutomation` and `leaveUndeletable` are `--mute-automation` and `--leave-undeletable`, and whose `store` is a Sync removal's `--store`, the directory the person names, and `preview` its `--preview`; `muteAutomation` is `--mute-automation` for `seed_run`, `clone_record`, `clone_org_plan`, `checkpoint_rewind`, `checkpoint_undo`, `empty_preview`, `empty_run` and `empty_undo` too. `clone_org_plan`'s `maxTotal`, `excludedObjects`, `excludedFields`, `filters`, `fit` and `fit…` are `--max-total`, `--exclude-object`, `--exclude Object.Field`, `--filter "Object=where"`, `--fit share` and `--fit-…`. A refusal that names one of those flags comes back with a line naming the parameter it stands for: under `checkpoint_preview`, the parameter of `checkpoint_rewind`; an emptying's line that names `--undo` or `--resume` with a run comes back with `empty_undo` or `empty_run`'s `resume`, and a run whose undo is offered with the `empty_undo` call that brings it back. A flag a script's advice names that its tool does not take -- a sweep, `--max-total` of a clone of a record, what narrows a clone of a record -- the script's line calls this script's own: the person gives it to the script, on a terminal. An environment's acceptance of automation is its file's, per resource (`accept: { automation: true }`): `env_apply` and `env_destroy` take no `acceptAutomation`, and a run refused for automation is accepted in the file, where the repository's reviewers read it: a refusal of theirs that names `--accept-automation` comes back with the line that says so. No environment mutes, and none of its runs offers it. Its acceptance of emails is not: that is `acceptEmails`, on the call.

`checkpointFirst` is the script's `--checkpoint-first`, on `seed_run`, `clone_record` and `clone_org_plan`: `{}` takes it with the defaults, `keepDays` sets the days it is kept (7 by default, 0 until it is deleted) and `excluded` leaves objects out, named. Each object it holds is held whole, so its cost is that of the tables, and its values stay unencrypted on this machine: give it only once the person has seen, in a dry run with it, what it would hold and cost. Refused, the run writes nothing; a run that wrote nothing deletes it.

## What the environment tools do not offer

No tool resets an environment (`sandforge env reset`) or destroys it by rewinding the org to a checkpoint (`destroy --rewind`) in this version: both take back everyone's changes since, not only the environment's records, and run from a terminal, where the script previews the rewind and asks for the org's alias. `env_destroy` takes back by removal alone. Nor do the tools validate a file offline, list the states this machine keeps, or take `--alias`: the alias of each org a file's roles name comes from the file, or from its `{ env: NAME }` variable as the environment the server was started in holds it.

## A clone of the whole org

`clone_org_plan` runs the dry run of a clone of the whole org (`sandforge clone --depth all --dry-run`), or of a sample of it that fits the target (`fit: "share"`): it reads both orgs and writes nothing to either. A dry run a real run would be refused after keeps no plan, and each refusal comes back with the parameter of `clone_org_plan` that lifts it -- `maxTotal`, `fitWithinMB`, `acceptAutomation`, `excludedObjects` … A dry run that would go keeps its plan on this machine, its owner's alone (0600 in a folder of 0700), until a day after it was drawn: a receipt with the line of its run, the records its gate counted and the acceptances it was given, and of a sample, a copy of the ids its dry run drew, held to the SHA-256 the dry run printed. The answer gives its id, its figures under `plan`, and the question a terminal would ask before the first write, which the agent shows the person.

`clone_org` takes that id and `confirm`, the alias of the plan's target, and nothing of what it writes: a scope given to it is refused, and `clone_org_plan` plans again. It runs the plan's line with `--yes`, the person having answered its question with `confirm`: of a sample, `--fit-plan` and the copy, so that it writes the records shown and no other; of every record, `--max-total` the count its dry run gave, so that a source that grew since is refused, not written. A copy changed or gone since (`SAMPLE_PLAN_MISMATCH`, `SAMPLE_PLAN_GONE`), a source past the count, a target with less room or more automation than planned are refused by the script, nothing written, and the plan is dead: `clone_org_plan` again. A day's API requests spent leave the plan as it was, for later in its day. A plan is written once: `clone_org` again on it is refused, `resume: true` takes up its run that stopped part way from its journal, and `run_remove` with that journal takes it back. Once a run that went through has ended, the server verifies what it wrote (`sandforge clone --verify` of its journal), and says the verification first when it is not `VERIFIED`.

Every personal field of a clone of the whole org is anonymized, always: no tool copies them as the source holds them, and `anonymize: false` is refused. A person who means to copy them as they are does it on a terminal, `sandforge clone --depth all … --no-anonymize` after its `--dry-run`, or in a `sandforge.yaml` whose `depth: all` resource says `accept: { realData: true }`, reviewed where the repository is. Neither `clone_org_plan` nor `clone_org` takes `--files`, `--keep-contact-points`, `--owner-map`, `--map`, `--config` or `--write-uncertain`: those stay options of the script, on a terminal, and the emails and phone numbers are neutralized whatever happens.

## Long calls

A client gives a call so long before it cancels it -- 60 seconds for any client on the defaults of the MCP SDK -- and a cancelled call stops its script as Ctrl-C would: a clone of the whole org, or even its dry run, cut part way. So a call whose script still runs once the call has held it 45 seconds answers with the handle of its run (`running: {run: "mr-…", tool, startedAt, …}`) and the run goes on: `run_status` with that handle says how far it is -- its time against its plan's, what its summary says it wrote, its journal, its script's last lines -- and, once it has ended, gives the answer its call would have given, verification included; `waitSeconds`, 50 at most, waits for its end first. `run_stop` stops it as Ctrl-C would, what it wrote kept, and answers as `run_status` does. `SANDFORGE_MCP_HOLD_SECONDS` sets the hold, 0 to 55 seconds. A call that ends within it answers as before.

A run handed back lives as long as the server: closing the agent's session stops it the same way, and nothing writes on unseen. What a later server reads of it is kept in `mcp-runs/` under the journal folder: what it was, and the summary a clone writes as it goes. `run_status` on such a handle says what that summary says, with the `clone_org` resume and the `run_remove` call that take the run up and back. `run_remove` of a run this server still runs is refused (`RUN_UNDER_WAY`), and `clone_org` of a target it still writes (`TARGET_BUSY`); a server knows its own runs only.

## What holds

Each call runs its script in a process of its own, as it runs on a terminal: a production org is refused before anything is read, and no flag lifts it; the user the alias connects as needs the permissions the script needs; the API requests left today, the daily emails, the data storage, a checkpoint asked first and the acceptances refuse a run before it writes, as the script's `--help` says; a take, a rewind or an undo of the org under way on this machine refuses a rewind and an undo. The script has no terminal: a question it asks stops it at the question, exit `2`, having written nothing, and the call's error carries the question in its words -- for the person using the agent to answer, never answered by the server.

A call the client cancels (`notifications/cancelled`) before it has answered stops its script as Ctrl-C stops it: before its next call to the org, its journal kept, so a rewind run again takes up from what still differs and an undo still returns the org to how it was before. Closing the server's stdin stops the scripts still running the same way, those of the runs handed back among them, and the server ends once they have. On Windows, which has no signals, the server sends the script a stop message over an IPC channel instead, and the script hears it as Ctrl-C.

## What a call answers

- **`structuredContent`**: `{exitCode, answer}`, where `answer` is the script's `--json` answer, shaped as its `--help` says, and `exitCode` its exit code: `0` done, `1` refused before it wrote or nothing done, `2` a request the script could not take or a question it asked, `3` partial, `4` unstable, `130`, `143` or `129` stopped. `isError` is set for any code but `0`, `3` and `4`, whose answer says what was left and why. `seed_templates` answers `{templates}`; `clone_org_plan` adds `plan`, the plan it kept; `clone_org` adds `verification: {exitCode, status, …}`, and of a verification not `VERIFIED` the objects it found short; a call still running past its hold answers `{running}`, and `run_status` adds `run: {run, state}` to the answer of a run that has ended, or answers `{running}` while it goes on. A call refused by the server answers `{refusal: {code, message}}`, its code `CONFIRM`, `ARGUMENTS`, `PLAN_GONE` (a plan unknown, past its day, dead, or whose journal is gone), `PLAN_USED` (a plan already written), `NOTHING_TO_RESUME`, `TARGET_BUSY`, `RUN_UNDER_WAY` or `RUN_UNKNOWN`; a plan its dry run drew but could not be kept, `PLAN_NOT_KEPT`.
- **Its text**: the verification of a clone of the whole org first when it is not `VERIFIED`, then the line it ran, the exit code, then the script's own lines -- a rewind's preview, with who last changed the records it takes back (`last changed by`), and its result, with what Undo could not bring back -- then what the server adds: the parameter a flag named above stands for, for a seed or a clone that wrote or that stopped part way, the `run_remove` call that takes the run back, and the `checkpoint_rewind` call that returns the org to the checkpoint it kept, for an apply, the `env_destroy` call that takes the environment back, for a plan, its question and the `clone_org` call that writes it, and for a clone of the whole org stopped part way, the `clone_org` resume that takes it up. An `env_plan` given `failOnDrift` that ends exit `3` found drift, which its text says, rather than a partial run. The structured content follows, as JSON.

## What leaves this machine

The server writes only to the client that started it, on its stdout; the scripts reach the orgs as they do from a terminal, and nothing else leaves this machine. On this machine, a plan of `clone_org_plan` keeps, for a day, the ids of the records a sample drew -- of a production, when it is the source --, its owner's alone, and `mcp-runs/` the summaries of the runs handed back, which name the source ids of what they wrote; the server removes them once no run needs them. What a tool answers -- counts, record Ids, the ids of the records a sample set aside as too heavy (`heavyRoots`), the names of the users who last changed records, the org's words in a refusal -- then goes wherever that client sends it: to the agent's model, whatever model that is. The extension's AI settings do not reach the server, and turning AI off in the extension does not stop it.

## The protocol

MCP [2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio), written without an SDK: JSON-RPC 2.0, one message a line on stdout and nothing else there, the server's own lines and the scripts' on stderr. A request of that revision names it in its `_meta`, and `server/discover` says which revision is served. Clients of the revisions before it -- 2025-11-25, 2025-06-18 and 2025-03-26 -- open with `initialize` and `notifications/initialized`, then send `tools/list`, `tools/call` and `ping`; an `initialize` asking for another revision is offered 2025-11-25, and a request naming another in its `_meta` is refused with error `-32022`. A batch, a line that is not JSON, a method or a tool it does not have are refused with JSON-RPC's own errors.
