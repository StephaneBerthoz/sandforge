# Frozen Dataset

Extract a business dataset from a UAT sandbox **once**, pseudonymize it deterministically, freeze it (manifest + salt fingerprint), then **replay it identically** after every dev sandbox refresh -- with a non-reidentification gate before versioning and a verification pass after loading.

<!-- how-to:start: written by scripts/sync-module-howto.mjs from howTo.frozen in packages/webview/src/i18n/locales/en.json -->

## How to

1. On the Extract tab, fill in Root object and click Save configuration.
2. Click Run selection: it picks the root records in the org selected in the side panel.
3. Click Create rules file (every field without a rule is cleared), then click Run extraction.
4. On the Load tab, pick the Target org (sandbox) to fill, then click Run load.
5. Read the Post-load verification that follows the load; Re-verify runs it again.

**Tip:** Preview writes nothing, a load never goes into a production org, and Remove the records this load created deletes them.

<!-- how-to:end -->

Typical case: a Developer sandbox refresh leaves you with metadata and zero records. Frozen Dataset gives you back a realistic set of root records covering your functional paths in one run, without ever shipping identifying data.

## Quick Start

1. Open **Frozen Dataset** from the sidebar (or `SandForge: Open Frozen Dataset` from the command palette)
2. **Extract** tab: fill in the root object, add coverage axes if you want them (with none, the whole root object is one combination, and the selection keeps one root for it), check the volume budget, which starts at 2,500 records, then **Save configuration**. The runs read the saved configuration: while an edit is not saved, the tab says **Unsaved changes** and offers neither run
3. Give the extraction its pseudonymization rules file -- see [the rules file](#the-rules-file): the **Extraction** card says where it goes, **Run extraction** waits for it, and **Create rules file** writes an empty one, which clears every field without a rule. The salt the pseudonyms are drawn with is made on the first extraction and kept in VS Code's secret storage -- see [the salt](#the-salt)
4. **Run selection** (coverage matrix) -- the tab says the step it is at as it goes -- then **Run extraction**. The 4-point control must return PASS for the dataset to be written
5. **Load** tab: pick the target sandbox -- none is picked until you do, and the dataset's source is listed but not offered -- tick **Pilot (one root record first)** to try a single root graph first, **Preview** to see what the load would do with nothing written, then **Run load**, which reads **Run pilot** while Pilot is ticked and **Reload** while **Reload without refresh** is -- **Stop the run** stops it before its next write. **Checkpoint first**, off unless ticked, takes a checkpoint of what the load writes before its first write. Post-load verification is chained automatically
6. To take a load back, **Last load** on the same tab removes the records the last load into the selected target created -- see [Removing a Load](#removing-a-load)

## Features

### Extraction Flow

1. **Coverage-matrix selection** (no random sampling): each axis is a configurable SOQL aggregate query; the module enumerates the **combinations actually observed** in the source org and keeps **one healthy root per combination**, plus one per declared edge case. A root is healthy when **its own records** hold at least one record of every `expectedObjects` entry -- it is judged on the same scope-aware extraction the dataset is made of, not on Forge's discovery graph, which describes the schema and is the same for every root of an object. A combination with no healthy root is listed as uncovered **with the reason** the last candidate was turned away. The volume budget (2,500 records by default) is **enforced mechanically**: anything above it is refused, and the refusal names the heaviest objects with their counts and suggests leaving them out with `excludedObjects`. The selection says each step as it starts -- the discovery as it reaches objects, each combination and each candidate it judges, the final measure of the roots it kept -- on the **Extract** tab, and `select` prints them on the command line. It has ten minutes, and runs in **Live Operations**, where Cancel stops it; stopped either way, it **keeps the combinations it decided**, names the combination it was probing and those it never reached, and says its volume is each kept root's own records added up rather than measured together -- a record two roots share counted twice, and the budget held to that sum. Each object is described once for the whole selection: the describes discovery makes serve every candidate's extraction, and a statement two extractions share is asked once.
2. **Scope-aware extraction**: reuses `RecordScopeCache` and `ScopedSoqlBuilder` (full descendants plus the reference data they need, never `SELECT *`), with a frozen date bound (`CreatedDate <= asOf`) and an `rt-map.json` written to the sas. Discovery runs once per run, up to `maxNodes` objects holding records (default 50; an empty table takes no place, nothing is reached through it, and four times the cap in objects are read at most) -- a cap raised, up to twice it, for the parents their records cannot be written without; when it stops at that cap, the selection and the manifest **say so**, and say when it was raised. The graph is **kept in the sas** (`discovery.json`) with the describes the step read and the org's key prefixes, under the source org, the root object and the cap, and stamped with the org's own clock as discovery began: the next selection or extraction reuses it when it is less than a day old and the org says its schema has not changed since -- one request, `If-Modified-Since` on its list of objects, which the org answers `304 Not Modified` -- and says `graph reused from select`; otherwise it discovers again and says why (no graph kept, another org, root object or cap, the schema changed, a day gone by). On the Developer Edition source, the extraction after its selection went from 409 requests to 9, and a selection run again from 421 to 20. The dossier goes **down from the roots** through the records under them, and **up only to the records its rows name**, read by id and bringing none of their other children -- a parent of the root's own object a root names, a root case's parent case, among them -- as a Forge clone of a record reads what lies outside its graph: the account a case names comes, and the policies, assets and feed items under that account do not; the territory an appointment is booked in comes, and the territory tree it belongs to does not; the quotes of the root opportunity come, and the other quotes of its account do not. A lookup the platform will not let a row leave empty also holds the row to the dossier: a quote line whose quote is not in it is left out. The **catalog** -- prices, products, selling models, price books, and the categories products are assigned to with the catalogs that hold them -- is read by what the dossier's records name and never walks down into other dossiers: a price book met through a lookup brings none of the quotes or orders priced from it, and a category none of the other products assigned to it. Its records are fetched by id when they are named late, and whatever `maxNodes` left out of the graph: each line carries its price, and each price its product, its book and its selling model, with the **selling model option** that lets the product be sold under that model, and each assignment of a product to a category its category and that category's catalog, unless `excludedObjects` leaves them out -- by name, whether the graph reaches them or not. The **items of an order past Draft** come the same way when discovery stopped before them, unless `excludedObjects` names them: the load writes such an order as a draft and activates it once the rest is written, and the platform activates no order without a product, so the extraction reads the items of the orders past Draft in the source -- and only those -- with their prices, those of an order the dossier only names among them. A price book keeps one price per product and currency, and per selling model where the dataset carries the models. The **standard prices** of the products in the dataset are read with it, and the standard price book is marked so the load can match it; `excludedObjects` naming the price books keeps that one, as Forge keeps it: the load matches it and never writes it, so the standard prices still go in. What an object left out this way costs is **named**, not hidden: the records that need it stay in the dataset as they are, and the manifest counts, per object, those that cannot be loaded as they are -- a line without its price, a price without its product or book, a price sold under a selling model without its option, an order past Draft left with no item it can be activated with, which the load leaves a draft. Objects without `CreatedDate` are read without the date bound and **named**; objects whose files (`base64` fields) the rules do not keep with an approved `keep` are **left out and named** -- bytes cannot be pseudonymized. `excludedObjects` leaves others out.
3. **Deterministic pseudonymization**: `HMAC-SHA256(salt, "generator|value")`. The same input value produces the same output whatever object carries it, so cross-object joins survive. `RecordTypeId` is replaced by the RecordType **Name**, resolved on the target by **namespace and DeveloperName**, never by label: `rt-map.json` and the dataset's `record-types.json` keep each record type's `namespacePrefix` (`null` for the org's own), and a record type a managed package installed loads as the same package's, never as the org's own that carries its `DeveloperName` on the object. A dataset extracted before the namespace was read has none: its names load as before where the target holds one record type of that `DeveloperName` on the object, and the load is refused, before anything is written, where the target holds two -- a package's and the org's own -- naming both; extract it again. Each record keeps beside the label the name of its own record type (`recordTypeDeveloperName`, `ns__Retail` for a package's, `Retail` for the org's own), and the load goes by it: two record types of one object under one label -- a package's and the org's own -- load as each record had them. A dataset extracted before that name was kept carries the label alone: its load is refused the same way where two record types of the object share it, saying the dataset is older; extract it again. `requiredLookupPlaceholders` names a package's record type `ns__DeveloperName`. A field the rules name no generator for is cleared, except the platform's own words, which are no one's data and which a load cannot do without: a feed item's `Type` (what tells a tracked change from a post); the time zones, locales, languages, currencies and email encodings the platform fills from its lists (`TimeZoneSidKey`, `LocaleSidKey`, `LanguageLocaleKey`, `CurrencyIsoCode`, `EmailEncodingKey`, `OperatingHours.TimeZone`); the start and end time of each day of a `BusinessHours` record and the day, times and type of a `TimeSlot`; whether a price book, a product or a price is active (`Pricebook2.IsActive`, `Product2.IsActive`, `PricebookEntry.IsActive`), which cleared go in inactive, and the target then refuses to sync a quote; and the value of a **restricted** or **required** picklist, a word of the schema, as the source's describe tells it -- an opportunity's stage, which the platform does not restrict and no opportunity goes without, is kept -- unless the personal data detector every module shares names the field by its API name or label (a gender identity, pronouns, a marital status, a nationality, and the GDPR's special categories: ethnic origin, religion, sexual orientation, political opinion, union membership, a disability). An unrestricted picklist a record can go without, a multi-select picklist, the state or country of an address, a field the detector names, and any name or free text, stay cleared. A rule the file declares still wins: a picklist that says something of a person is cleared by declaring it. The **Extract** tab lists the fields an extraction kept without a rule under its result, and **Clear these** writes a `clear` rule for each into the rules file, every other key of the file kept and the minor number of its `rulesVersion` moved on; the dataset already frozen keeps them, the next extraction clears them, and a required one cleared becomes a value a load asks for. A classic encrypted field (`encryptedstring`) that the user SandForge reads the source as sees masked, lacking View Encrypted Data, is not kept: read, it gives its mask, which a load would have written into the target as the value. The manifest lists those fields as not kept (`encryptedNotKept`), an empty list when there is none, and the **Extract** tab and `extract` name them under the result. A manifest without the list -- written before the extraction left those fields out, or before it said so of none -- does not tell whether its dataset holds masks: its load and its preview leave out every field the target encrypts that the dataset holds a value of, each named in the preview, the report and the command line's output as one that may hold masks such as `****1234` (`may-hold-masks`), unless **Write encrypted fields as the dataset holds them** is ticked on the **Load** tab (`load --write-encrypted` on the command line). The manifest lists the fields kept without a rule, and the required fields the rules leave empty -- each a value a load will ask for, an account's `Name` among them when a business account's is cleared and its `LastName` when a person account's is, which the describe of an org with person accounts calls required of neither -- which the **Extract** tab and `extract` say as the dataset is frozen. `dateShift` and `dateMonthStart` take a datetime as the org writes it (`2026-10-01T08:00:00.000+0000`) or with any offset, and `dateShift` writes it back in UTC (`…Z`).
4. **Non-reidentification control (gate)**: 4 checks -- substitution actually applied (including a value leaking into another field of the same record -- but for a field the dataset keeps, and for the record type's own name or developer name in `RecordTypeId`, which a text field mirroring the record type repeats), fields under the `clear` generator left empty, shapes preserved (`registrationSIV`, `phoneE164`, `email`, `postalCodeGeneralize`), and zero residual source ID (18-character Salesforce checksum). **One FAIL and nothing is written or versioned.**
5. **Manifest**: semver version, `status: frozen`, source (org + decision date), salt fingerprint (SHA-256, 12 hex -- never the salt), rules version, volumetry (ceiling + measured, counting what the dataset holds), control results, and **coverage**: objects reached, whether discovery stopped at its cap, objects read without the date bound, objects left out for their files, and the records held that cannot be loaded as they are for an object `excludedObjects` leaves out.

### Load Flow (Replayable)

Entry guards refuse with an actionable message, and never issue DML against the source:

- **sandbox or Developer Edition org only** (Production Guard tier check: a Developer Edition org says it is no sandbox, and is taken, as Forge takes it, for the development org it is -- by the preview and the removal too; a sandbox marked Staging is refused, on the **Load** tab before **Checkpoint first** takes anything and before the mute assigns a permission set);
- configured **protected environments** are refused, as is the source org recorded in the manifest, which the **Load** tab lists marked as the source without offering it;
- **mocked callouts**: detected through custom metadata (`mockDetection`); when it is not configured the guard is explicitly disabled and reported in the tab;
- an **empty dataset** is refused.

Then: schema alignment (missing fields dropped **and listed**, restricted picklists including per-RecordType assignment gaps via the UI API), **technical placeholders** for lookups that became required on the target (never a silent exclusion), a two-pass insert for cycle FKs, each **person account's contact** linked to the one the platform wrote with the account, or sent as a contact of its own where the target wrote none (see **Person accounts** below), and persistence of the `referenceId -> Id` mapping in the sas -- with which of its records the load **created** (inserted, or a placeholder) rather than linked or reused, and when it ran -- by this machine's clock, and by the target's own dates of the records it created, read back as it ends -- which is what removing it takes. A load without **Reload** leaves the loads before it in the org, and the mapping keeps them, each with what it created and its dates, for a later reload to purge or a removal to take. A load that **stops part way** keeps its mapping too -- cancelled, or failed once it had created or purged records (Production Guard refusing a later batch, a placeholder or a write the target refused, a pass after the inserts that threw) -- with what it created so far and its dates: a removal takes it back without loading again -- from the **Last load** card, or with `remove` on the command line -- and the next reload purges it. So does a load whose process was killed -- VS Code closed under it, the command stopped outright: as the target answers each batch, what it created is written to the sas beside the mapping, in a journal of the load (`referenceid-mapping.<org id>.load-<time>.ndjson`, keys and ids alone), and a journal no running process writes any more is read as a load that stopped part way, listed on the **Last load** card, removed or purged as above; it goes once a mapping holds what it names. The error, cancelled or failed alike, says what the load left, and names the removal beside the reload. One cancelled, or failed, before it created or purged a record keeps no mapping of its own: the mapping stays as the loads before it left it. The audit trail records a load cancelled before it wrote anything, and before the target refused anything, as **stopped**, under `LOAD_CANCELLED`, and one cancelled after, as **cancelled**, with its counts. An object the cancel stops while it is written -- before its rows go out, between two calls, or between the two writes of the emails, some of which wait for their task -- ends **stopped** on the **Load** tab, unless the target refused a row of it, and its line says what it inserted, what failed and how many rows the cancel kept from the target, which the audit trail counts as not sent. A write of its own that throws -- Production Guard refusing it, a call that fails -- ends an object, a reload's purge, the placeholders, the cycle pass or the statuses **failed** instead, its line saying what it did, what the failure kept from the target, and why; the audit trail counts the rows of an object the failure kept back as not sent too. A purge the target refused records of ends failed as well, saying how many. The **Load** tab counts the links the cycle pass left unresolved beside the ones it made, and the person accounts' contacts the load linked, sent as contacts of their own, or placed neither way, and names the links it could not make per object and lookup: each lookup left empty on a record the load wrote, and why -- the record it points at was not loaded, or the target refused the update, in its words -- and apart, a link that went with a record the load did not write.

Before the first write -- a reload's purge comes after it -- every required field the dataset leaves empty is checked against the configuration, and **all** the gaps are listed in one refusal -- nothing is written, and nothing purged, until each has a placeholder or a default. A line of an opportunity or a quote is held to a price, though the describe requires neither of the two: a line with neither is refused by the target (`total price must be specified`), so it asks a default for `UnitPrice`, and of a line that holds both only the unit price is sent, the target taking one. An account is checked as its kind is held: a business account to its `Name`, a person account to its `LastName`, though the describe of an org with person accounts requires neither, and a default for one goes to the records of that kind alone. Only the records the load writes are checked, and only they receive a default: a record it only links -- the standard price book, a selling model found by its key, a record a reload reuses -- is never sent. A default is the same for every record it fills unless it says otherwise: a text value may carry `{n}`, the record's rank among the records of its object in the dataset, or `{referenceId}`, each replaced per record; one that carries neither, given for a field the target's describe calls **unique** or for the object's **name**, gets the rank appended (`Frozen territory 1`, `Frozen territory 2`) -- run on a client sandbox, a default name given to two service territories was refused for the second, "That name is already taken", though the describe calls that name not unique (a Developer Edition org took two of the same name), and the platform holds business hours unique by name the same way. The rank is the record's place in the whole dataset, so a record gets the same value from one load to the next; the preview, the report and the command line say which defaults go per record, and the preview gives the first value. Objects with no record are left alone. An object the target lacks, or takes no insert of (not createable for the running user, like an error log the platform keeps itself), is **not sent**: the report names it among the objects not loaded, counts the records of it the load links as reused and the ones it had to write as failed -- in the audit trail too -- and the load ends with errors when it had records of it to write. A feed item whose type the dataset does not carry -- a dataset extracted before 1.38.2, whose rules cleared it -- is **left out** with what cannot go in without it, since a tracked change cannot be told from a post; the report says to extract the dataset again. A value the rules cleared is **left out** of the insert, so the target applies its own default (the running user as owner). A write of more than 200 records goes in one Bulk API 2.0 job, whose rows carry every field any of them carries: such a value goes as an empty cell, which the platform reads as a field left out, and each record's id comes back to the mapping whatever fields it carries. Objects are inserted parents first; a cycle is kept together and, inside it, whatever a required lookup points at goes first. Records the platform owns are matched, not inserted: the **standard price book** (standard prices are written before custom ones), the **direct AccountContactRelation** Salesforce creates with each contact, and the **contact role** it writes, primary, as it takes an opportunity with its `ContactId`: the dataset's role of that contact on the opportunity is linked to the one the platform wrote, given by an update the fields it lacks -- its role, which the platform leaves empty -- and never inserted beside it, which left the opportunity two roles of one contact. The platform's is the role made with the opportunity, the same second, by the user the load writes as, never one made under it later; when the target's automation made a second one of that contact in the same save, nothing tells which is the platform's, and the dataset's role goes in as read, the line saying why. The object's line, the report and the command line count it among the records reused, as written by the platform with their opportunity, and say any field the target would not take. So are the records the target keeps one of: a **selling model** it already holds, found by its type, pricing term and unit -- which the rules must keep, since a cleared key matches nothing -- and the **selling model option** joining a product and a model the load matched. The standard price book, the selling models and their options are looked up on a **Catalog** line of the **Load** tab, after what a reload reuses by its identity keys and before the alignment: it says whether the standard book was found, how many records of each object it linked, and why the target could not be asked about one; a read that throws ends it failed, with why, before anything is written. Options are written before the prices that need them. A record type the running user cannot use is dropped and listed, naming the type the record gets instead. An **Order or Contract** whose status is past Draft is created at a Draft status of the target (read from `OrderStatus` / `ContractStatus`), its children follow, and its status is applied last -- the report lists what the target refused. The **Load** tab's report says why records failed: per object, each status code and message, with how many records.

A record whose lookup the target will not take empty names an object `excludedObjects` leaves out cannot be loaded as it is -- the extraction says so (above) -- and the load **leaves it out**, with what cannot go in without it, before anything is written: counted per object on the object's line, in the **Load** tab's report and its preview, among the records not sent, and in the counting contract (`excluded-parent`), never asked a placeholder for. A placeholder declared for that lookup in `requiredLookupPlaceholders` is the configuration offering one: those records then go in pointed at it.

A record whose **parent this load could not write** -- refused by the target, of an object the load does not send, or held back in turn -- is **held back** before its insert, and so is what names it in turn: written without its parent, through any lookup the dataset gives a value, required or not, it would stand in the target as what it is not -- a contact whose account the target refused goes in as a private contact, and the target then refuses every relation of it. Such a record is counted as failed, `PARENT_REFUSED: the Account record its AccountId names was refused in this load`, as Forge counts a `parent_refused` row and Sync a `PARENT_REFUSED` one, and apart in the counting contract (`parent-refused`). A lookup the dataset leaves empty stays empty, and a duplicate the target skipped holds nothing back.

A record the target **refuses on fields it names** -- a validation rule of its own (`FIELD_CUSTOM_VALIDATION_EXCEPTION`), or a restricted picklist refusing its value (`INVALID_OR_NULL_FOR_RESTRICTED_PICKLIST`) -- is written again once, as Forge writes one in its first round (Forge goes on to three rounds, and leaves out the lookup a filter refused when the target lets it be empty; a load does neither): without those fields, or, for a picklist whose declared rule replaces a rejected value (`picklistRules` / `defaultPicklistRule`), with that value; a rule that would send again the very value refused, or an empty one, leaves the field out, and a multi-select picklist goes without all its values, since the refusal names the field and not which of them. The alignment cannot catch every such value before the write: a record type never given values of a restricted picklist takes none of them, while the UI API answers the field's whole value set for it. Taken the second time, the record is inserted, mapped and created by the load like any other, so its children are written against it; the object's line, the **Load** tab and the command line say which field it went without -- or which value it got -- what refused it, in the target's words, and how many records, and the audit trail counts them apart among the records created (`writtenWithoutFields`). Refused again, it fails with both refusals; a refusal that holds any other error, or names no field the record gives a value to, is a failure as before. The second write goes past Production Guard as the first did; a cancel that came during the first write keeps the refused records from it, and they stay the failures the target made them. The counting contract expects such a record as any the load inserted, and names it under the field it went without.

**Reload without refresh**: ticked, the button reads **Reload**, and a reload whose purge would delete or deactivate records asks first, with how many the preview's plan counts -- read first when no preview of that reload is shown -- armed by the target's name typed; a pilot's reload purges nothing and asks nothing. That confirmation also lists what the target runs as the purge deletes, as a removal's does, with the box that mutes it, the same box as the one beside the button. Ticking **Sweep too** takes as well what the target's automation made for each load the reload replaces, which the purge alone leaves -- the tasks a flow opens on each contact a load inserts went from 30 to 60 to 90 over two reloads on a real org --: each load's sweep is listed, as a removal's is, with the same two ticks, what fires as it deletes is read with the purge's, and the reload cannot be confirmed until both are read; it runs around the purge, part before its first delete and part once its deletes are through, and the report says per load what it took and what it left; one refused, or that did not take all it was asked to, ends the load **Partial**, never Completed. A load whose sweep left something -- refused, kept, or listed as made late or tied to nothing and not ticked -- stays recorded once the purge took its records, as a removal keeps the load it took back, with what its sweep found: the next reload with **Sweep too** sweeps it again, and so does a removal with **Sweep first**, and each lets it go once its sweep took all it found; a reload without it lets it go. The loads one reload or removal sweeps together are no other run in each other's window: what is tied to nothing of one is taken when asked, though the next wrote within the quarter of an hour. A reload cancelled or failed once its sweep had deleted says beside its error what the sweep took. Per-object identity keys (ExternalId, name, composite pairs) let the load reuse existing records, and the standard price book, selling models and options it matched are matched again before anything is purged, and kept. What earlier loads **created** -- the last one, and those before it that no reload purged -- and this one does not find again is purged **children before parents**, and undeletable objects are **deactivated** through a configured field. Business hours, which the platform never deletes (their describe says they are not deletable, and a client sandbox refused their purge, then refused them sent again: "The Business Hours Name is already in use"), are matched on **every** load, a reload or not, to the ones the target holds under their name -- the name the declared default gives them when the rules cleared it -- or under the identity keys the configuration gives `BusinessHours`, and linked rather than inserted: every org holds its own `Default`. One an earlier load created that a reload does not find again is never sent to be deleted: it is left in place, and the report, the command line and the preview count it as kept. A record they only **linked** is never purged: it was in the target before them, or is the platform's, and a reload whose rules or dataset changed would otherwise delete it the moment it no longer matches. A record an earlier load created that the reload finds again stays **created**, so its removal and the next reload still take it. What the target refuses to purge stays named for the next reload. A mapping written before loads kept what they created cannot tell its created records from its linked ones: a reload into an org whose sas holds one is refused before anything is written, as below, unless the org was refreshed since; then the reload purges only records of objects no load links, never one of an object with identity keys, a selling model or option, or the standard price book, and the report counts what it left in place. Activated orders are returned to a draft status first, and one the purge leaves in the org -- its delete refused, or not reached when a cancel or a failure stops the reload -- gets its status back: what that leaves on it is kept with the load that created it, so that load's removal does not read it as changed since, and one whose status cannot be given back is listed among the purge's failures. Activated contracts are deleted as they are: the target deletes one so, and a sandbox would not set one back to Draft. The records of a load the target did not date are judged as its removal judges them, by this machine's clock at its end read on the target's; from a target that does not tell its clock, what the purge leaves on them is not kept, and that removal reads them as changed. Custom prices are deleted before standard ones, direct relations go with their contact, and a record already deleted by a cascade counts as purged. So does one the target refused while a record the purge reached later stood -- a contract item price under an activated contract the purge deleted next: once its deletes are through, the purge sends once more, children first, what the target refused to delete, and the second answer counts -- deleted, or already gone, the record is purged; refused again, it stays a failure, in the target's words of that answer -- and its line says how many went that way. It then reads back what is still refused: a record it read before its first delete and no longer finds went with a parent, and is purged; one it could not read before -- out of the session's sight, which a query no more finds than a deleted one -- and every one when that read fails, stays a failure, which says it was not checked. Stopped by a cancel or a failure, it neither sends them again nor reads them back: its line counts them failed, and the next reload or a removal finds them gone. Native duplicate rejections on the target are an explicit degraded mode: those records are **skipped and listed** (recognised by their status code, whatever the org's language). The **Load** tab's report says what the purge deleted and deactivated, per object, what it left in place, and why the target refused the rest: each status code and message, with how many records, as for the load's own failures.

**Person accounts**: the platform writes a person account's contact itself as it takes the account, and links the two by the account's `PersonContactId`, which no insert or update sets. The load never sends such a contact -- one the sidecar (`personcontact-sidecar.json`) names, or any contact the dataset flags `IsPersonAccount` -- beside the platform's. The contacts go after the accounts, and at their turn the load reads back the contact the platform wrote with each account it has in the target -- inserted, or found by a reload's identity keys -- and maps the dataset's contact onto it, so that what points at it (a case's contact, a contact role, a custom lookup) is written against that one. The contact object's line, and a **Person contacts** line, say how many it linked, sent as contacts of their own, or placed neither way; those it linked are counted as linked records, which the counting contract expects and the verification counts in the target. One whose account the target holds as a business account -- its record type there is no person account's (the record type issue says why, when the load dropped it), or the target has no person accounts at all, which its describe says before anything is asked -- goes as a contact of that account, as any contact does: counted as inserted, created by the load, so that a removal or a reload's purge deletes it as any other, and listed as sent as a contact of its own, with why, link by link. One whose account was not loaded, or is not in the dataset, is not sent, and is counted as failed with why; what pointed at it is left empty, and the cycle pass says so. Neither a reload's purge nor a removal sends the delete of a contact the load linked: the platform deletes it with its account. The person fields the account carries (`FirstName`, `LastName`, `PersonEmail`, `PersonMobilePhone`, the contact's custom fields as `__pc`) go in with the account, as the rules give them for `Account`: a rule written for a field of `Contact` does not reach the person account's, and the contact's own row is never sent. A person account goes without the `Name` the platform computes from its first and last names, whatever the rules give it, and a business account without the person fields, which it holds empty. Which accounts are person accounts is read from the dataset: the sidecar, the `IsPersonAccount` flag when the rules kept it, and a last name, which only a person account holds.

**Pilot**: a single root graph (~2 min) before committing to the full load, with the catalog its prices need though none of its records names it: the standard prices, the standard price book and the selling model options.

**Preview**: what a load into the selected target would do, with the options ticked, and nothing written -- read through the code the load runs before its first write: the entry guards (a target the load would refuse is refused, saying why), what a reload finds by its identity keys, what the catalog already holds, the schema alignment and the required fields. Per object, the table says how many records the load would insert, how many it would link -- found by identity keys, or in the catalog -- how many fields it would drop and picklist values it would rewrite, how many records it would not send, and on a reload, how many records of the loads before it the purge would delete or deactivate. Below it: the objects not loaded and why, the placeholders and defaults with the records each fills -- and for a default that gives each record a value of its own, which, with the first record's value -- the person accounts' contacts, which go in with their account, counted apart, and on a reload what the purge would keep because the platform does not delete it. Beside the plan, the target's **active validation rules** on each object the load would insert records of, each with the field its error names when the rule's metadata says one (`ErrorDisplayField`, which the org gives as the field's label in its language, read back to the field's API name from the org's field definitions), read as Sync's simulation and Forge's pre-flight read them: a preview cannot evaluate a rule, so a record one of them refuses is counted to insert -- run on a client sandbox, three loads in a row were refused by three rules of the accounts, each fixed rule showing the next. Each rule's formula is read from its metadata, five a request in Tooling composites and a hundred rules at most, and a rule whose formula holds only on a change of a record -- `ISCHANGED`, a `PRIORVALUE` compared with the value, a `NOT(ISNEW())` guard -- is **named apart**, not listed: no insert meets it (run on a large client sandbox, the preview listed fourteen rules of one object, most of them such guards). A rule whose formula cannot be read, or is not, stays listed. The rules of an object that receives **only a placeholder** are listed with the placeholder: it goes in with its name alone, and one refused stops the load. When the target will not list them, the preview says why. The record type the target would give the records it creates without one is predicted under the plan, and with **Checkpoint first** ticked it says what the checkpoint would hold and cost, nothing taken. What only a write tells is not in it: a record the target refuses, a duplicate it skips, a contact's direct relation or an email's task, linked to the one the platform writes once its record is in. The role of the contact an opportunity goes in with is counted apart, never to insert: the platform writes it with the opportunity, and the load links it once the opportunity is in. From the command line, `load --dry-run` prints the same.

**Stop the run**: while a load runs, the **Load** tab offers it, as Live Operations offers its cancel: the load stops before its next write, keeps its mapping when it wrote something, and a removal or a reload then takes back what it wrote. A cancel the extension refuses -- the load already over -- is said in a notification.

**From the command line**: `load --reload` is a replace. Before anything is written, the purge included, it reads what a removal of the loads before it would do -- the removal's own preview, below -- and is refused (exit `1`) when that removal would leave records of theirs in the org: kept as changed since the load, kept for records that stay under them -- a contact made by hand since under one of their accounts, which the org would delete along with the account --, of an object the user may not delete, out of the user's sight, or unread; or when one of those loads was recorded before loads kept what they created. What hangs from their records is read as the removal reads it: what came with a load -- made as it wrote, unchanged since -- goes with it, unless a record that stays hangs from it in turn -- a campaign member added since to a contact the target's automation made with the account --, and what the target's automation likely made for it, as its user within a minute, holds nothing when `--sweep` takes it first. Loaded again beside them, the dataset would stand in the target twice, and the purge would delete what was changed since, and what stays under them along with them, which a removal keeps. Take the load back with `remove` first -- `--include-changed` takes what changed since too, and what was added under them since -- then load. The reload is refused the same way (`REPLACE_LEAVES_RECORDS`), once it has read what it finds by its keys, when its purge would have the org delete along a record it finds again: a quote it finds by its name under the opportunity an earlier load wrote, which nothing finds again, went with that opportunity, and the reload wrote its lines under a quote no longer there. Give that parent identity keys too, or take the load back first. `--gone-first <file>`, with `--reload --dry-run`, names the records taken back before the reload runs, a JSON array of their ids: hanging from the loads' records, they hold nothing. `sandforge-env` hands it the records its apply takes back first; a reload that runs reads what is still there. What the target runs as the purge deletes is read and named next, as a removal's is: nothing is written while something fires or could not be read (exit `1`, `refused (AUTOMATION_NOT_ACCEPTED): …`, and with `--json` `refused: { code, message }` beside `refusals`; its dry run says so), unless `--accept-automation` takes it, or `--mute-automation` keeps it quiet: the refusal names the permission sets a mute would assign, under its lease, never a command that assigns them by hand. The purge takes what the loads before it created, not what the target's automation created for them -- the tasks a flow opens on each contact a load inserts stayed, one set per load replaced --: `--sweep` takes that too, the sweep of each load replaced as its removal makes it (`--sweep-late` and `--sweep-untied` take what it lists as made late or tied to nothing), around the purge, under the mute's lease when muted. What the target runs as it deletes is named once the sweep has read what it takes, before the first delete, and refused unaccepted as the purge's is (exit `1`, `AUTOMATION_NOT_ACCEPTED`); `--dry-run --sweep` lists what it would take, per load, and reads what fires on that with the purge. The report says per load what it took (`sweeps`); one refused, or that did not take all it was asked to, ends the load on exit `3`, its `status` `partial`. What a sweep left stays tied to the load it replaced, which stays recorded: a later `load --reload --sweep` or `remove --sweep`, with `--sweep-late` or `--sweep-untied` for what it listed so, takes it. What it finds changed since that load it keeps, as a removal keeps the records changed since, and names with what takes it: kept so, unasked, it ends no reload partial -- each reload after the first ended on exit `3`, and none could take it --, and `--include-changed` with `--reload --sweep` (on the **Load** tab, the box the reload's confirmation shows with the sweep) takes it. Asked with `--sweep`, the reload lists before anything is written what the sweep would take, as its dry run does -- a list that cannot be read writes nothing (exit `1`) --, and a refusal names what fires on the purge's deletes and on the sweep's, each with what deletes it; a reload cancelled or failed after its sweep deleted prints what the sweep did beside the error, and `--json` carries it as `sweeps` on `frozen:load:error`. A pilot's reload purges nothing, and is not asked. The **Load** tab's **Reload** is the same replace -- it sent a reload alone, whose purge deleted without a word the records someone had changed since the load -- and so is its **Preview** with Reload ticked. Refused, the tab says on the **Last load** card what a removal would leave and why, in the extension's words, and offers the way out: take that load back first -- the records changed since, and what was added under them since, included, once the org's name is typed, as for any removal -- then load again; or cancel, which writes nothing. `--max-total <n>` holds a load, or a reload, to the records its dry run counted to insert: one that would insert more is refused once it has read what it would write, before its first write and the purge, and a dry run given it says so and ends on exit `1`. With `--json`, each step adds to what the panel would receive what an environment reads of it: the dataset's folder, version and digest (`sha256:` over the files a load reads -- the manifest without the verdict a verification writes back into it, every `data/*.json`, the record types, the person accounts' contacts and the platform's records -- the same wherever the folder is moved or copied) for `extract`, `load` and `verify`; the mapping file for `load`, `verify` and `remove`; per object, what the step counted; and the verdict per object of `verify`, and of the verification a load chains.

**Muting the target's automation**: `load --mute-automation` reads what the target runs on the objects the load writes, and on a reload what fires as its purge deletes, and keeps quiet, for the load alone, what the target's own bypasses keep quiet; its permission sets are given back after the last write; with `--dry-run` it says what it would assign and assigns nothing. See [Muting the target's automation for a run](../faq.md#muting-the-targets-automation-for-a-run).

**Checkpoint first** (off unless ticked, on the **Load** tab): the load takes a checkpoint of each object of the dataset, and each the target's flows that still run create as it writes them, files included, before the mute's permission sets are assigned and before its first write, a reload's purge among them. A rewind to it takes the load back, and what anyone did on those objects since. A checkpoint holds an object whole: its cost is that of the target's tables, not of the dataset; **Preview** says it, and the load asks nothing of its own. It leaves out Chatter posts, Knowledge article versions, users, permissions and setup, a placeholder's object unless the target's automation adds it, and what an Apex trigger or a flow SandForge could not read creates outside it, which a rewind leaves as it is. It is kept on this machine, unencrypted and readable by you alone, for the days `sandforge.checkpoint.beforeRunKeepDays` sets (7 by default, 0 until it is deleted), and listed on the Checkpoints page, marked **Before Frozen Dataset load**. A checkpoint refused or stopped as it is taken refuses the load, nothing written. A load that wrote no record deletes it, and says so; one that stopped part way keeps it, and so does one that failed without saying what it wrote. The report names it with **Rewind to before this load…**, which opens the preview of that rewind, and says what it takes that the removal does not; the **Last load** card offers it after a removal, and marks a load a rewind to it took back: see [Rewound runs in the histories](checkpoint.md#rewound-runs-in-the-histories). A load of an earlier session offers neither: the mapping does not name its checkpoint, which the Checkpoints page still lists. From the command line, `load --checkpoint-first`, with `--checkpoint-keep-days <n>` and `--checkpoint-exclude-object <ApiName>`: the command takes it once the load may write and before the load's lease; `--dry-run` says what it would hold and cost and takes nothing; refused, the load exits `1`, nothing written. A load refused before it writes, or that reports it wrote nothing, deletes it, and one that stops or fails part way keeps it, what it wrote not being told there. `--json` gives it under `checkpoint`, with the `sandforge-checkpoint rewind` command on its output.

**The record type the target gave**: a record the dataset holds on Master, with no record type read, or whose record type was dropped goes in without one, and the target gives it its type: the default of the user the load writes as or, where that user's describe names Master, the one other type open to them when there is exactly one. **Preview** predicts it per object, with why each went without one, and once the last record is written the load reads back the first 200 of each object: the report says how many, why and what they hold, naming what still ran of a muted load where they hold another type than predicted, and a read-back that failed in the org's words. The command line prints the same, and `--json` carries `recordTypesGiven`.

**Automation**: before its first write -- once its entry guards and Production Guard let it through, before its emails are judged, the checkpoint it takes first and the mute's lease -- a load names what the target runs as it inserts its records and updates them: each flow, Apex trigger, process and workflow rule of the objects of its dataset, from the read its emails are judged on, what the mute's plan keeps quiet and what a bypass the user holds keeps quiet left out. While something runs, or the target would not say what it runs, the load is refused, nothing written (`AUTOMATION_NOT_ACCEPTED`), unless it has the accord -- `--accept-automation`, or on the **Load** tab the box **Load although … runs automation as the records go in**, never ticked unasked; `--mute-automation` keeps quiet what tests the org's bypass, and the refusal names the permission sets it would assign under its lease. Run on a scratch org, a flow after save on the creation of an opportunity product, which deleted that product, left the load's two products deleted the second they went in: the load asked nothing, and only its verification saw it. **Preview** and `--dry-run` list what runs and say the refusal a load would meet (`refusalCodes`); the report and `--json` carry it as `automation`, and a refused load beside its error. What fires as a reload's purge and its sweep delete is asked apart, as said above.

**Emails**: before its first write -- once its entry guards and Production Guard let it through, before the checkpoint it takes first and the mute's lease -- a load reads what the target runs on what it writes (its inserts and updates, a reload's purge and sweep), as Seed and Sync read it, the mute's plan holding when it mutes. Its flows, processes and workflow rules that send an email are counted on the records of the dataset -- at most, as Production Guard counts a load, a pilot's and a reload's records found again among them -- against what the target has left today of its daily email limits (`/limits`): past them, the load is refused, nothing written, whatever accord it has (`FROZEN_EMAILS_EXCEEDED`), since a record whose flow fails in the save is refused. When something that still runs sends one, or could not be read, whether the target delivers them is read with one line of anonymous Apex that sends nothing, as the user the load writes as: on System email only or No access, nothing is asked; on All email, or when the org would not say, the load is refused, nothing written (`EMAILS_NOT_ACCEPTED`), unless it has the accord -- `--accept-emails`, or on the **Load** tab the box **Load even though … delivers the emails** under the mute's, never ticked unasked; `--accept-automation` never stands for it. A mute whose lease, read back, does not hold every set it was to assign leaves running a sender no question named: the load is refused, its lease given back first. **Preview** and `--dry-run` say what the load would meet -- the count per limit, what sends, the deliverability read, and the refusal -- planning the mute when it is ticked, nothing assigned; the report and `--json` carry it as `emails`, and the audit trail what the org said of them and that they went with the accord. Addresses the `email` generator pseudonymizes go under `example.invalid`, but a field kept in clear keeps its own, and an owner, a record the target already holds and an address an alert names can still be written to. What an Apex trigger sends is read nowhere.

### Post-Load Verification

Read-only, chained to the load (or replayed with **Re-verify**): per-object counts against the **counting contract** and orphans on mandatory lookups, both among **the records this load wrote** (a sandbox is seldom empty), presence by key (ExternalId), and each account the target holds as a person account holding the contact the load linked. A business account, which took the dataset's contact as one of its own, is not judged there -- the counts are -- and a target whose describe has no person accounts is not asked about them. A record the load wrote again without a field the target refused is counted as any it inserted, and its empty lookup is no orphan, nor its empty key a missing one: the counting contract names it under that field. It also says what the load **did not write**, from the counting contract, whose counts are of what the load wrote and match them however much failed: per object, the records the target refused and those held back for a parent it refused. The records of an object the load could not send -- the target lacks it, or takes no insert of it, as the preview said -- are counted apart, "not loadable, as the preview said", and fail nothing. Beside the orphans of the mandatory lookups, it counts the lookups the load left empty because the record they name was not loaded -- skipped, or refused after its child was written -- and does not ask about those records again as orphans. It gives each object of the counting contract a verdict of its own: passed when the org holds every record of it the load says it wrote, the load wrote all it had to, and none of them is an orphan on a mandatory lookup or misses its presence key. For robustness it re-measures until **two identical readings** before returning a verdict: `passed`; `partial` when all that is wrong is that the load wrote part of the dataset -- some records of an object, none of an object whole -- or left lookups empty for a parent it did not load; `failed` when it wrote none of an object, or the org does not hold what the load says it wrote; `unstable`. The verdict is recorded in the manifest under `controls.dryRunLoad`. What the mapping names is counted against the counting contract of the load that wrote it: a load that stopped part way -- cancelled, or failed once it had written -- keeps its mapping and writes no contract, and **Re-verify** refuses it, saying why, rather than judging its records by the contract of the load before. Reload the dataset -- the reload purges or finds again what the stopped load wrote -- or remove the stopped load before loading the dataset again, then verify: loaded again without **Reload**, the dataset goes in beside what the stopped load wrote. It refuses first -- before anything the sas's mapping says -- when `sasDir` names another sas than the one the last load wrote to, or when that sas no longer holds the counting contract the load wrote (moved, emptied or replaced since), and says so.

### Removing a Load

The **Load** tab's **Last load** card names the last load into the target selected above -- run from the panel or from the command line; the sas keeps a mapping per target org, so a load into another org leaves it named -- and **Remove the records this load created** takes it back without loading again. What goes is what the mapping says the load **created**: every record it inserted, and each technical placeholder -- after a reload, with the records earlier loads created that it found again and kept, as the confirmation says. What it linked to or reused stays: the standard price book, a selling model or option the target already held, the direct AccountContactRelation Salesforce made with a contact the load did not create, a record a reload found by its identity keys that no load created. The direct relation of a contact the load created goes with the contact: "To remove a direct relationship between a contact and an account, change the contact's primary account or delete the contact" (Salesforce Help, "Considerations for Relating a Contact to Multiple Accounts"). So does the task the platform wrote with an email the load created, with the email: "Deleting an EmailMessage record automatically deletes the associated Task" (Salesforce Help, knowledge article 000384885). So does the contact role the platform wrote with an opportunity the load created, with the opportunity. The load keeps each with the record it goes with: the confirmation counts neither among the records it keeps, and neither a removal nor a reload's purge sends its delete. The contact the platform wrote with a person account the load created is neither taken nor kept: the platform deletes it with its account, and refuses a person contact deleted on its own, so the confirmation counts it nowhere. A contact the load sent as one of its own is one it created, and goes as any other. Business hours the load created stay: the platform does not delete them, so no removal sends their delete -- sent, they were refused, the removal ended partial and the load was offered again -- and the card, the result and the command line name them as kept. Once the last load's records all went, or when it created none, the card offers the load before it whose records are still in the org, as an **Earlier load**: loads are taken back one at a time, the last first, since a load's records can depend only on those of the loads before it.

The removal is Forge's, the one a Forge run's history entry offers. The confirmation names the org, which you type, the records per object it takes, and what the target runs as they go -- what fires as an activated order is set back to Draft, then before and after each delete, what a ticked sweep deletes among them, read again as the ticks change it -- with the permission set that would keep a bypass quiet and, where a bypass silences something of it, a box that mutes it for the removal, under a lease taken right before the first delete, once the question about the objects your user may not delete is answered, and given back as it ends; what it muted is said with the result. Production Guard judges the delete, and refuses a production org. Children go before their parents, an activated order is set back to Draft first (and given its status back if it stays), an activated contract is deleted as it is, with its item prices, and custom prices go before standard ones. The load is dated by the target's own dates of what it created, read back as it ended, as a Forge run is; a load whose dates could not all be read back is dated by this machine's clock instead, and ends with its last write as the target dated it: a contact made by hand under its account seconds after it stays, with the account. A record that records staying in the org depend on is kept -- through a lookup the org will not let them lose too: a price an order line that stays still uses, a standard price a custom one that stays needs, a selling model option an active price that stays is sold under, the products and actions of an activated order the removal keeps, and the item prices of an activated contract that stays -- and so is one changed since the load, or one that records added since depend on -- unless you tick **Also remove the records changed since the load**. Ticking **Sweep first** sweeps, before the load's records go, what the target's automation made for the load -- Forge's sweep (`ForgeRunSweep`): what it ties to the load's records, by a lookup at one, by one's lookup at it, or through what hangs from those, three links at most, among the records the load's user created in the load's window, as the target dated its writes, from a second before the first to a minute after the last -- a load killed part way, which never read its dates back, is dated by the records its journal names, from the first created to the last, read back from the org or its recycle bin -- on the objects the load wrote, their children, the standard side-effect objects (tasks, events, feed, email messages, notes, case comments) and the objects the target's flows create, less every record the load's mapping holds; listed in the confirmation before you type the org's name -- which cannot be confirmed until that list, and what fires on what it takes, are read, nor with the sweep once its list could not be --, per object, classed as [Sync's](sync.md#removing-what-a-run-created) are, judged by Production Guard, and recorded in the audit trail beside the removal. With no more asked it takes what was made for the load. Two ticks take what came late -- tied, but more than a minute after its record, up to 15 minutes, or by the org's Automated Process user -- and what is tied to nothing of the load, the second refused, in the extension's words, when another run of this machine, of any module, wrote to the target in the window -- a load the same removal or reload sweeps is none; a load from another sas into the same org is one, told by the sas it wrote to, which the audit trail records with each load, and the command line in its journal folder (`frozen-loads.ndjson`) --, or when that user created records in it on objects neither the load nor the automation reaches. **What stays, and why** says the rest, and the button says what it does and how much ("Remove 4 records and what the sweep takes"). A removal that kept records for what the automation likely made under them names them and offers **Take back what the target's automation made for this load, then remove again**; what a sweep found made is kept with the load for a later removal. It runs first, once the removal has read the load's records -- a record a roll-up summary restamps as the sweep deletes its child is then no change since the load -- so that a record the automation hung under one of the load's holds none of them back: run for real, a removal kept eight appointments and seven work orders for the feed items the target's automation created under them during the load. It runs in **Live Operations**, where Cancel stops it before its next call to the org; the audit trail records it (`cleanup_delete`, module `frozen`, counts only), the sweep in an entry of its own; what the org refused is sent once more once the rest has gone; a sweep refused, or that did not take all it was asked to, ends partial a removal that took every record of the load -- one that left records of its own ends as it did, partial or failed --; the result says per object what was deleted, what was already gone, what was kept and why, and what the org refused, in its words -- and what that second try changed -- and names the files attached to the records it deleted that stay in the org -- a confirmation the org generated for an order, say: the removal takes only what the load created.

The mapping then forgets the records that went and is **marked**, whether the removal ended or was cancelled, with when, how many every removal deleted or found gone, and what the last one left. A removal that left none of the load's records in the org is not offered again. One that left some -- kept for a change since or for records that stay, refused by the org, or not reached before you cancelled it -- leaves the card offering **Remove what is left of this load's records**, with or without the records changed since: the confirmation names only the records left, and which removal left them; the result and the audit entry say it picked up where that removal left off; and the mark then counts what every removal took, a cancelled one's included. One that took nothing is offered again too. Once none of the load's records is left, the card offers **Take back what the target's automation created**: the sweep alone, for what a sweep that failed left in the org. Each reads what an earlier one left on the records as its own doing, not as changes. A sandbox refreshed since the load is refused -- its records went with the refresh -- and so is a mapping written before loads kept what they created, which a **reload** does not replace either: it would delete what someone changed since, and is refused before anything is written. **Re-verify** refuses a load whose records were removed: load the dataset again first. It refuses one a removal took part of too, saying how many records it left: remove what is left, or reload the dataset, which purges or finds them again.

From the command line, the same removal, through the panel's own handler: it prints the same plan, reads what a sweep asked with it takes, then what the target runs as the records of both go, and says it. Without `--accept-automation` it then deletes nothing (exit `1`, `AUTOMATION_NOT_ACCEPTED`) while something fires or could not be read, and names the permission sets `--mute-automation` would assign, never a command that assigns them by hand; `--mute-automation` mutes what the target's bypasses silence, under a lease taken before the first delete and given back as the removal ends, and what no bypass keeps quiet still needs `--accept-automation`. Only then does it ask you to type the alias (unless `--yes`), and remove; `--json` says what it muted under `mutedAutomation`, and `status` is `partial`, or `cancelled` once the sweep was stopped, with exit `3`, when the load's records all went and a sweep was refused or did not take all it was asked to; a removal that left records of its own keeps its own `status`, `partial` or `failure`, with exit `3` all the same. `--include-changed` takes what changed since the load too, `--sweep` sweeps first what the target's automation made for the load, what it ties to the load's records alone, `--sweep-late` and `--sweep-untied` take too what came late and what is tied to nothing, the second refused as the tick is, and `--sweep-list` lists what that sweep would take and what it would keep, and deletes nothing. Each other load the mapping records whose records all went -- a load a reload replaced, kept for what its sweep left -- is swept with it, each in its own window, listed and said by its load's date, and let go once its sweep took all it found. A removal that left records names what the automation likely made that kept them, and that `--sweep` takes it. Run again after a removal that left records in the org, it prints what that removal left, asks, and removes those; once none is left, it says so, deletes nothing and ends as done (exit 0), as it does when no load into the target is recorded, or the load created nothing a removal takes. With `--sweep`, the sweep then runs alone, held to what fires as a removal is, and the command ends as it did: exit `3` and `partial` while the org refuses what it was to take. Run from `sandforge-env destroy --sweep`, the run stays partial until then. A removal refused before its first delete -- for what fires without `--accept-automation`, by Production Guard, its question answered no, or for its mute -- ends on `refused (CODE): …`, with exit `1`, and with `--json` carries it under `refused` (`{code, message}`) and its code in `refusalCodes`. `--preview` says what the removal would do and does nothing: Forge's removal, stopped before its first write, as `sandforge-seed --remove --preview` stops it -- per object, the records it would delete, those it would keep as changed since the load and who last changed them, those gone already, those it cannot see, and those it would leave because the user may not delete them; what the target runs as they go; what it would be refused for, each under the code the removal is refused with (`refusalCodes`) -- a production org (`GUARD_BLOCKED`), one whose override lets the delete through and whose question the command line answers no (`GUARD_DECLINED`), a target refreshed since the load, or that automation without `--accept-automation` -- with `--mute-automation`, what still runs once what a mute would keep quiet is left out, nothing assigned, and the mute's own refusal for a user who cannot assign permission sets; and the business hours it keeps. It deletes nothing, writes nothing to the sas or the audit trail, asks nothing, and ends as done (exit 0) once it has said it, its refusals included. It cannot know what hangs from the records, which a removal reads at each object's turn: a record kept for records that stay is counted with those to delete.

```bash
pnpm exec tsx packages/extension/cli/sandforge-frozen.ts remove --config frozen.json --target MY-DEV
pnpm exec tsx packages/extension/cli/sandforge-frozen.ts remove --config frozen.json --target MY-DEV --preview
pnpm exec tsx packages/extension/cli/sandforge-frozen.ts load --config frozen.json --target MY-DEV --reload --dry-run
```

### The Rules File

The extraction reads the pseudonymization rules from `~/.sandforge-sas/rules.json` by default (`rulesFilePath` or `sasDir` in the configuration move it), and is refused without them. The **Extraction** card of the **Extract** tab says where the file is and what it holds -- its `rulesVersion` and how many fields it rules -- or that it is missing or unreadable, and **Run extraction** waits until it is there. **Create rules file** writes `{"rulesVersion": "1.0.0", "rules": {}}` there, never over a file already there, and opens it in an editor; **Open rules file** opens the one there. An empty file is valid and safe: every field without a rule is cleared, the platform's own words aside, and the extraction's result then lists what it kept without a rule, for review. Prices are cleared like any field: a line of an opportunity or a quote then holds none, which the target refuses, so the extraction names `UnitPrice` among the required fields the rules leave empty, and a load asks a default for it, unless the rules keep a price.

The file is a JSON object with a semver `rulesVersion` and `rules` keyed `Object.Field`, each naming a `generator`: `keep` (only with `"approved": true`, set by whoever reviewed it), `clear`, `firstName`, `lastName`, `companyName`, `phoneE164`, `email`, `registrationSIV`, `contractNumber`, `postalCodeGeneralize`, `dateMonthStart`, `dateShift`, `geoRound1` or `kmRound10`; a `comment` is kept as written. For example:

```json
{
  "rulesVersion": "1.0.0",
  "rules": {
    "Contact.Email": { "generator": "email" },
    "Account.Industry": { "generator": "keep", "approved": true, "comment": "reviewed" }
  }
}
```

### Security and the Quarantine Directory (Sas)

- The **sas** (`~/.sandforge-sas` by default) is **outside the repository by construction**: `SasPathGuard` refuses any output path located inside the repo. The selection (source IDs), `rt-map.json`, the `{{TOKEN}}` values (`tokens.json`) and the `referenceId -> Id` mapping never leave it.
- The **salt** is kept in VS Code's secret storage, never in a file nor the repository; only its **fingerprint** (12 hex) is recorded and shown. A second salt is never made while one is kept -- determinism across dataset versions would be lost. See [the salt](#the-salt).

### The Salt

- **Made once, kept.** The first extraction makes the salt every pseudonym is drawn with, keeps it in VS Code's secret storage and says so; every later extraction pseudonymizes the same records the same way. The status strip shows its fingerprint and where it comes from. A load never needs it.
- **Shared between teammates.** Two people extract the same pseudonyms only with the same salt: `SandForge: Copy Frozen Dataset Salt` copies yours to the clipboard, and `SandForge: Use a Frozen Dataset Salt` keeps the one a teammate gave you (it asks before it replaces one already kept). Give it as you would a password: whoever holds it can tell which source value a pseudonym was drawn from.
- **CI and the command line.** `SANDFORGE_FROZEN_SALT`, where it is set, wins over the salt kept in the editor. `sandforge-frozen` reads that variable, or the file `--salt-file <file>` names, and never makes a salt: an extraction given none is refused.
- The bridge **redacts**: the selection sent to the UI carries no source ID, and the details of `clear-empty` violations (which may embed a residual value) are redacted on the extension side.
- All DML goes through the existing **Production Guard** (tier check; each decision is recorded with the load in the audit trail, unless `sandforge.safety.auditLogging` is off).

## Limits

- Selection measures volumetry by running a **real extraction pass** on each candidate and on the retained roots (bounded by the budget), one statement per object of the graph each. It is an interactive operation, not a batch job: past ten minutes it stops and keeps what it decided.
- Without `mockDetection` configured, the "mocked callouts" guard is disabled (shown as a warning). Deploy it before loading into an org that makes callouts.
- Reload without refresh needs identity keys that are usable on the target (ExternalId recommended).
- A removal takes what the mapping of its target org names, one load at a time, the last first. Each target org has a mapping and a counting contract of its own in the sas (`referenceid-mapping.<org id>.json`, `counting-contract.<org id>.json`): a load into another org leaves them as they were, and the last load into each can still be verified, removed or purged by a reload. A load into the same sandbox after a refresh replaces that org's mapping: the loads before it, whose records went with the refresh, are no longer named. A sas written before mappings were kept per org holds one `referenceid-mapping.json`, read for the org it names and rewritten as that org's at its next load.
- Of a mapping written before loads kept what they created, a reload never purges a record of an object with identity keys in the configuration, a selling model or option, or the standard price book. A load run with identity keys the configuration has dropped since could have linked records of other objects: nothing records it, and the reload purges them.
- Picklist values outside the RecordType assignment require the **UI API** on the target (available on recent orgs). It does not see a record type never given values of a field, for which it answers the field's whole value set: the target refuses such a value at insert, and the record is written again on the declared rule.
- A record holding two values its record type refuses is refused for the first alone -- run against a real target, the refusal named one field of the two -- and, written again without it, refused for the second: it fails.
