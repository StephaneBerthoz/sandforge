# Frozen Dataset

Extract a business dataset from a UAT sandbox **once**, pseudonymize it deterministically, freeze it (manifest + salt fingerprint), then **replay it identically** after every dev sandbox refresh -- with a non-reidentification gate before versioning and a verification pass after loading.

Typical case: a Developer sandbox refresh leaves you with metadata and zero records. Frozen Dataset gives you back a realistic set of root records covering your functional paths in one run, without ever shipping identifying data.

## Quick Start

1. Open **Frozen Dataset** from the sidebar (or `SandForge: Open Frozen Dataset` from the command palette)
2. **Extract** tab: fill in the root object, the coverage axes and the volume budget, then **Save configuration**
3. Set the salt -- `export SANDFORGE_FROZEN_SALT="<stable-secret>"` (never in the repository) -- and create the pseudonymization rules file
4. **Run selection** (coverage matrix), then **Run extraction**. The 4-point control must return PASS for the dataset to be written
5. **Load** tab: pick the target sandbox, tick **Pilot** to try a single root graph first, then **Run load**. Post-load verification is chained automatically
6. To take a load back, **Last load** on the same tab removes the records it created -- see [Removing a Load](#removing-a-load)

## Features

### Extraction Flow

1. **Coverage-matrix selection** (no random sampling): each axis is a configurable SOQL aggregate query; the module enumerates the **combinations actually observed** in the source org and keeps **one healthy root per combination**, plus one per declared edge case. A root is healthy when **its own records** hold at least one record of every `expectedObjects` entry -- it is judged on the same scope-aware extraction the dataset is made of, not on Forge's discovery graph, which describes the schema and is the same for every root of an object. A combination with no healthy root is listed as uncovered **with the reason** the last candidate was turned away. The volume budget (2,500 records by default) is **enforced mechanically**: anything above it is refused.
2. **Scope-aware extraction**: reuses `RecordScopeCache` and `ScopedSoqlBuilder` (full descendants plus the reference data they need, never `SELECT *`), with a frozen date bound (`CreatedDate <= asOf`) and an `rt-map.json` written to the sas. Discovery runs once per run, up to `maxNodes` objects (default 50) -- a cap raised, up to twice it, for the parents their records cannot be written without; when it stops at that cap, the selection and the manifest **say so**, and say when it was raised. The dossier grows from the roots through the lookups between records, both ways: the account an opportunity names, the quotes under that account. A lookup the platform will not let a row leave empty also holds the row to the dossier: a quote line whose quote is not in it is left out. One the row may leave empty holds it to nothing -- a quote under the root's account is kept whichever opportunity it belongs to. The **catalog** -- prices, products, selling models, price books, and the categories products are assigned to with the catalogs that hold them -- is read by what the dossier's records name and never walks down into other dossiers: a price book met through a lookup brings none of the quotes or orders priced from it, and a category none of the other products assigned to it. Its records are fetched by id when they are named late, and whatever `maxNodes` left out of the graph: each line carries its price, and each price its product, its book and its selling model, with the **selling model option** that lets the product be sold under that model, and each assignment of a product to a category its category and that category's catalog, unless `excludedObjects` leaves them out -- by name, whether the graph reaches them or not. The **items of an order past Draft** come the same way when discovery stopped before them, unless `excludedObjects` names them: the load writes such an order as a draft and activates it once the rest is written, and the platform activates no order without a product, so the extraction reads the items of the orders past Draft in the source -- and only those -- with their prices. A price book keeps one price per product and currency, and per selling model where the dataset carries the models. The **standard prices** of the products in the dataset are read with it, and the standard price book is marked so the load can match it; `excludedObjects` naming the price books keeps that one, as Forge keeps it: the load matches it and never writes it, so the standard prices still go in. What an object left out this way costs is **named**, not hidden: the records that need it stay in the dataset as they are, and the manifest counts, per object, those that cannot be loaded as they are -- a line without its price, a price without its product or book, a price sold under a selling model without its option, an order past Draft left with no item it can be activated with, which the load leaves a draft. Objects without `CreatedDate` are read without the date bound and **named**; objects whose files (`base64` fields) the rules do not keep with an approved `keep` are **left out and named** -- bytes cannot be pseudonymized. `excludedObjects` leaves others out.
3. **Deterministic pseudonymization**: `HMAC-SHA256(salt, "generator|value")`. The same input value produces the same output whatever object carries it, so cross-object joins survive. `RecordTypeId` is replaced by the RecordType **Name**, resolved on the target by **DeveloperName**, never by label. A field the rules name no generator for is cleared, except a feed item's `Type`, which is kept: the platform's own word for what the item is, which the load needs to tell a tracked change from a post. A rule on `FeedItem.Type` still wins.
4. **Non-reidentification control (gate)**: 4 checks -- substitution actually applied (including a value leaking into another field of the same record), fields under the `clear` generator left empty, shapes preserved (`registrationSIV`, `phoneE164`, `email`, `postalCodeGeneralize`), and zero residual source ID (18-character Salesforce checksum). **One FAIL and nothing is written or versioned.**
5. **Manifest**: semver version, `status: frozen`, source (org + decision date), salt fingerprint (SHA-256, 12 hex -- never the salt), rules version, volumetry (ceiling + measured, counting what the dataset holds), control results, and **coverage**: objects reached, whether discovery stopped at its cap, objects read without the date bound, objects left out for their files, and the records held that cannot be loaded as they are for an object `excludedObjects` leaves out.

### Load Flow (Replayable)

Entry guards refuse with an actionable message, and never issue DML against the source:

- **sandbox only** (Production Guard tier check);
- configured **protected environments** are refused, as is the source org recorded in the manifest;
- **mocked callouts**: detected through custom metadata (`mockDetection`); when it is not configured the guard is explicitly disabled and reported in the tab;
- an **empty dataset** is refused.

Then: schema alignment (missing fields dropped **and listed**, restricted picklists including per-RecordType assignment gaps via the UI API), **technical placeholders** for lookups that became required on the target (never a silent exclusion), a two-pass insert for cycle FKs, each **person account's contact** linked to the one the platform wrote with the account, or sent as a contact of its own where the target wrote none (see **Person accounts** below), and persistence of the `referenceId -> Id` mapping in the sas -- with which of its records the load **created** (inserted, or a placeholder) rather than linked or reused, and when it ran -- by this machine's clock, and by the target's own dates of the records it created, read back as it ends -- which is what removing it takes. A load without **Reload** leaves the loads before it in the org, and the mapping keeps them, each with what it created and its dates, for a later reload to purge or a removal to take. A load that **stops part way** keeps its mapping too -- cancelled, or failed once it had created or purged records (Production Guard refusing a later batch, a placeholder or a write the target refused, a pass after the inserts that threw) -- with what it created so far and its dates: a removal takes it back without loading again -- from the **Last load** card, or with `remove` on the command line -- and the next reload purges it. The error, cancelled or failed alike, says what the load left, and names the removal beside the reload. One cancelled, or failed, before it created or purged a record keeps no mapping of its own: the mapping stays as the loads before it left it. The audit trail records a load cancelled before it wrote anything, and before the target refused anything, as **stopped**, under `LOAD_CANCELLED`. An object the cancel stops while it is written -- before its rows go out, between two calls, or between the two writes of the emails, some of which wait for their task -- ends **stopped** on the **Load** tab, unless the target refused a row of it, and its line says what it inserted, what failed and how many rows the cancel kept from the target, which the audit trail counts as not sent. A write of its own that throws -- Production Guard refusing it, a call that fails -- ends an object, a reload's purge, the placeholders, the cycle pass or the statuses **failed** instead, its line saying what it did, what the failure kept from the target, and why; the audit trail counts the rows of an object the failure kept back as not sent too. A purge the target refused records of ends failed as well, saying how many. The **Load** tab counts the links the cycle pass left unresolved beside the ones it made, and the person accounts' contacts the load linked, sent as contacts of their own, or placed neither way, and names the links it could not make per object and lookup: each lookup left empty on a record the load wrote, and why -- the record it points at was not loaded, or the target refused the update, in its words -- and apart, a link that went with a record the load did not write.

Before the first write -- a reload's purge comes after it -- every required field the dataset leaves empty is checked against the configuration, and **all** the gaps are listed in one refusal -- nothing is written, and nothing purged, until each has a placeholder or a default. Only the records the load writes are checked, and only they receive a default: a record it only links -- the standard price book, a selling model found by its key, a record a reload reuses -- is never sent. Objects with no record are left alone. An object the target lacks, or takes no insert of (not createable for the running user, like an error log the platform keeps itself), is **not sent**: the report names it among the objects not loaded, counts the records of it the load links as reused and the ones it had to write as failed -- in the audit trail too -- and the load ends with errors when it had records of it to write. A feed item whose type the dataset does not carry -- a dataset extracted before 1.38.2, whose rules cleared it -- is **left out** with what cannot go in without it, since a tracked change cannot be told from a post; the report says to extract the dataset again. A value the rules cleared is **left out** of the insert, so the target applies its own default (the running user as owner). Objects are inserted parents first; a cycle is kept together and, inside it, whatever a required lookup points at goes first. Records the platform owns are matched, not inserted: the **standard price book** (standard prices are written before custom ones), and the **direct AccountContactRelation** Salesforce creates with each contact. So are the records the target keeps one of: a **selling model** it already holds, found by its type, pricing term and unit -- which the rules must keep, since a cleared key matches nothing -- and the **selling model option** joining a product and a model the load matched. The standard price book, the selling models and their options are looked up on a **Catalog** line of the **Load** tab, after what a reload reuses by its identity keys and before the alignment: it says whether the standard book was found, how many records of each object it linked, and why the target could not be asked about one; a read that throws ends it failed, with why, before anything is written. Options are written before the prices that need them. A record type the running user cannot use is dropped and listed, and the user's default applies. An **Order or Contract** whose status is past Draft is created at a Draft status of the target (read from `OrderStatus` / `ContractStatus`), its children follow, and its status is applied last -- the report lists what the target refused. The **Load** tab's report says why records failed: per object, each status code and message, with how many records.

A record the target **refuses on fields it names** -- a validation rule of its own (`FIELD_CUSTOM_VALIDATION_EXCEPTION`), or a restricted picklist refusing its value (`INVALID_OR_NULL_FOR_RESTRICTED_PICKLIST`) -- is written again once, as Forge writes one: without those fields, or, for a picklist whose declared rule replaces a rejected value (`picklistRules` / `defaultPicklistRule`), with that value; a rule that would send again the very value refused, or an empty one, leaves the field out, and a multi-select picklist goes without all its values, since the refusal names the field and not which of them. The alignment cannot catch every such value before the write: a record type never given values of a restricted picklist takes none of them, while the UI API answers the field's whole value set for it. Taken the second time, the record is inserted, mapped and created by the load like any other, so its children are written against it; the object's line, the **Load** tab and the command line say which field it went without -- or which value it got -- what refused it, in the target's words, and how many records, and the audit trail counts them apart among the records created (`writtenWithoutFields`). Refused again, it fails with both refusals; a refusal that holds any other error, or names no field the record gives a value to, is a failure as before. The second write goes past Production Guard as the first did; a cancel that came during the first write keeps the refused records from it, and they stay the failures the target made them. The counting contract expects such a record as any the load inserted, and names it under the field it went without.

**Reload without refresh**: per-object identity keys (ExternalId, name, composite pairs) let the load reuse existing records, and the standard price book, selling models and options it matched are matched again before anything is purged, and kept. What earlier loads **created** -- the last one, and those before it that no reload purged -- and this one does not find again is purged **children before parents**, and undeletable objects are **deactivated** through a configured field. A record they only **linked** is never purged: it was in the target before them, or is the platform's, and a reload whose rules or dataset changed would otherwise delete it the moment it no longer matches. A record an earlier load created that the reload finds again stays **created**, so its removal and the next reload still take it. What the target refuses to purge stays named for the next reload. A mapping written before loads kept what they created cannot tell its created records from its linked ones: the reload purges only records of objects no load links, never one of an object with identity keys, a selling model or option, or the standard price book, and the report counts what it left in place. Activated orders are returned to a draft status first, and one the purge leaves in the org -- its delete refused, or not reached when a cancel or a failure stops the reload -- gets its status back: what that leaves on it is kept with the load that created it, so that load's removal does not read it as changed since, and one whose status cannot be given back is listed among the purge's failures. Activated contracts are deleted as they are: the target deletes one so, and a sandbox would not set one back to Draft. The records of a load the target did not date are judged as its removal judges them, by this machine's clock at its end read on the target's; from a target that does not tell its clock, what the purge leaves on them is not kept, and that removal reads them as changed. Custom prices are deleted before standard ones, direct relations go with their contact, and a record already deleted by a cascade counts as purged. So does one the target refused while its parent stood and then deleted with it -- a contract item price under an activated contract the purge deleted next: once its deletes are through, the purge reads back what the target refused, and what is gone is purged, not failed. Stopped by a cancel or a failure, it does not read them back: its line counts them failed, and the next reload or a removal finds them gone. Native duplicate rejections on the target are an explicit degraded mode: those records are **skipped and listed** (recognised by their status code, whatever the org's language). The **Load** tab's report says what the purge deleted and deactivated, per object, what it left in place, and why the target refused the rest: each status code and message, with how many records, as for the load's own failures.

**Person accounts**: the platform writes a person account's contact itself as it takes the account, and links the two by the account's `PersonContactId`, which no insert or update sets. The load never sends such a contact -- one the sidecar (`personcontact-sidecar.json`) names, or any contact the dataset flags `IsPersonAccount` -- beside the platform's. The contacts go after the accounts, and at their turn the load reads back the contact the platform wrote with each account it has in the target -- inserted, or found by a reload's identity keys -- and maps the dataset's contact onto it, so that what points at it (a case's contact, a contact role, a custom lookup) is written against that one. The contact object's line, and a **Person contacts** line, say how many it linked, sent as contacts of their own, or placed neither way; those it linked are counted as linked records, which the counting contract expects and the verification counts in the target. One whose account the target holds as a business account -- its record type there is no person account's (the record type issue says why, when the load dropped it), or the target has no person accounts at all, which its describe says before anything is asked -- goes as a contact of that account, as any contact does: counted as inserted, created by the load, so that a removal or a reload's purge deletes it as any other, and listed as sent as a contact of its own, with why, link by link. One whose account was not loaded, or is not in the dataset, is not sent, and is counted as failed with why; what pointed at it is left empty, and the cycle pass says so. Neither a reload's purge nor a removal sends the delete of a contact the load linked: the platform deletes it with its account. The person fields the account carries (`FirstName`, `LastName`, `PersonEmail`, `PersonMobilePhone`, the contact's custom fields as `__pc`) go in with the account, as the rules give them for `Account`: a rule written for a field of `Contact` does not reach the person account's, and the contact's own row is never sent.

**Pilot**: a single root graph (~2 min) before committing to the full load, with the catalog its prices need though none of its records names it: the standard prices, the standard price book and the selling model options.

### Post-Load Verification

Read-only, chained to the load (or replayed with **Re-verify**): per-object counts against the **counting contract** and orphans on mandatory lookups, both among **the records this load wrote** (a sandbox is seldom empty), presence by key (ExternalId), and each account the target holds as a person account holding the contact the load linked. A business account, which took the dataset's contact as one of its own, is not judged there -- the counts are -- and a target whose describe has no person accounts is not asked about them. A record the load wrote again without a field the target refused is counted as any it inserted, and its empty lookup is no orphan, nor its empty key a missing one: the counting contract names it under that field. For robustness it re-measures until **two identical readings** before returning a verdict (`passed` / `failed` / `unstable`). The verdict is recorded in the manifest under `controls.dryRunLoad`. What the mapping names is counted against the counting contract of the load that wrote it: a load that stopped part way -- cancelled, or failed once it had written -- keeps its mapping and writes no contract, and **Re-verify** refuses it, saying why, rather than judging its records by the contract of the load before. Reload the dataset -- the reload purges or finds again what the stopped load wrote -- or remove the stopped load before loading the dataset again, then verify: loaded again without **Reload**, the dataset goes in beside what the stopped load wrote. It refuses first -- before anything the sas's mapping says -- when `sasDir` names another sas than the one the last load wrote to, or when that sas no longer holds the counting contract the load wrote (moved, emptied or replaced since), and says so.

### Removing a Load

The **Load** tab's **Last load** card names the load whose mapping the sas holds -- run from the panel or from the command line -- and **Remove the records this load created** takes it back without loading again. What goes is what the mapping says the load **created**: every record it inserted, and each technical placeholder -- after a reload, with the records earlier loads created that it found again and kept, as the confirmation says. What it linked to or reused stays: the standard price book, a selling model or option the target already held, the direct AccountContactRelation Salesforce made with a contact the load did not create, a record a reload found by its identity keys that no load created. The direct relation of a contact the load created goes with the contact: "To remove a direct relationship between a contact and an account, change the contact's primary account or delete the contact" (Salesforce Help, "Considerations for Relating a Contact to Multiple Accounts"). The contact the platform wrote with a person account the load created is neither taken nor kept: the platform deletes it with its account, and refuses a person contact deleted on its own, so the confirmation counts it nowhere. A contact the load sent as one of its own is one it created, and goes as any other. Once the last load's records all went, or when it created none, the card offers the load before it whose records are still in the org, as an **Earlier load**: loads are taken back one at a time, the last first, since a load's records can depend only on those of the loads before it.

The removal is Forge's, the one a Forge run's history entry offers. The confirmation names the org, which you type, and the records per object it takes; Production Guard judges the delete, and refuses a production org. Children go before their parents, an activated order is set back to Draft first (and given its status back if it stays), an activated contract is deleted as it is, with its item prices, and custom prices go before standard ones. The load is dated by the target's own dates of what it created, read back as it ended, as a Forge run is; a load whose dates could not all be read back is dated by this machine's clock instead. A record that records staying in the org depend on is kept -- through a lookup the org will not let them lose too: a price an order line that stays still uses, a standard price a custom one that stays needs, a selling model option an active price that stays is sold under, the products and actions of an activated order the removal keeps, and the item prices of an activated contract that stays -- and so is one changed since the load, or one that records added since depend on -- unless you tick **Also remove the records changed since the load**. It runs in **Live Operations**, where Cancel stops it before its next call to the org; the audit trail records it (`cleanup_delete`, module `frozen`, counts only); the result says per object what was deleted, what was already gone, what was kept and why, and what the org refused, in its words, and names the files attached to the records it deleted that stay in the org -- a confirmation the org generated for an order, say: the removal takes only what the load created.

The mapping then forgets the records that went and is **marked**, whether the removal ended or was cancelled, with when, how many every removal deleted or found gone, and what the last one left. A removal that left none of the load's records in the org is not offered again. One that left some -- kept for a change since or for records that stay, refused by the org, or not reached before you cancelled it -- leaves the card offering **Remove what is left of this load's records**, with or without the records changed since: the confirmation names only the records left, and which removal left them; the result and the audit entry say it picked up where that removal left off; and the mark then counts what every removal took, a cancelled one's included. One that took nothing is offered again too. Each reads what an earlier one left on the records as its own doing, not as changes. A sandbox refreshed since the load is refused -- its records went with the refresh -- and so is a mapping written before loads kept what they created: a **reload** purges its records, except those of objects a load may have linked. **Re-verify** refuses a load whose records were removed: load the dataset again first. It refuses one a removal took part of too, saying how many records it left: remove what is left, or reload the dataset, which purges or finds them again.

From the command line, the same removal, through the panel's own handler: it prints the same plan, asks you to type the alias (unless `--yes`), and removes; `--include-changed` takes what changed since the load too. Run again after a removal that left records in the org, it prints what that removal left, asks, and removes those; once none is left, it says so and deletes nothing.

```bash
pnpm exec tsx packages/extension/cli/sandforge-frozen.ts remove --config frozen.json --target MY-DEV
```

### Configuration

Per-project configuration persisted by the extension (main keys):

| Key                                       | Role                                                                                              |
| ----------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `rootObject`                              | Root object API name                                                                              |
| `axes`                                    | Coverage axes (`name`, `label`, `filterField`, `valuesSoql` aggregate with the `axisValue` alias) |
| `edgeCases`                               | Edge cases (`whereFragment`, marker in the data)                                                  |
| `budgetMaxRecords`                        | Volumetry ceiling (default 2,500)                                                                 |
| `expectedObjects`                         | Objects a root's own records must include for it to count as healthy                              |
| `maxNodes`                                | Objects discovery may reach (10–500, default 50); past it the dataset is marked as cut short      |
| `excludedObjects`                         | Objects the dataset leaves out, whether the graph reaches them or the cap left them past it       |
| `excludedFields`                          | Per-object fields excluded from the SELECT clause                                                 |
| `sasDir` / `datasetDir` / `rulesFilePath` | Paths (defaults: `~/.sandforge-sas`, `<sas>/dataset`, `<sas>/rules.json`)                         |
| `datasetVersion`                          | Semver stamped on the next frozen dataset                                                         |
| `protectedOrgIds`                         | Protected environments (refused at load time)                                                     |
| `identityKeys`                            | Per-object identity keys (reuse on reload)                                                        |
| `undeletableObjects`                      | Object -> deactivation field (leftovers deactivated, not deleted)                                 |
| `requiredLookupPlaceholders`              | `Object.field` placeholders (required lookup missing from the dataset)                            |
| `requiredFieldDefaults`                   | Declared default values, keyed `Object.field`                                                     |
| `picklistRules` / `defaultPicklistRule`   | Declared removal or replacement of rejected values                                                |
| `duplicateErrorPatterns`                  | Markers of the target's native duplicate-rejection errors                                         |
| `mockDetection`                           | Custom metadata + `IsMocked` boolean field                                                        |
| `mandatoryLookups` / `presenceKeys`       | Mandatory lookups and presence keys used by the verification                                      |

The **Extract** tab edits `rootObject`, the budget, the axes and the edge cases through a form; everything else goes through the **Advanced configuration** JSON area.

### Security and the Quarantine Directory (Sas)

- The **sas** (`~/.sandforge-sas` by default) is **outside the repository by construction**: `SasPathGuard` refuses any output path located inside the repo. The selection (source IDs), `rt-map.json`, the `{{TOKEN}}` values (`tokens.json`) and the `referenceId -> Id` mapping never leave it.
- The **salt** comes from `SANDFORGE_FROZEN_SALT` and nowhere else; only its **fingerprint** (12 hex) is recorded. Never regenerate a second salt silently -- determinism across dataset versions would be lost.
- The bridge **redacts**: the selection sent to the UI carries no source ID, and the details of `clear-empty` violations (which may embed a residual value) are redacted on the extension side.
- All DML goes through the existing **Production Guard** (tier check; each decision is recorded with the load in the audit trail, unless `sandforge.safety.auditLogging` is off).

## Limits

- Selection measures volumetry by running a **real extraction pass** on the retained roots (bounded by the budget). It is an interactive operation, not a batch job.
- Without `mockDetection` configured, the "mocked callouts" guard is disabled (shown as a warning). Deploy it before loading into an org that makes callouts.
- Reload without refresh needs identity keys that are usable on the target (ExternalId recommended).
- A removal takes what the mapping names, one load at a time, the last first. A load into another org, or into the same sandbox after a refresh, replaces the mapping: the loads before it are no longer named.
- Of a mapping written before loads kept what they created, a reload never purges a record of an object with identity keys in the configuration, a selling model or option, or the standard price book. A load run with identity keys the configuration has dropped since could have linked records of other objects: nothing records it, and the reload purges them.
- Picklist values outside the RecordType assignment require the **UI API** on the target (available on recent orgs). It does not see a record type never given values of a field, for which it answers the field's whole value set: the target refuses such a value at insert, and the record is written again on the declared rule.
- A record holding two values its record type refuses is refused for the first alone -- run against a real target, the refusal named one field of the two -- and, written again without it, refused for the second: it fails.
- The removal's confirmation counts among the linked records it keeps the direct relation of a contact the load created, and the task the platform wrote with an email the load created, though the platform deletes each with its record.
