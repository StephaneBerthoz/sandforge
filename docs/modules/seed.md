# Seed

Fill a Salesforce sandbox, scratch org or Developer Edition with realistic test data: from a built-in template in one confirmation, with no AI key, or generated with Faker profiles or AI, imported from a CSV file, or copied from another org. Seed handles object dependencies automatically.

Seed opens on its template gallery -- **Quick Seed**, a template seeded from one confirmation -- with three other ways to seed listed under it:

- **Generate data**: the 4-step Seed Wizard, for the objects, record counts and field rules you choose, generated with Faker profiles, AI, or an industry persona
- **CSV Upload**: Import data from a CSV file with auto column mapping, validation, and a 4-step wizard
- **Clone from Org**: Clone records from a source org into a target org with relationship-ordered insert and ID mapping

## Quick Start

1. Navigate to **Seed** from the sidebar
2. Pick a template from the gallery -- **CRM Starter**, marked _Start here_ and listed first, fits a Developer Edition's 5 MB -- check its record counts and the org, and press **Start Seeding**; or pick one of the other ways under it: **Generate data**, **CSV Upload**, or **Clone from Org**
3. Follow the guided wizard of the way you chose
4. View results with per-object record counts, error details, and export options

## Seed Modes

### Generate data (Seed Wizard)

The 4-step wizard, for the objects, counts and rules you choose. Above its first step, an industry persona can fill the field rules (optional): its patterns shape the rules of the objects described, and of those described after.

- **Step 1 -- Select:** Choose an org, pick objects from the schema list, and set record volumes. The objects an empty org is seeded with first -- Account, Contact, Opportunity, Lead, Case, Campaign, Task, Event, Product2 -- are pinned at the top, the others under them in the order the org gives, and a search finds an object by its API name or label. Ticking a standard object whose parent the run does not seed offers that parent in one click: a contact's or an opportunity's account, a case's account and contact, a price book entry's product.
- **Step 2 -- Configure:** Customize field generation rules per object. Each described field opens on a rule the run accepts: a Faker method chosen from the field's type, name and object (an email address on an email field, a company name on an account's Name, a street, city, state, postal code or country on the parts of an address, a job title on a person's title, a date to come on a close date and one 20 to 65 years back on a birth date -- see [Generated values](#generated-values)), and no Faker rule at all on a checkbox or another type no generator fits. A text field nothing in its name reads -- a site, an account number, a description -- opens blank unless the org requires it, which gets a sentence: set it here to fill it. A field of one of those other types -- a multi-select picklist, a time field -- opens with no value, so a required one still has to be filled in before the run, or its records fail on it. A number is drawn within the digits the org says the field holds, and a percentage up to 100; a latitude or longitude opens with no value, since one drawn at random would point nowhere near the address generated beside it. A Faker rule takes its method from the list of methods SandForge generates; a template or persona that names any other method is refused before the first record is written, with the object and field it sits on. A generated or AI-written value longer than the field is cut to the field's length, at a word boundary when there is one. A lookup field receives the ids of records its target object created earlier in the same run, so that object has to be part of the run; an optional lookup to an object outside the run, such as an owner, is left out of the run and keeps whatever the org puts there, and so is an optional lookup to the object itself, such as an account's parent, which the insert writing the object cannot fill; and so is an optional lookup that would make two objects of the run wait on each other, such as a custom lookup from an account to a contact while the contacts point at their accounts -- a standard lookup is kept before a custom one, and otherwise the one pointing at the object picked first; a required one is still sent, so the run is refused before it writes anything and names the object the lookup points at. Under **Advanced Settings**, a relation fills one lookup of an object from a parent object's records -- the ones this run creates, or records already in the org, picked by a SOQL filter and bounded by a number of parents you set -- and gives each parent exactly N children, a random number between two bounds, or an average spread evenly (0.5 gives a child to every other parent). The relation decides how many records its child object gets, in place of the count set on the first step, and says under its row how many it plans; an object takes its count from one relation at most. A relation the run cannot honour -- parents written after the child, a spread that makes no child -- keeps the wizard on this step. The run writes the parents first and gives each child the id its parent got; a child whose parents could not be written or found is not written at all. **Record types**, above the fields, lists the record types the target offers you on each object that has more than one, or a person account's, which is marked: none ticked, the records take your default; several take turns at random. Accounts given a person account's type are written as person accounts -- a first and last name, the person's email and phones, and no `Name`, which the org builds from the two names -- and accounts given none, or a business type, as business accounts, without the fields only a person account holds; the account's fields below list what the run writes for the kind chosen -- no `Name` for a person account, its last name required; no first or last name, `Person…` or `__pc` field for a business account, its `Name` required. A person type ticked with a business one keeps the wizard where it is, as the command line refuses it.
- **Step 3 -- Execute:** Progress is reported as each object starts, with the records written so far and a live progress bar. With fewer than five objects the wizard comes here straight from Step 1: the objects' fields are read on this step, with the same default rules Step 2 would show, and the run waits until every object is read. A banner says the run uses those default rules, with the persona's patterns when one was picked, and links back to Step 2; the relations and the record types are set on this step.
- **Step 4 -- Results:** Summary badge (success/partial/failure, or cancelled for a run stopped with Cancel -- the records it created stay in the org and are counted), records created vs. failed, per-object breakdown. An object's refused records are grouped by what refused them -- the status code and the fields it named, with the number of records and the first one's message as its example -- the three largest groups open; each code the error catalogue knows says what it means and what to do -- in a seed's own words for those a seed meets most (a required field, a validation rule, a restricted picklist, a duplicate value or duplicate rule, storage full, a missing standard price, a failed Flow) -- and one it does not know links a search of Salesforce Help for it; when the run posted the first 1,000 refusals of an object only, the groups say so. **Open a created Account in** _org_ opens in the browser the first account the run created -- the first record it created when it created no account -- in the org it wrote to: the page names the run and the record, and the extension takes the org and the object from what the run kept. Save as template, export CSV, or seed again. **What this run created** takes the run back, with the removal the command line runs: the confirmation lists the records per object and asks for the org by name, the last object written goes first, into the recycle bin, a record changed since the run stays unless included, Production Guard judges the delete -- none is offered on a production org, a Developer Edition is not one -- and the audit trail records it. A removal under way stops from the card or Live Operations between two calls to the org, or two delete jobs, and what it left is offered again. **Sweep first** (off unless ticked) also takes back, before the run's records go, what the target's automation created during the run as its user -- a task a flow opened on each seeded contact -- listed in the confirmation before the org is typed, Forge's sweep in a Forge removal's words; the window is read back from the run's own records, a second before the first insert to a minute after the last. What a run created is kept on disk in the extension's storage until it is removed -- of the runs removed, the 20 latest; past the bound on the bytes the runs take, a run still in its org is dropped only with a warning naming its org, its date and its records -- written as each call to the org answers -- each REST call of an object a duplicate rule sends through REST, each Bulk API job -- and each call is noted before it goes, a Bulk API job with its id once the org has opened it, so a run can still be taken back after the window was reloaded, and one whose window closed before it ended too: **Earlier seeds**, under the other ways to seed, lists them newest first, with the panel's CSV imports and clones, each named by its way, a run that did not end marked partial with what the org had confirmed by then, each saying whether it can still be removed, and opens one onto its removal. A Bulk API job still running when the window closed runs on to its end in the org: the next time the list is shown, the job is read back by its id, and the records it created are listed and removed with the run; a job the org still processes is read again later. The records of a REST call under way when the window closed, 200 at most, may be in the org without being listed. A seed still writing in this window is listed as running, with a link to Live Operations, and is not offered a removal until it ends; a removal asked for meanwhile is refused (`RUNNING`), as Sync refuses one. A seed another window is writing is listed as running there, never as partial, and is refused the same way; its Bulk API job is not read back while that window runs. Quick Seed's results offer the same.

**Quick Seed** lets you skip configuration entirely: **Use This** on a template opens one confirmation -- its record counts, which you can change, the org, and the locale its names and addresses are drawn in (the org's own unless you choose another) -- and **Start Seeding** runs it. The org is preselected, as long as it is still connected: the one the Home recommendation named; else the one chosen for an earlier template; else the org selected in the panel, unless it is a production org (a Developer Edition is not one). Nothing is written until you press Start. A run that has reported progress can be stopped with **Cancel run**, as the wizard's can; what it wrote stays in the org, and its results say it was cancelled.

A page waits on the run it started -- a seed, a CSV import, a clone -- for up to 12 hours, as Sync's does: the run goes on in the extension and answers once it ends. Should the page stop waiting, it says the run may still be writing and that Monitor's Live Operations shows where it is, rather than offering to try again, which would write its records twice.

- A Developer Edition has 5 MB of data storage. Before the guard is asked and before the first record is written, a seed reads what the org has left (`/limits`) and is refused when its records take more -- 2 KB a record, 4 KB a person account, 8 KB a campaign, as Salesforce counts them -- with both figures, and nothing is written. An org that does not say what it has left is seeded, and the SandForge log says so.
- Before Start, the confirmation -- and the wizard's Execute step -- says what the org runs as these records are created: its record-triggered flows, Apex triggers, processes and workflow rules on the objects the seed writes, which of them send emails or other messages, create records or run on after the save, and the custom permissions their start conditions name, with whether you hold each and the permission set that holds it. A read that fails is said, and holds nothing back. The emails the records make the org send are counted from the counts as you set them -- each email action of what fires on insert, once a record -- against what the org has left today of its single emails and its workflow emails (`/limits`); on an org held to the 15 single emails a day of a Developer Edition, email alerts count against the single emails too, as a Developer Edition counted them. Past what is left, Start waits and the confirmation says the seed would be refused, with both figures and the ways out -- lower the counts, set the object to 0, turn the sender off, or give yourself the permission set whose bypass keeps it quiet -- and a run sent all the same is refused before the guard is asked and before anything is written (`SEED_EMAILS_EXCEEDED`). An estimate that cannot be made -- the org's limits or automation unread -- is said, and refuses nothing.
- Prices go to the org's standard price book, which every org has, active or not, and none can create: each product gets one standard price, and the opportunities and their line items point at that book. A new org's book is inactive, and the org takes the prices and line items as it is.
- A case is written with its contact, and the org files it under that contact's account. A random pick keeps to the values the org's picklist has, or takes the org's own when it names none of them.
- An object the org does not have -- Knowledge articles where Knowledge is off -- or one you may not create -- campaigns without the Marketing User box on your user -- is skipped with that reason, and so is what hangs on it; the rest is written.
- A field the org requires and the template names no rule for -- a required text field of the org's own on Account -- is filled as Step 2 would fill it, and the object's results name it; a required lookup, or a type no generator fits, is left for the org to refuse.
- In the confirmation's counts, an object set to 0 is left out, with what cannot be written without it (line items without prices), and the records a relation places under another follow it: three contacts per account stay three per account.

### CSV Upload

Import data from a CSV file with a 4-step wizard:

- **Step 1 -- Upload:** Select your target org and object, then drag-and-drop a CSV file (or use the file picker). A preview of the first 10 rows is shown immediately. One import takes 50,000 rows at most: a larger file is refused as it is read, with its row count, to be split into files of 50,000 rows or fewer.
- **Step 2 -- Map Columns:** CSV headers are auto-matched to Salesforce fields using case-insensitive, underscore-tolerant matching. Override any mapping by typing a field's label or API name in the column's box, or picking it from the list of the object's fields; empty the box to leave the column out. Status indicators show matched, unmapped, and type-incompatible columns. Only the mapped columns are sent, 500 at most: past that, the step says how many are mapped and waits until enough are left unmapped.
- **Step 3 -- Validate:** Records are validated against Salesforce field metadata: type mismatches, missing required fields, length violations, invalid picklist values, and duplicate external IDs. Errors are grouped by type in accordion sections. Proceed if validation passes or if the error rate is below 10%.
- **Step 4 -- Execute:** Records are inserted via the Seed pipeline. While the import runs, **Cancel run** stops it before its next batch, as Live Operations' Cancel does; the way back to the gallery is hidden until it ends, since leaving would stop nothing. View per-object results on completion: an import you stopped reads **Cancelled**, with the records it imported before the stop, which stay in the org until you remove them. **What this run created**, under the results, takes back what the import created -- the rows it inserted, or upserted where the org held no record of their external id -- with a seed's removal; a record an upsert wrote over was the org's before, and stays. The audit trail records an import cancelled before its first row as **stopped**, under `IMPORT_CANCELLED`, and one cancelled once a row went in as **cancelled**.

**Supported formats:** UTF-8 CSV with headers. BOM is stripped automatically. Papaparse handles parsing with `dynamicTyping: false` for predictable type conversion.

What an import creates is kept as a seed's is, as each call to the org answers: it is listed under **Earlier seeds**, named **CSV Upload**, and can be taken back from there after the window was reloaded, or after it closed during the import.

### Clone from Org

Clone records from one Salesforce org to another with a 4-step wizard:

- **Step 1 -- Source Org:** Select the source org (all connected orgs except the current target). A visual indicator shows the source-to-target direction.
- **Step 2 -- Select Objects:** Browse objects from the source org with a searchable list. Check objects to clone and optionally add a SOQL WHERE clause per object to filter records (e.g., `Industry = 'Technology'`). Next asks for the preview, which needs a target as well as a source: the target is the org selected in SandForge, and with none selected Next stays disabled and the step says to pick one on the Organizations page.
- **Step 3 -- Preview:** While the preview is prepared, the step says so, and Back sets it aside. View the insertion order (topological sort of dependencies), the lookups a second pass fills in (see below), record counts per object, and sample records. The order and those lookups are read as the run reads them: from the target org's describe, and only from the lookups the source org's describe has too. A lookup only the target has is never read, so it orders nothing and every record goes in with it empty; one the target requires -- a master-detail, or a lookup made required, deployed to the target alone -- is named above Execute, as the target will refuse every record of its object. A lookup only the source has is listed apart: the target has no field for its values, and the clone leaves them out of every record. An object either org cannot describe stops the preview, which names the object and the org, as it would stop the run before anything is written. A warning appears for clones exceeding 10,000 records. The run goes to the orgs the preview was made for: select another org after it and the preview is set aside, the wizard says why, and Next previews again for the org selected now. The extension refuses a run that names no preview, names one it no longer holds (it keeps the last 50 and forgets them when it restarts), or is not for the orgs of the preview it follows, before reading either org; each refusal says which.
- **Step 4 -- Execute:** Execute, or Next on the preview, runs the clone and shows it running, with **Cancel run**, which stops it before its next object or batch, as Live Operations' Cancel does; the wizard, and the page's way back to the gallery, stay on the run until it ends. Records are fetched from the source org (cursor-based pagination, 2000/batch), relationships are remapped, and records are inserted in dependency order. A field the target org does not have is left out of every record -- sent, the org would refuse the whole record -- and the results name it under its object. So is an owner, or another lookup at a user or a queue, the target org holds no record of -- asked of the target once per id, as Forge's runs of whole tables ask -- which the platform fills, the owner with the user the clone writes as, and the results count the records that went without it under their object: between two orgs that do not share their users, such as a Developer Edition and a sandbox, the target refused every record. Per-object progress is shown during execution. Results open on a badge saying how the clone ended -- complete, partially complete or failed -- and include an ID mapping table (source ID to target ID) with CSV export. A clone stopped with Cancel reads Cancelled instead: the results say how many records it had created, which stay in the target org until you remove them, list only the objects it reached, and, when the cancel came before its second pass, say that the lookups it owed stay empty. **What this run created**, on the results, takes back what the clone created in the target, the last object written first, with a seed's removal; a record it linked to, which the target held, stays, and the second pass's writes to the clone's own records are read as the clone's, not as changes since. A clone that fails, including one the production guard blocks or whose confirmation you decline, shows its error as soon as the extension reports it; a request SandForge refuses before reading either org, such as a filter that does more than select records, is said in words, and the SandForge output channel names the part it refused. A clone that ends without results goes back to its preview, to run again; dismissing its error keeps the objects picked and the preview.

**Emails and phone numbers.** A clone copies real records, and the target org's flows, triggers and email alerts act on them as they go in. Unless **Keep emails and phone numbers as they are** is ticked on the preview, every email address is written under `.invalid` and every phone number as a fictional one, as Forge, Sync and Autopilot write them, so the target's automation reaches no one; the results say how many values were neutralized, field by field, or that they were kept. The field an upsert matches on is kept as read. Before the first write, the clone reads what the target runs as the records are created, as a template seed does, and is refused past the daily emails the target has left, with the figures and the ways out: narrow the filters, leave the object out, turn off what sends, or hold the permission that keeps it quiet.

What a clone creates in the target is kept as a seed's is, as each call to the org answers: it is listed under **Earlier seeds**, named **Clone from Org**, and can be taken back from there after the window was reloaded, or after it closed during the clone. To copy a record and what hangs on it, [Forge](../forge-quickstart.md) follows its relationships for you; for whole objects run again and again, [Sync](sync.md) keeps a configuration.

**Self-referential objects and cycles** (e.g., Account.ParentId, or an account's key contact while each contact points at its account) are written in two passes, as Forge writes them: the records go in with those lookups empty, and a second pass fills them in once the record they point at is in the target. An account's parent the clone does not copy is sent as it was read, like any lookup at a record outside the clone. The results say how many lookups the second pass filled in, and why it could not fill the others -- a cycle's lookup at a record that was never cloned stays empty. Only a cycle of lookups that must be set when the record is created -- required, or not updatable -- stops the clone, before anything is written, with the lookups named.

## Features

### Forge (Graph-Based Discovery)

The Forge page provides a richer workflow with four input modes:

- **Record** -- Paste a Record ID or Salesforce URL, preview the record live, then discover its full dependency graph
- **SOQL** -- Write a query to pick the root object. Its WHERE clause filters the
  object after FROM, and discovery counts the rows it matches. Only that object is
  filtered: related objects in the graph are not narrowed to the matching rows, and
  each one is read from its whole table. Every object is capped at 200 records or
  fewer per run. ORDER BY, LIMIT and the other clauses after WHERE are not applied.
  A WHERE clause longer than 512 characters, containing `--`, `/*` or `*/` (even
  inside a quoted value), or ending with a semicolon cannot be sent: the page says
  so under the query and Discover stays disabled until it is rewritten.
- **Template** -- Select a saved template for repeatable operations. A template
  saved from a SOQL query runs as that query, on Discover and on Reuse last graph
  alike: its WHERE clause filters the object after FROM, every object is capped at
  200 records or fewer, and a clause that cannot be sent keeps Discover disabled and
  Reuse last graph hidden.
- **AI** -- Describe the records to clone, and the model drafts the SOQL query
  discovery starts from -- NL2SOQL's draft, from the same context, so it needs AI
  on and an Anthropic key. The draft is checked against the source org, its
  object, fields and relationships, and stays editable; Discover runs it once the
  query as it reads has passed the check, as the SOQL run it is. A run from this
  tab is kept in the history as that SOQL run; one stored as an AI run by an
  older release reopens on **Record**.

After input, the Discovery phase renders an interactive dependency graph in a split view. Click any node to inspect fields, toggle inclusion, and configure anonymization per field.

**Recent runs**, under the input form, lists the last runs: each refills the form, and a run that created records — finished, or stopped part way by a failure or a cancel — can remove them from the org it wrote to, children before their parents, keeping the records it linked to and, unless you ask, the ones changed or added to since the run — see [Forge: remove what a run created](../forge-quickstart.md#remove-what-a-run-created).

### Generated values

- A name field holds a company's name -- an account's Name, an opportunity's -- unless its own name says whose it is (a first, last or middle name, a contact's name kept on another object, a company name) or its object is a person: on Contact, Lead, User and Individual, and in a person account's own fields, it holds a person's name. A user's Username is the exception: it gets a username, an email address in form on a reserved domain, carrying a token drawn for the run, since a username is unique across every Salesforce org and the org refuses a user whose Username is a person's name.
- Company names are made up, and read as companies of the locale's country: none is a real company's. A run gives no two records the same company: past the locale's 360, the same companies come back as regional branches, a region of the country beside the root ("Brantwell Pacific Logistics", "Groupe Vercourt Ouest"), and are numbered only once all six regions are used.
- People are drawn from more than 200 first names and 200 last names per locale, the first and the last name apart, and a record's email address is written on its own name. Each run draws anew: a second run writes other people, other companies and other numbers. From the command line, the seed the run prints draws the same again.
- A record's street, city, state, postal code and country come from one address of the locale, the street written the way the country writes it.
- Dates are drawn around today: a close date in the weeks to come -- in the weeks past for a closed stage --, a past date within the year, a birth date 20 to 65 years back, a meeting on a working hour of the month to come. A case's subject is one a customer would write, and its comments what an agent writes.
- The people and places are drawn in the org's default locale -- a French org gets French people in French cities -- or in the locale chosen under **Names and addresses** on a template's confirmation or the wizard's Execute step (American English, French, German, Spanish, Japanese or Brazilian Portuguese; the org's own is the default and says so), or the one `--locale` names; a locale SandForge has no names for draws in the nearest it has, or in American English.
- A record the org refuses on a field a validation rule, a restricted picklist or a lookup filter of its own names -- a phone written in another format than the org's rule wants -- is written again without that field, as Forge, Frozen and Sync write it; at most twice, each time without the field the last refusal named, and never without the lookup a relation fills, a reference rule's field or the record type. The object's results say how many records went without which field, and in the rule's words; a record refused again keeps the org's last refusal. An object of more than 10,000 records, streamed to the org in chunks, is not written again.
- Generated email addresses use domains no mailbox can be at: example.com, example.net, example.org, and names under .example and .test. Generated phone numbers come from ranges nobody holds: North America's 555-0100 to 555-0199, the blocks Arcep keeps in France for audiovisual works, Germany's Bundesnetzagentur drama numbers, and, for Spain, Japan and Brazil, which keep none for fiction, blocks their numbering plans leave unassigned. A sandbox whose flows email or text new contacts reaches nobody.
- AI Data Generation is asked for the same, and its answer is checked whatever it says: an email address on any other domain moves to a reserved one (acme.com becomes acme.example), and a phone number outside those ranges is replaced by one inside them, whether it fills a phone field or is written in a text as a number to dial -- in international form, with its area code in brackets, with its leading 0, grouped 3-3-4, or in the national forms of Spain and Brazil (912 345 678, 11 91234-5678). A persona's random picks are held to the same rule: an email address or a phone number among the values it picks from is rewritten the same way.

### From the command line

- `sandforge-seed --target <alias> --object <Api>:<n> ...` fills a sandbox or a Developer Edition org without the editor, with the panel's orchestrator; a production org is refused before anything is read, and `--dry-run` only reads. An object named this way gets a rule for each field the org requires, its `Name`, and its standard email and phone fields, filled as [Generated values](#generated-values) says; an account is written as a business account, without the fields only a person account holds, unless `--record-type` gives it a person account's record type. `--locale` picks the country the names, addresses and phone numbers are drawn for, the org's default locale when it is not given. Before writing, the run prints the data storage its records take against what the target has left, then what the target runs as they are created and the emails they make it send against what it has left today, and refuses a run past either, writing nothing; a dry run says what a real run would meet, and `--json` carries the email figures in its `emails`
- **How it writes** -- through the panel's write path: an object of 200 records or fewer goes through the REST API, `--batch-size` records a call (200 by default); one of more goes in one Bulk API 2.0 job, but through REST when an active duplicate rule of the org watches it, as below; past 10,000 records, one job whose records are gathered 2,000 at a time. A dry run says which of these each object would take. Ctrl-C stops the run before its next call, or aborts the job still open, prints the summary of what it wrote -- `"interrupted": true` with `--json`, which `--remove` takes back -- and exits `130`; a SIGTERM, as a CI job cancelled or timed out sends, stops it the same way and exits `143`. Every run that writes keeps what it creates in a file as it goes, insert by insert, as the panel keeps its runs -- in `seed-runs/` of `SANDFORGE_JOURNAL_DIR` (`~/.sandforge` by default), named as the run begins -- so a run killed before it printed its summary is taken back all the same
- **Record types** -- `--record-type <Object>=<Name>[,<Name>]` gives an object's records the record types named, by API name, several taking turns at random; one the object does not have, or the running user may not use, is refused before anything is written. Without it, the records take the running user's default, and the run names the other record types open to them. On an org with person accounts, accounts given a person account's record type are written as person accounts -- a first and last name, the person's email and phones, drawn as a contact's are, and no `Name`, which the org builds from the two names -- and the run says so; record types mixing the two kinds are refused
- **The same numbers twice** -- every run prints the seed its draws were made with, and `--seed <n>` takes it back: the same command with the same seed gives each parent of a `--between` relation the same number of children and draws the same names, companies and values, so a dry run plans what the run after it writes
- **Removing a run** -- `sandforge-seed --remove <summary.json | run file | run id> --target <alias> [--include-changed] [--sweep | --sweep-list]` takes back the records a run created, from the summary it printed with `--json`, saved to a file, or from its file -- a Bulk API job under way when the run stopped read back by its id first --, with the removal Sync, Forge and Frozen run: the last object written first, into the recycle bin, a record changed since the run kept unless included, what the org refuses counted with its reasons. What it left on the run's records is kept beside the summary for the next one. `--sweep` first deletes what the target's automation created during the run as its user, as a Forge or Frozen removal's sweep does, refused where that user likely worked by hand; `--sweep-list` lists what it would delete and deletes nothing. It removes from a sandbox or a Developer Edition org, and refuses any other. A run made from the panel is taken back from its results (Step 4), or from **Earlier seeds**

### AI

- AI Data Generation creates context-aware realistic values using Anthropic (Claude); additional providers are planned. When AI is off, or a call is refused (missing key, token budget, the model declining to answer), comes back cut off or empty, or returns fewer values than asked, the fields it left empty receive a generated sentence instead and the run continues; the results step names those fields on the object that received them, and the refusal is written to the SandForge log. Because the value is always text, the wizard offers AI generation only on text and long text fields, and a run whose rules name a number, date, checkbox, email or picklist field type for it is refused before the first insert (wizard runs always name the field type; a template that omits it is not checked)
- Personas you create from a description keep only the patterns Seed can generate: a pattern naming an unknown generator or Faker method is dropped, and numeric params written as text are read as numbers

### Dependency Resolution

- Automatic topological sort of parent-child relationships before insert
- Cycle detection with clear error messages
- Lookup fields point at records their target object inserted earlier in the same run, picked at random; a relation places each child under a parent instead -- one this run creates or one already in the org -- with the number of children per parent it sets
- Configurable depth: Direct (1 level), Full (5 levels), or Custom (1 to 10 levels -- the most discovery accepts)
- An insert of more than 200 records goes in one Bulk API 2.0 job -- except into an object an active duplicate rule of the org watches, which goes through the REST API, 200 records a call, with the rule's matches saved: a Bulk API job cannot waive a duplicate rule, and a new org's standard account rule refused most of 500 seeded accounts sent that way --, its rows with every field any of them carries, and each record's id comes back whatever fields it carries and whatever form the platform writes its values back in: the lookups of the objects inserted after it, and a clone's ID mapping table, can name every record it created

### Templates and Export

- **Save as template** on the results step stores the configuration the run just used -- its objects, record counts, field rules and relations -- under the objects and the date. It is added to the gallery, next to the pre-built templates, and never overwrites one already there. A save the host refuses shows its reason next to the button
- **Export CSV** on the results step saves, per object, the records requested, created and failed, with the ids of the records created -- the first 1,000 of an object that created more, and a count of the ones not listed
- Template Engine supports JSON/CSV with variable interpolation

## Tips

- Use **CSV Upload** when you have existing data in spreadsheets or exports from other systems
- Use **Generate data** when you need realistic but synthetic data of objects and rules of your own (no production data exposure)
- Start with Quick Seed on an empty org: a template, one confirmation, no AI key
- To copy real records from another org, use Forge for a record and what hangs on it, Sync for whole objects run again and again, or **Clone from Org** for a few objects once: each run can be removed
- Enable "Anonymize PII" in Forge to automatically mask sensitive fields during cloning
- Keep batch sizes at 200 (the default) unless you hit governor limits, then reduce
