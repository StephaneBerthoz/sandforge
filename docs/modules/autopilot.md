# Autopilot

Copy objects from one Salesforce org into another, whole or fitted to what the target has left, in the order their dependencies set, with the records they reference. It is a copy, not a generator: it needs a source org that holds the records, and it writes what that org holds.

<!-- how-to:start: written by scripts/sync-module-howto.mjs from howTo.autopilot in packages/webview/src/i18n/locales/en.json -->

## How to

1. Pick an org under Source Org and another under Target Org, then click Next.
2. Tick each object to copy, then click Next.
3. On Review plan, check the two orgs, Total records and What the plan copies.
4. Click Copy into, which names the target org, then follow each wave under Live Stats.

**Tip:** SandForge cannot remove what an Autopilot run writes: try it on a scratch org or a sandbox you can refresh.

<!-- how-to:end -->

Before you start, know three things:

- **It copies whole tables, unless you fit the plan.** Each object you select is read and written whole, every record of it, as selected; of the other objects, only the records the selection references are read. A run copies 50,000 records of a selected object at most: past that, its first 50,000 by Id are copied, with the records they reference, and the plan says so beside the count the source holds. **Fit to storage…** on the review keeps part of each object instead: see [Fit to storage](#fit-to-storage).
- **Masking is off by default.** Emails and phone numbers are neutralized unless you untick the box, but names, addresses and every other field go in as the source holds them unless you pick a compliance framework on the review step.
- **A run cannot be removed.** Autopilot keeps no list of the records it created, so no removal takes a run back: try it on an org you can refresh or throw away, such as a scratch org, or tick **Checkpoint first** on the review, whose rewind is then the way back: see [Checkpoint first](#checkpoint-first). To copy objects and be able to remove a run, use [Sync](sync.md); to copy one record and what hangs on it, [Forge](../forge-quickstart.md).

## Quick Start

1. Open **Autopilot** from the launcher's Modules list (it needs two connected orgs)
2. **Connect source and target**: the org the records come from, and the org they go into
3. **Select objects**: the objects of the source to copy. An object the target does not have is listed, marked _Not in the target org_, and cannot be picked
4. **Review plan**: the two orgs, each with its type and instance; the objects and records the plan copies, in waves, what it reads only by id, and the lookups it leaves empty; what the plan comes to against the target's data storage and API requests, with **Fit to storage…**; the personal fields it found, and a **Personal data** tile saying what becomes of them; **Neutralize emails and phone numbers (recommended)**, ticked; **Checkpoint first**, unticked; and, under **Advanced: compliance framework**, the masking to apply
5. **Copy into**, the button that names the target org, then follow the run on the dependency graph and the control panel

## What a run copies

- **The objects you select**, copied whole unless the plan is [fitted](#fit-to-storage): the plan says _Copied whole, as selected_ and names them. One holding more than the 50,000 records a run copies of a selected object, whether or not the plan follows its lookups, is named apart: the plan says how many of its records it copies, the first by Id, of how many the source holds, and copies the records those reference.
- **The records they reference**: of any other object, only the records the selected ones point at, read by id -- the accounts of the contacts you copy, say. The plan lists these objects apart from the ones copied whole.
- **What it leaves empty**: a lookup the plan does not follow -- too many lookups away from a selected object, or past the objects a plan holds -- is left empty, and the plan lists each with why. A lookup a record cannot be written without is named too: those records will be refused.
- **Dependency order**: parents go before the records that point at them, in waves; a lookup of a cycle goes in empty and is filled by a second pass. One the target refuses to fill, or whose record never followed -- refused, held back, or of an object skipped or whose write failed --, stays empty: the record is written, without its link, and the run ends partial. The result, its node and the command line's summary say how many records stayed without which lookup and why, under the target's code, `PARENT_REFUSED` or `PARENT_NOT_WRITTEN`, and the audit trail counts them per object. A record whose parent the target refused is held back rather than written without it, and so is one whose parent is of an object the plan holds and the run did not write -- skipped with **Skip Node**, or whose write failed: its node and the command line's summary count it among the refused under `PARENT_NOT_WRITTEN`, with the object and why, and the audit trail among the failed. A lookup at an object the plan does not hold goes as before. Statuses are applied after the records under them.
- **Record types**: a record goes in on the target's record type of the same object and API name. One on Master in the source, or of an object whose record type the run does not write, goes in without one, and the target gives it its type: the default of the user the run writes as or, where that user's describe names Master and exactly one other record type is open to them, that one. `--plan-only` predicts it. Once written, the first 200 of each object are read back, after the last write, and its node and the command line's summary say how many went in so, why, and what they hold, naming what still ran of a muted run when the target's automation set another. One on a record type the user the run writes as cannot use in the target is held back alone, before its write, and the records under it with it; the object's other records go, and the object fails only when none of them went. Its node and the command line's summary count it among the refused under `RECORD_TYPE_UNAVAILABLE`, a line per record type with how many records carry it and what to change in the target -- give that user access to the record type, or activate it if it is inactive --, and the audit trail among the failed; a record under it is held back under `PARENT_REFUSED`.
- **Accounts as their kind**: a person account as a person account, a business account as a business account, by the rule Forge and Sync share. One sent without its record type goes in as a person account where the person type is the only one open.
- **Currencies**: the plan lists the currencies the target does not hold active; a record in one of them is written in the target's corporate currency, its amounts converted at the source's rates.

## Fit to storage

A plan too big for the target need not be cut by hand. The review says what the plan comes to against the target's data storage and API requests, and whether a run would write, ask or be refused; a run refused for its storage says the figures and offers the same fit. **Fit to storage…** opens it, nothing written:

- **The same share of every object** keeps the largest share that fits, spread evenly over each selected object by Id. **At most so many records of each object** caps those you name, an object left empty uncapped, and **Then take the largest share of what the caps leave that fits** adds the share. **Use no more than** bounds the MB, whatever the target has left.
- **What it may take**: 80 % of what the target says it has left, half a MB off first for the rounding of that figure, less the room kept for what its flows still running create under the records. What **Mute the target's automation** keeps quiet creates nothing; what an Apex trigger creates is named, not counted. Its writes leave a tenth of the day's API requests, room for a checkpoint taken first among them, and it holds to the most records a run may write.
- **Every record stays with its parent**: an account comes with all its contacts, and a record whose parent was cut is cut with it. A lookup at its own object, or one filled after its wave, stays empty when the record it names was cut, and the plan names it.
- **What it says**: object by object, the records in the source, kept and cut; what bounded the fit; the room kept for the flows, or that the target's automation could not be read; which lookups stay empty; and the requests of the source it read to choose the records. A plan that cannot be cut to fit is refused, with why.
- **Undo fit** gives the original plan back. A fitted plan meets the run's checks again, what the target has left read afresh, and is refused if it no longer fits. A record that comes to name a cut record between the fit and the run stays out, neither written nor refused, and is counted. The result and each node say what the fit kept and cut and what was held back since, and the audit trail records the fit.

## Masking

- **Emails and phone numbers** are neutralized by default, whatever the framework: every email address is written under `.invalid` and every phone number as a fictional one, so that what the target's automation sends to them reaches no one. What it sends to the records' owners, the records the target already holds and an address an alert names may still go, and the run asks first: see [Before a run writes](#before-a-run-writes). Untick **Neutralize emails and phone numbers (recommended)** to copy them as the source holds them.
- **A compliance framework** -- GDPR, CCPA, HIPAA or PCI-DSS -- anonymizes the personal fields it covers. **None** is the default, on the review step and on the command line, and stays so: a copy holds the source's records as they are, its emails and phone numbers neutralized as a Sync run writes them. With **None**, nothing is anonymized beyond the emails and phone numbers, and the review step says so beside the framework picker: names, addresses and the other personal fields are copied as the source holds them until you pick a framework. The review step says, per object, which personal fields no rule of the framework covers, which would be copied as the source holds them, and the run ends with a **Compliance Report** you can export as JSON. Its timeline gives each object the time the run's message that finished it carries, and how it finished: completed, failed, or skipped where Skip Node or a stop kept it from the target; an object the run did not finish is not listed.

## Before a run writes

- **Production Guard** asks before a run writes to a production org; a sandbox, a scratch org and a Developer Edition org are not production orgs.
- **The volume**: past `sandforge.safety.confirmAboveRecords` records (2,000 unless you set it), or near the target's data storage, a confirmation lists the records per object; a plan whose records take more data storage, or more of the day's API requests, than the target has left is refused, and nothing is written. Those requests count a checkpoint taken first, the reads that check the record types the target gave and the read of its deliverability.
- **Emails**: what the target's flows would send as the records go in is counted against the emails it has left today -- on a Developer Edition, 15 single emails a day, its email alerts among them -- and a run past them is asked about. So is a run whose target's automation -- or its flows, processes or workflow rules -- could not be read: the confirmation says their emails were not counted, and why, as a Sync run's does.
- **Whether those emails go out**: when something that still runs may send one -- a flow, process or workflow rule with an email action, or one whose definition was not read, whatever the mute leaves -- the run reads whether the target delivers it, with one line of anonymous Apex that sends nothing, as the user it writes as, and never in a production org. On System email only or No access none goes out, and nothing is asked. On All email, or when the org would not say, the run's question opens on them: what may send, and where the emails go -- the records the run writes are under `.invalid` unless you unticked the box, but not their owners, the records the target already holds nor an address an alert names. Its button then reads **Execute and send the emails**, and going on is the accord. An automation that could not be read asks the same way, what it may send being unknown. What an Apex trigger sends is read nowhere.

## Checkpoint first

Off unless ticked on the review, and recommended there, as a run has no removal. The run then takes a checkpoint of each object it writes, and each the target's flows that still run create as it writes them, files included, once its question is answered and before the mute's permission sets are assigned. **Rewind to before this run…**, on the result, opens the preview of a rewind to it.

- **Its cost is that of the tables, not of the run's records**: a checkpoint holds an object whole, and a rewind to it takes back what anyone did on those objects since, as well as the run. The question says the records, API requests, time and space it takes, before anything is read.
- **What it leaves out**: Chatter posts, Knowledge article versions, users, permissions and setup, and what an Apex trigger or a flow SandForge could not read creates outside it. A rewind leaves those as they are, and the result names the objects it does not hold.
- **On this machine**: unencrypted, readable by you alone, for the days `sandforge.checkpoint.beforeRunKeepDays` sets (7 by default, 0 until it is deleted). The Checkpoints page lists it, marked **Before Autopilot run**.
- **Refused, or stopped as it is taken**, the run writes nothing, and the page says why. A run that wrote nothing -- the target took none of its records -- deletes it, and says so.
- It is offered on a sandbox, a scratch org or a Developer Edition, and says why not on another target. Once a rewind to it has gone through, the result carries the mark: see [Rewound runs in the histories](checkpoint.md#rewound-runs-in-the-histories).

## While it runs

The review says, above **Copy into**, that SandForge cannot remove what the run writes, or, with **Checkpoint first** ticked, that the checkpoint is the way back. The page waits on the run for up to 12 hours, as Seed's and Sync's do; should it stop waiting, it stays on the run and says it may still be writing and that Monitor's Live Operations shows where it is. A second run on the same target is refused while one writes, `AUTOPILOT_RUNNING`, and nothing of it is written. The control panel shows the records processed, the API calls, the elapsed time and the current wave, and offers **Pause**, **Resume**, **Skip Node** and **Stop**; Live Operations lists the run, paused while it is paused, and its Cancel stops it as **Stop** does. A stopped run writes nothing after the stop and says what it did not write, or left unfinished: lookups a second pass would have filled, statuses not given back. The audit trail (Reports → Audit trail) records each run, with what it wrote per object.

As the run ends, each object takes the status the run left it on: **Completed** when it wrote or linked any of its records; **Failed** when the target took none of them -- a record held back because the parent it names was refused, or for its record type, counts among the refused --; **Skipped** when **Skip Node** kept it from the target before its turn, or **Stop** cut it short or came before its turn. A skipped object is never said completed, on the graph or in the compliance report: the graph draws it dashed, with the word Skipped, where an object still waiting is drawn solid. A run that wrote part of what it set out to -- records refused, a lookup left empty -- ends **Partially complete**, and one that wrote nothing **Failed**, said above the panel's tabs. The audit trail lists an object skipped with **Skip Node** as skipped, with the records it did not send, and one a stop cut short with what it wrote and what it did not send, as the command line's summary does.

## From the command line

`sandforge-autopilot --source <alias> --target <alias> --object <ApiName>` runs the same copy without the editor, into a sandbox or a Developer Edition org -- a production target is refused before the scan --, with `--plan-only` to scan and plan without writing, `--compliance <name>` for a framework, `--keep-contact-points` to copy emails and phone numbers as read, and `--max-total <n>` for the most records it may write (10,000 by default). See [Command line & CI](../../ci-examples/README.md).

`--json` gives how the run ended under `result.status`: `success`, `partial` or `failure`, as the panel and the audit trail say it. It is `partial` when the target refused some of the records, when a record it wrote keeps a lookup the run could not fill, listed under `result.lookups` with why and how many records (`leftEmpty`), or when one stays a draft, the status it had in the source refused, listed under `result.statuses`. A refusal beside records the run linked to is `partial` too: `failure` is a run that wrote and linked nothing. The exit code stays `0` unless `--fail-on-partial` is given, which then exits `3`.

`--plan-only` writes nothing, and it does send requests: beside the scan's count of each object, it reads the record types of both orgs, a request each, then for each object with records the target's describe, and, where the target holds a type besides Master, the records per record type in the source, a request for a table, or per 200 ids for an object read by id. That is what its prediction of the record types costs.

`--fit share` fits a plan as the panel does, `--fit-cap <Object>=<n> | <n>` sets at most n records of an object, or of every one another `--fit-cap` does not name, and `--fit-within <MB>` bounds the MB. `--plan-only` and a real run say what was kept and cut, object by object, and which lookups stay empty, and `--json` names the ids kept. The fitted plan meets the gate again, `/limits` read afresh; a plan that cannot be cut to fit is refused, exit `1`. A plan refused for its storage, its API requests or `--max-total` names `--fit share`.

`--accept-emails` is the question's answer: where the target delivers the emails of what still runs, or would not say whether it does, a run without it is refused, `EMAILS_NOT_ACCEPTED`, exit `1`, nothing written: the line names the code, and `--json` answers `refused: { code, message }`. An automation that could not be read asks the same way, what it may send being unknown. `--plan-only` says what a real run would meet.

`--checkpoint-first` takes the checkpoint above, kept `--checkpoint-keep-days <n>` days (7 by default, 0 until it is deleted), without the objects `--checkpoint-exclude-object <ApiName>` names; `--plan-only` says what it would hold and cost, and takes nothing. A checkpoint refused refuses the run, exit `1`, nothing written. The output names it and the `sandforge-checkpoint rewind` command that takes the run back, and `--json` gives it under `checkpoint`.

`--mute-automation` keeps quiet, for the run alone, what the target's own bypasses keep quiet, its emails counted of what still runs. Its permission sets are given back right after the last write, and when some were assigned, the record types are read again before the first write, as an assignment may open others; with `--plan-only` it says what it would assign and assigns nothing. See [Muting the target's automation for a run](../faq.md#muting-the-targets-automation-for-a-run).
