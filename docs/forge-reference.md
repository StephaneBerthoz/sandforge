# Forge: Reference

The [quickstart](forge-quickstart.md) takes you through a first clone in a few steps. This page says what each of those steps reads, checks, writes and keeps, and what the clone command takes.

## What Forge handles for you

- **Record-scoped clone**: only the transitive closure of the root record (1 Case → ~50 records, instead of every row of every related table)
- **RecordType cross-org**: re-mapped automatically by object, namespace and `DeveloperName`, among the active record types of both orgs. A record type a managed package installed matches the same package's in the target, and one the org made itself matches the target's own, never one the other, though both carry one `DeveloperName` on the object: a source record type the target holds only under another namespace is left unmapped, the log and the command line's `record-types` line say so, and a simulation offers its gap. SandForge names a package's record type `ns__DeveloperName` wherever it shows or takes one
- **Reference data**: `BusinessHours` and `OperatingHours` mapped by `Name` instead of cloned
- **Person Account quirks**: `__pc` and auto-`Name` fields stripped per-record; in a target without person accounts, the account goes in as a business one by its name, and its contact as a contact of that account
- **Picklist drift**: a value the target would refuse — in a restricted picklist, not one of the field's values there, or not one the record type the row goes in with allows — is replaced by that record type's default or left out, and the results say which, per object and field; an unrestricted picklist or a combobox takes any value, and keeps the one read, save a standard status, stage, priority or role, checked as a restricted one; a value the target refuses all the same — a record type never given values of a field takes none of them, though the target's UI API lists them all for it, so no check before the write can tell — has its record written again without that field, and the results say so
- **Validation rules of the target**: a record a rule refuses on a field it names is written again without that field, and the results say which field and why
- **Cycle FKs** (Account ↔ Contact): 2-pass insert + UPDATE
- **Required parents outside the graph**: a record that cannot be written without a record of an object discovery did not reach — the invoice a case's junction row names — gets that record read by id, with what it cannot be written without, never what is under it; the "Auto-fetch parents" toggle copies, one by one, what that leaves (a parent a lookup naming several objects names), its picklist values, validation rules and person contact handled as the run's own rows are
- **Upsert via External Id** (command line only, `--upsert`): re-runs patch existing rows instead of failing on `DUPLICATE_VALUE`, and the summary counts the rows patched as `updated`, apart from the ones created. The wizard always inserts.
- **Emails and phone numbers, neutralized by default**: every record goes in with its email addresses under `.invalid` and its phone numbers replaced by fictional ones, anonymized or not, so the target's automation reaches no one ([below](#emails-and-phone-numbers))
- **GDPR / PHI presets**: one-click anonymization for Email, Phone, Address, Birthdate (4 starter presets)

## Clone directly

What [**Clone directly**](forge-quickstart.md#clone-directly) skips, and what still guards it.

What the path skips is said beside the button: the metadata diff between the two orgs, which runs on the Review screen, is not run, nor the read of the gaps the target holds against the rows, so none is decided — the rows they refuse are refused — and a run to see first what would be written is Review's **Simulate**. Everything that guards a run still does ([below](#before-the-run-writes)): a production target is refused, what the target runs as the run inserts its records is read all the same and put to you before anything is read, and the records the run is about to write are counted and held to the target's data storage before the first is written. The button is off whenever **Discover Graph** is: a source and a target that are two orgs, and an input the extension accepts. Production Guard and the duplicate-run cooldown answer the run as they answer one started from Review. The page can be left while the discovery runs — for another page of the panel, through the command palette or a shortcut: the run still starts as the discovery answers, and the page comes back on it. A discovery that fails stops on the discovery screen with its error, shown when the page comes back if it failed while the page was away, and one you leave with **Back** starts nothing; **Retry Discovery** then runs the discovery alone, and its graph waits for Review.

## Simulate a run

The gaps [a simulation](forge-quickstart.md#simulate-a-run) finds, and the decisions they take.

What the target would refuse or change, record by record, goes to Review as gaps, each counted on its records and never carrying a record's data — a picklist value, a currency code or a record type's name at most, otherwise lengths and counts:

- a picklist value the record type the record goes in with refuses, with the values it allows and what the run writes instead (its default, the first value it allows for a required field, or nothing); a dependent value its controlling value does not allow, by the describe's `validFor`, on an object whose record types were not read; a value of a picklist that takes any value, absent from its list, which goes in as an inactive value;
- a field the target requires and fills nothing in for, absent or empty in the records — one only the target has, too;
- a text longer than its field in the target, and a number with more digits before its point than the field holds;
- a record type the target has no counterpart of under the source's name, and one the user the run writes as may not use, each with the record types it may be mapped to;
- a currency the target does not hold active, read once from both orgs' `CurrencyType`: the run writes its rows in the default their record type gives the currency field, where it read one the target holds, and in the target's corporate currency otherwise, each currency field of the row converted into it — divided by the source's rate of the row's currency, multiplied by the target's rate of the one it goes in, rounded to the field's decimals — and the gap names the currency written and the fields converted. An org with advanced currency management on is read its dated rates too (`DatedConversionRate`), and an opportunity is converted at the rates of its close date, the platform's own rule, where a dated rate covers it; whether it is on is read from the org's currency settings (`CurrencySettings.enableCurrencyEffectiveDates`, through the Tooling API), and, where they cannot be read, from whether the user may create a dated rate — when neither says it is on, the static rates convert the opportunity and its line says the dated ones could not be confirmed. The records whose currency is their parent's — an opportunity's products, its quotes and their lines, an order's products, a contract's lines, a custom object's detail rows — take the currency their parent went in, their amounts converted by the same factor; a quote is written in its opportunity's, which the platform gives it whatever it is sent. The prices follow their lines: written once the records their lines belong to have gone in, each goes in the currency of those records, on the source's own price of the same product and price book in that currency, read as the standard prices are, the lines pointed at it — a product the source does not price in it keeps its own price, converted into it, and its standard price with it, said on the price's line ("2 GBP → EUR: price(s) replaced by the source's own price in the currency of the record their lines belong to, for the same product and price book"). A price nothing asks another currency of goes, in a currency the target lacks, in the currency written as before. A run says it on the object's line and in its results ("1 row(s) in GBP written in USD, the target's corporate currency, GBP not being active there: amounts converted at the source's rates, dated by CloseDate (Amount)"); a currency mapped to another the target holds is converted the same way;
- a value of a unique field the target already holds, asked 200 values a request.

The run's config keeps the decisions taken on them, with templates: a picklist value written as another, or left out, for every record of the object or for one record type of the target; a source record type written as a target one, or as the object's default; a value given to a field the records leave empty; a text cut to the target's length; an object left out of the run, what points at it then left empty as any lookup at a record outside the clone; the records that hold a value a gap names, held back; and a gap left as it is, which a simulation still reports, marked ignored. Each is applied once to each record before it is written, in a simulation as in a real run, and the results and the command line's summary list each with the records it changed.

## Graph or table

The discovery, Review and execution screens show a graph's objects either as a graph, drawn with its relationships, or as a table. On discovery and Review, each row has the box that includes or leaves out its object. The execution's table gives each object a row with what its node on the graph says: its status, its progress while it is written, its records and fields, its personal fields and the errors discovery met, updated as the run goes. The `sandforge.forge.graphView` setting chooses between them:

- `auto` (the default): the graph up to 25 objects, the table past that;
- `graph` or `table`: always that view.

On Review, **Find an object in the graph** searches the objects by API name: those it matches are ringed on the graph, **Show** brings one into view, and **Leave out this branch** leaves out the object with every object only it reaches — what another way from the top of the graph reaches stays. The branch goes as unticked boxes go, kept in the run's `excludedObjects`, and **Put them back** takes it back at once. The run's root offers no branch: it would be the whole clone.

The **Graph View** / **Table View** switch on any of these screens overrides the setting on all three, for every run, until the panel is closed. Why 25: each progress event of a run redraws the whole execution graph, and past a few dozen objects the redraw takes longer than the time between two events the extension sends, so the panel stops answering until the run ends — a record clone can reach hundreds of objects. The table redraws only the row of the object an event is about.

## What the target runs as the clone writes

A clone writes its records into an org that runs its own automation on them: written into a sandbox, a clone fired the target's record-triggered flows on every record it created, flows that send an email or a text message among them. The **Automation** tab of the Review screen says, before the run, what the target org runs on the objects the run writes. It is read once as Review opens, with the metadata diff, and the run started from Review takes that read for what it puts to you before it reads anything ([below](#before-the-run-writes)):

- **What it lists.** Per object, what each write of a record fires: the insert of every record the run creates; the update of those it writes a second time — a lookup filled in once its record exists, an order given back its status; and the delete of a removal of the run's records. Under each write, the target's active record-triggered flows (`FlowDefinitionView`, whose `TriggerType` says before or after the save, or before a delete, and `RecordTriggerType` which writes start the flow), its active Apex triggers (`ApexTrigger` over the Tooling API, its `Usage…` flags saying the events), its active Process Builder processes (`FlowDefinitionView` with `ProcessType = 'Workflow'`, placed on their object by the record variable of their active version, `FlowVariableView`, or by their metadata) and its workflow rules (`WorkflowRule` over the Tooling API: whether a rule is active is in its metadata alone, and one left unread is listed all the same), in the order the platform runs them: the flows before the save, the triggers, the workflow rules, the processes, the flows after it. The tab counts on its label what fires as the run inserts, but what a permission the user the run writes as holds keeps quiet.
- **What reaches people.** A flow's or a process's email alert, Send Email, custom notification and outbound message, and a workflow rule's email alerts and outbound messages, carry a **Sends messages** badge and are named; an Apex action whose name says text message — SMS, Twilio, WhatsApp — is listed as a text message, a guess from its name alone. What runs once the save is committed is listed too, as a rollback does not stop it: a flow's asynchronous path, known before its metadata is read; its scheduled paths, with their offsets; a workflow rule's time-dependent actions.
- **Which objects.** Those the run writes, as far as the graph tells before a row is read: the objects Review includes, but the reference data the run matches by name; the catalog past the graph when a line cannot be written without its price — the price, its product, book and selling model — or an assignment without its category and catalog; and an order's items when discovery stopped before them. An object you leave out on Review after the read drops off the tab; one you take back in is already read.
- **What keeps a flow quiet.** The start condition of each flow is read from its active version's metadata, with the Decision the flow starts with, and a workflow rule's criteria from its own: the custom permissions they name are listed, and the custom settings (`$Setup`), user fields (`$User`), profiles (`$Profile`) and custom metadata (`$CustomMetadata`) that keep it quiet. A start condition keeps the flow from starting for what it requires not to be: `NOT({!$Permission.<name>})`, alone or among the terms the formula requires together, `NOT(OR(…))` over alternatives one of which it is, a permission or a checkbox compared with false, a profile compared unlike a name. So does an outcome of the Decision the flow starts with that ends it, when every path of the flow starts with that Decision. The tab says whether the user the read runs as — the user the run writes as — holds each custom permission (`UserSetupEntityAccess`), says to assign in the target org the ones that user does not hold, and marks quiet for the run what a held one keeps quiet. Under each one that user does not hold, it names the permission sets of the target that include it (`SetupEntityAccess` joined to `PermissionSet`; neither a profile's own nor a permission set group's, which cannot be assigned), the smallest first — the one that grants the fewest setup entities and object permissions beside it — and the command that assigns that one to the user the run writes as, `sf org assign permset --name <permission set> --target-org <alias> --on-behalf-of <username>`, with a button that copies it. SandForge never runs it. When no permission set holds the permission, the tab says so: an admin creates one that includes it. A permission named any other way is listed without that advice, and what a Decision further on tests is named: either may be a way out of the flow, or what starts it.
- **Assignment and duplicate rules.** The active assignment rule of a Case or a Lead the run writes (`AssignmentRule`) is listed, with whether it applies. Forge sets each record's owner itself, and every create and update it sends says `Sforce-Auto-Assign: FALSE` unless the run asks for the rules (`ForgeConfig.applyAssignmentRules`, the clone command's `--apply-assignment-rules`): REST otherwise applies the target's active assignment rules to the Cases, Leads and Accounts it writes, which can give them another owner and mail that owner. The active duplicate rules of each object (`DuplicateRule`) are listed: Forge's writes save a record a rule only alerts on (`Sforce-Duplicate-Rule-Header: allowSave=true`), and a rule that blocks still refuses it. Which of the two a rule does is in its metadata alone, which the tab does not read.
- **What it costs.** Five requests to the target — the flows, the triggers, the processes, the workflow rules, the duplicate rules — a sixth when the run writes cases or leads, for their assignment rules; one to place the processes the definition view names no object for, one for the ids of the custom objects workflow rules name, one for the custom permissions of the user when a condition names one, and up to four when that user does not hold a bypass a condition names — the custom permissions, the permission sets that include them, and what each grants; and the start conditions, process and rule definitions: the org gives metadata one row per query, so each flow version and workflow rule is retrieved whole by its id (`/tooling/sobjects/Flow/{id}`), 25 in one Tooling composite — every subrequest a composite takes, where it runs five queries at most and halts every query after the fifth (`PROCESSING_HALTED`); the start conditions leave the room in their last composite to the definitions. What the org will not retrieve is read by query, five a request, and once a composite of retrieves gives nothing back, every record left is; a subrequest an org halts all the same is sent again, as many a request as it ran, within the same requests. It reads 1 500 start conditions at most, in 60 requests (300 when it reads them by query), the flows after the save of a created record first, then the ones before it, then those of an update and of a delete, and 500 definitions of processes and workflow rules, in 20 (100 by query), those of the objects nearest the record first and a process before a rule; the tab says how many it left unread, and the objects whose start conditions it left. A host that cannot send a composite reads one a request, 25 start conditions and 15 definitions at most. It keeps four requests in flight at most, beside the two describes of the metadata diff.
- **What it cannot read.** A part the target refuses — any of the above, a start condition, a definition — is said with the org's reason, and the rest is read all the same. Nothing in the tab holds back **Execute Forge**: the question comes as the run starts.

The tab does not read the code behind an Apex trigger or an Apex action, the flows and processes a platform event starts, escalation and auto-response rules, a bypass checked in Apex or in a formula field, or what fires on the files the run copies.

With the automation, Review reads from the target org's metadata what it holds against the rows before any of them is read, each as a gap, and a line under the preview says how many it read, how many refuse rows, what it cost, and what the target would not give:

- **Validation rules.** Each active rule (`ValidationRule` over the Tooling API) on an object the run writes, with its message and the field it shows its error on: a row it refuses on that field goes again without it. Its formula, read from its metadata one request at a time, 25 rules at most, is searched for what keeps it quiet (`$Permission`, `$Setup`, `$User`, `$Profile`, `$CustomMetadata`, as a flow's start condition is read), and a rule kept quiet by a custom permission the user the run writes as holds refuses nothing.
- **Duplicate rules.** Each active rule (`DuplicateRule`), with what it does on insert, read from its Metadata API definition: one that blocks refuses the rows it matches whatever `allowSave` says; one that allows the insert, with an alert or a report, lets the run save. One that blocks is a warning, not a gap that stops the run: whether a row matches depends on what the target holds, and a rehearsal that meets a refusal makes it blocking, with its rows. A rule whose definition could not be read is taken for one that may block.
- **Fields only the target requires.** A field the target will not take a row without — not nillable, createable, not filled in at insert — that the run does not write: the source has no such field, cannot give it, or the run leaves it out. Every row of its object is refused unless it is given a value.
- **Lookup filters.** The filter of each lookup the run writes, as a warning: neither this read nor a simulation checks it against the rows, as what it refuses depends on the records the lookups point at in the target. A rehearsal does: each row the filter refuses comes back as `FIELD_FILTER_VALIDATION_EXCEPTION`, a gap with its field and its rows. In the run, a lookup the target lets be empty is left out of a row the filter refuses; a required one leaves the row refused.
- **The API budget.** The daily API requests the target has left (`/limits`, `DailyApiRequests`) against the calls the run takes: its writes, 200 rows a call, and a read of each object for each 2 000 rows. Past what is left, the run is said to be refused; past 80 % of the org's daily limit, warned. A clone of one record is never said to be refused for it, as discovery counted whole tables; a budget the target will not say, as it may answer a user without Manage Users, is a warning, never taken for enough.

It costs a request each for the validation rules, the duplicate rules and the limits, one per formula and per ten duplicate rule definitions, one for the user's custom permissions when a formula names one, and one per describe the run and the metadata diff do not already hold; it keeps four requests in flight at most and gives up after 60 seconds. Nothing of it holds back **Execute Forge**.

## Emails and phone numbers

Whatever the target runs on the records it receives, the clone gives it no address or number of a real person unless you ask it to. By default, every record it writes — the rows of its objects and the parents it copies from outside the graph — goes in neutralized, whether **Anonymize PII** is on or not:

- **An email field**'s address goes in under `.invalid`, the domain kept from ever resolving: `jane@acme.com` becomes `jane@acme.com.invalid`, readable and never delivered, as Salesforce leaves the users' addresses of a refreshed sandbox. One already under `.invalid` is left as it is; one the field cannot hold with the suffix becomes a short address of its own, `user-…@example.invalid`, drawn with a key of the run's own — but for an external id a run of the command line's `--upsert` matches records by, whose short address is drawn from the address alone, the same in every run, so that the next run matches the copy it wrote.
- **A phone field**'s number becomes a fictional one, in the mobile range kept for fiction, `+33 6 39 98 XX XX`, written in the layout of the number it replaces (its spaces, dots, dashes and parentheses, as many digits: `01.23.45.67.89` becomes `06.39.98.XX.XX`), so that a validation rule of the target on the number's format, which the source number met, is met; a number no form of the fiction is as long as is written `+3363998XXXX` (`063998XXXX` where the field cannot hold the country code). The same number gives the same fictional one throughout a run, and two numbers never the same one. The range holds 10 000 numbers: past them, a number is left out, its field empty, and the run counts it.
- **A text field** whose API name gives it to either — `Notification_Email__c`, `SMS_Number__c`, `CC_Emails__c` — has each address, or each run of seven digits or more, in its value treated so, the rest of its text left as it is. A checkbox or a picklist named like one, such as `Email_Opt_Out__c` or `Phone_Type__c`, is left alone.

With **Anonymize PII** on, the anonymized email and phone fields follow the same rule: an address goes under `example.invalid` or `.invalid`, never `example.com`, and a phone whose method leaves a number — the default mask, a fake, a shuffle, the format redrawn — takes a fictional one, never the last digits of the real one.

**Keep emails and phone numbers as they are**, among the options of the Forge page, writes them as the source holds them, and says that the target's flows, triggers and email alerts may then reach real people. A template saved from the run keeps the choice, and so does a run put back in the form from **Recent runs**. The results say whether the run neutralized them, and how many values in how many fields, field by field; the run's audit entry (Reports → Audit Trail) says it too, under `contactPoints`, `contactPointFields` and `contactPointValues`, with the counts alone.

## Before the run writes

Run for real, a clone whose dry run said 37 records wrote 34 216 into a sandbox — a parent added to its graph widened what was read of its children — and another fired the target's record-triggered flows on every record it created. Whether started from Review or with **Clone directly**, a run now passes these checks first, and a run stopped by one writes nothing:

- **The target.** A sandbox, a scratch org or a Developer Edition org — a Trailhead playground is one. Any other org, and one whose edition SandForge never read, is refused as a production org before anything is read, and no setting lifts the refusal: Forge does not write to production, as the command line does not.
- **What fires as the run inserts and updates.** Before the run reads anything, the extension takes the **Automation** tab's read of the same graph, ten minutes old at most, or reads it again — always after you cancelled this confirmation, so that a permission set assigned meanwhile is seen. When a flow or an Apex trigger of the target fires as the run inserts its records, or as it updates the records it writes a second time, a VS Code confirmation lists each, with its object, its kind and its name, and the custom permissions that keep a flow quiet. The run updates a record it inserted to fill in a lookup left empty at insert — a record's lookup at another of its object, or a lookup of a cycle, its record written later — to give an order or a contract back the status it had past Draft, to give an event's invitee its answer, and, on a retry, to fill in the lookups the run it retries left empty. Which objects it updates is told from the graph before anything is read: every object of a cycle that holds a lookup at another of it is counted, as the write order that decides which goes first is read from the fields afterwards. For a custom permission the user does not hold, the confirmation names the smallest permission set of the target that includes it and the command that assigns it, which **Copy the command** copies — and cancels the run, which you start again once the command ran — or says no permission set holds it. A part of it that could not be read is said there too, and asked about rather than passed over. **Cancel** reads and writes nothing.
- **What it is about to read.** A clone of whole tables reads each object a page at a time and writes each page before it reads the next, holding one page; a clone of one record holds every record it reads of an object until it writes them. Either reads at most `sandforge.forge.maxRecordsPerObject` records of one object (50 000 by default, a million at most): an object with more is read to that number and said truncated. An object read to **Records per object** with rows left in the source — on **Smart**, a clone of one record has no such cap and a clone from a SOQL query 100 — is named, with the cap, in the results, in a simulation's results and in the confirmation before the write. When nothing caps the read of an object it writes — **Records per object** on **All** — and its table holds more than that number, as discovery counted it, a VS Code confirmation lists those tables with their counts before anything is read. A clone of one record reads only what its record reaches of each table, which no count says before the read: the table is the most it can read. A simulation is not asked. **Cancel** reads and writes nothing.
- **What it is about to write.** Once every row is read, and before the first is written, the records are counted per object — a clone of whole tables, which holds no row before it writes the first, counts each table before it reads anything (`SELECT COUNT()` under the object's filter, no more than it reads of it, the person accounts apart) — and the data storage they take is estimated by the sizes Salesforce documents (help.salesforce.com, knowledge article 000383664): most records 2 KB, a person account 4 KB, a campaign 8 KB, a campaign member 1 KB, an article 4 KB and more with rich text, an email message its actual size. That is held to what the target has left (its limits, `DataStorageMB`): records that do not fit are refused. The prices the clone may read as it writes them are counted in too, at most: a price in the currency of the record its lines belong to, the source's own beside the one read, which is known once that record is written; every currency the record may go in is counted, the run reads no other, and the gate says how many. Past `sandforge.safety.confirmAboveRecords` (2 000 by default; 0 never asks about the volume), past 80 % of what the target has left — Salesforce counts storage a while after a load, so less may be left than it says — or when the target will not say what it has left, as it may answer the user the run writes as, a VS Code confirmation lists the records per object and the storage; past 50 000 records it says the volume is large. When the target's flows, processes and workflow rules send emails as the records go in, the daily limits they count against are read too (`SingleEmail` for a Send Email, `DailyWorkflowEmails` for an email alert; on an org held to the 15 single emails a day of a Developer Edition, an email alert counts against the single emails too, as Seed counts it, and the confirmation says so): past what the target has left today, a flow that sends fails, and a record whose flow fails in the save is refused, so the confirmation says it, with the emails each record sends; when the target will not say what it has left of one of those limits, the confirmation says it too, with the emails counted against it. A bypass that keeps the flow quiet, or a smaller run, avoids it. What sends and could not be read is counted as sending nothing, so the confirmation asks then too, and says why those emails were not counted, as a Sync or an Autopilot run's does: the target's automation, or its flows, processes or workflow rules, refused, or the definition of a flow, a process or a rule that fires as the records go in refused or left past the read's bound, named per object. A flow a package installed is never read — the target names its active version in no form an id takes, and lets no user read its definition — so a target whose package runs one on an object the run writes always asks, and the confirmation names the package. When this window simulated the same case — the same two orgs and the same record, query, template or prompt, whatever the depth, the caps or the objects discovery found since — the confirmation sets beside each object what that last simulation counted, and says when it ran and its total; past twice that total, or more than 500 records past it, it asks whatever the volume, and says what may have widened the read. **Cancel** writes nothing.

A clone of one record reads every row it clones before it writes any, so that what is counted is every row it writes, and holds them meanwhile. A run of whole tables — a query, a template — counts each table before it reads a row, as above, then reads and writes it a page at a time. A run refused or cancelled at one of these checks goes back to Review — a retry, to the results of the run it retries — which says why, and the audit trail records it as stopped, under `PRODUCTION_TARGET`, `AUTOMATION_DECLINED`, `READ_DECLINED`, `WRITE_DECLINED`, `STORAGE_EXCEEDED` or `CONFIRMATION_UNAVAILABLE`; a run you confirmed is recorded as confirmed.

## Rehearse a run

No Salesforce API validates a record without saving it: only a transaction that is rolled back gives the platform's own verdict — its validation rules, its triggers and flows, its duplicate rules, its restricted picklists. **Rehearse**, beside **Simulate** in Review's action bar, gets that verdict on the rows the run would write, and keeps none of them:

- **The rows.** The run's own executor reads, cleans and checks every row as **Execute Forge** would — picklists checked against the target's record types, email addresses and phone numbers neutralized, the decisions of the **Gaps** tab applied — with a writer that keeps each row instead of sending it. Up to 200 rows, every one is rehearsed; past that, one row per object, record type and set of fields given a value, with the records the run creates that it names. Files are not copied. The updates a run makes after its inserts — a lookup a second pass fills in, an order's status given back — are rehearsed too: every one up to 19, past that one per object, set of fields and status given back, with the records each is of and names; one of a record the target already held is never sent.
- **The calls.** Each composite call (`/composite`, all or none, its subrequests run in the order sent) holds up to five sObject Collections requests of up to 200 rows each, each row with its own verdict, a row naming a record of an earlier request by that request's answer (`@{rows0[3].id}`); then the updates of the records it created, one subrequest each, as many as its 25 subrequests leave room for; and ends on an update of a record that does not exist, which fails: the call is rolled back whole. A call that stops at a refused row leaves the rows of its later requests for the next call, sent again with the records they name; a row whose parent was refused is not judged, nor is an update of a record refused. A call that stops at a refused update leaves the updates after it for a call of their own, which creates their records again. A call whose closing update did not fail would have been kept: the rehearsal stops there and names the records it created.
- **Before the first call.** Production Guard refuses a production org, as for a run. A VS Code confirmation says how many records the rehearsal creates of those the run would, the updates it makes of them, the composite calls it costs and the most it may cost, what the target runs as they are created and updated, and what a rollback does not take back. Rolled back with each call, and never sent: emails, `@future` and Queueable jobs, platform events published after commit, and the asynchronous paths of Flows. Not rolled back: platform events published immediately, and callouts already made. **Cancel** sends nothing.
- **The verdicts.** A line under the button says where the rehearsal stands — reading, waiting for the confirmation, the call under way — then what it judged, what would save, what was refused, what it could not judge, and the calls it made, and of the updates the run makes after its inserts, what it judged, what would save, what was refused, and how many it did not rehearse. Each refusal joins the gaps, with its status code, the first field it named, the message without the row's own values (none for the codes whose message is the value), and how many rehearsed rows got it, and how many of the run's rows those stand for. A refusal a read before the run also reports takes that read's gap: a required field, a refused picklist value of a record type, a text too long (by its length), a number out of range, a unique value the target holds, a lookup filter. A validation rule, a restricted picklist or a lookup filter that names its field is a warning: a real run writes the row again without that field. An update refused is a gap of its own, **Update refused in the rehearsal**, a warning: the record goes in without what the update gives it.
- **Live Operations and the audit trail.** While it runs, the rehearsal is listed in Live Operations on the Monitor page, call by call, where **Cancel** stops it before its next call: the call under way is rolled back whole, as every call is. Reports → Audit Trail records each rehearsal as a **Forge Rehearsal** (`forge_rehearse`) on the target org, in counts, never a value of a record: the rows it rehearsed, what it judged, what would save, what was refused and what it could not judge, of the updates what it judged, what was refused and how many it did not rehearse, and the calls it made; one you declined at the confirmation, cancelled — with the calls it had made — or that was refused before it started, as stopped, under the code that says why (`REHEARSAL_DECLINED`, `REHEARSAL_CANCELLED`, `PRODUCTION_TARGET`, among others); one that failed, as a failure. A call whose closing update did not fail left its records in the target: that rehearsal is recorded as a failure under `REHEARSAL_NOT_ROLLED_BACK`, with the records it left, per object.

## Copy the files of the cloned records

Off by default. On the **Review** screen, **Copy the files of the cloned records** copies, once the records they hang on are written:

- the **Salesforce Files** linked to a record the run clones, the latest version of each, published on the cloned record and linked to every other cloned record the file was linked to;
- the **attachments** whose parent the run clones, written under the cloned parent.

Nothing else: a file linked only to records outside the clone is never read, a library is not copied, and a file that hangs only on records the target already held, linked to rather than created, is left out.

- **Size.** The largest file copied is 10 MB unless you set another, up to 35 MB: what one call to Salesforce carries. A larger file is left out and listed in the results, never cut. Before anything is written, records included, the files together are checked against the file storage the target org has left (its limits, `FileStorageMB`): a run whose files do not fit writes nothing and says what they take and what is left. A run whose files could not all be looked up in the source writes nothing either, and says so.
- **Anonymization.** The content of a file cannot be anonymized. While the run anonymizes its records, the Review screen asks, in a confirmation of its own, that you accept the files are copied as they are, and **Execute Forge** stays off until you do. The acceptance is never kept with a template or a past run: each run asks again.
- **Afterwards.** The results say, per object, how many files were copied and their size, the links written, and every file left out with why. The files a run created are counted in its audit entry, a Salesforce File under `ContentDocument` and an attachment under `Attachment`, and **Remove the records this run created** removes them with the rest: deleting a document removes its versions and its links.

With or without this option, a field that holds a file's content — a quote document's `Document`, a custom field of that type — is left empty in the clone: read, it gives the address of its content, never the content, and that address is not written in its place. The results name those fields per object. So is a classic encrypted field (`encryptedstring`) that the user SandForge reads the source as sees masked, lacking View Encrypted Data: read, it gives its mask (`***-**-1234`), which is not written in its place, on the records of the run nor on a parent fetched from outside the graph, and the results, a simulation's included, name those fields per object. Only this option copies a file's content: a Salesforce File's version and an attachment's body.

## Gaps and their decisions

The **Gaps** tab of the Review screen lists what the target holds against the rows the run is about to write: what its metadata says, what a simulation of the run found row by row, and what the platform refused in a rehearsal. A gap found by several of them is listed once, with the gravest severity any of them gave it. They are grouped by what they do — will refuse rows, may refuse or change rows, refuse nothing — then by object; the gaps of an object the run leaves out, by its box or by a decision, are not listed. Each says what it is, the object, the field, the record type and the picklist value it is about, how many rows it touches, what the read said of it (the values the target allows, a length, a rule's name and message), where it was found, and what the run does when nothing is decided. While gaps that will refuse rows are left undecided, Review says how many beside **Execute Forge**, with **Decide on Gaps**, which opens the tab, and **Execute Forge** asks once before it runs: **Decide on Gaps**, or **Execute anyway**, the rows they refuse then refused and the others written.

Each gap offers the decisions that fit it, taken in one click or one pick:

- **Write another value**, among the values the target allows: kept in `picklistValueMappings`, for the gap's record type when it has one;
- **Leave empty**: a picklist value is mapped to nothing (`picklistValueMappings` with `to: null`), and any other field is left out of the object's rows (`fieldExclusions`);
- **Give a default value** to a field the target requires: `defaultValues`;
- **Cut to the field's length**: `truncateFields`;
- **Write as record type**, one of the target's or the object's default: `recordTypeMappings`, each record type by its name, `ns__Retail` for package `ns`'s. A bare name, as decisions and templates were written before the namespace was read, still names the one record type of the object that carries it; where a package's and the org's own both do, it names the org's own, as Salesforce reads a bare name, and the package's is written with its namespace;
- **Leave the object out**: `excludedObjects`, and its box on the graph unticked, as unticking the box adds it;
- **Hold back these rows**: `skippedRows`, by the gap's id — the rows that hold the gap's picklist value or currency in its field, for its record type when it has one, are not written, and what names one of them goes as what names a row the target refused;
- **Leave as it is**: `ignoredGaps`.

Holding back the rows is offered only where they are exactly the rows the gap is about: a picklist value the target or the record type refuses, a value its list does not hold, a currency it does not hold active, as a simulation finds them. A value refused by its controlling value is not offered it, as the rows holding it under a controlling value that allows it go in; nor is a refusal a rehearsal saw, as it judged one row for each shape of row, not each row. The rows held back are counted with the decisions the run applied. A decision taken is shown as taken, with **Undo**. The tab's label counts the gaps that will refuse rows, on the objects the run writes, that no decision answers yet. Decisions the run holds that answer no gap listed — brought by a template or a past run, or taken on a gap no read finds any more — are listed under the gaps, each with **Undo**: the run applies them all the same.

Every decision is part of the run's configuration: **Execute Forge**, the retry of what failed and **Clone directly** send it, the run's entry in **Recent runs** keeps it, and going back to the form to change an option and discovering again keeps it too.

Under the gaps, **For the target's admin** lists what the target's metadata would need for the rows to go in as they are, from the gaps listed that refuse or change rows: per object, and per record type where a gap holds for one, a picklist value to add or to select for a record type, a dependent value to allow, a required field to make optional, a text field to lengthen, a number field to widen, a record type to create or to make available to the user the run writes as, a currency to activate, a lookup filter to loosen, a validation or duplicate rule to turn off, Create to give on an object — each with its step in Setup, and the rows it touches. **Copy for the target's admin** copies it for whoever administers the target. SandForge changes none of it. A gap no change of the target's metadata cures — a unique value the target already holds, the day's API requests, a field you left out yourself — is not in the list, nor is one that refuses nothing.

A record type that accepts no value of a restricted picklist is found neither by the read of the target's metadata nor by a simulation: the target's UI API lists the field's values for it all the same, and its layouts' record type mappings may not name the field at all, so no read before the write can tell it. Only a rehearsal finds it, as the platform refuses the record, and its refusal joins the gaps; a real run writes the record again without that field and says so.

## Review's controls

The **Controls** tab of the Review screen sets what the run supports beyond its gaps, each written into the run's configuration as it is set, the plan, the gaps and the diffs read so far kept:

- per object of the run, the fields left out of its rows (`fieldExclusions`), ticked among the fields the source lets a run write, read for the object picked — a field left out is not read from the source either, save a lookup, whose record the clone walks to, and the few fields the run reads for its own work: a name reference data is matched by, a currency, a status given back past Draft, an active flag; a filter on its read (`objectSoqlFilters`), a WHERE clause held to the rules the extension checks a run by — 512 characters at most, no comment marker, no semicolon at its end — within the record's scope in a record clone; and the fields written under another name in the target (`fieldMappings`);
- for the whole run, the records of each object at most (`maxRecordsPerObject`), among the caps the form offers; and the owners given to the target's users (`ownerMappings`): a source user's id, and one of the target's active standard users, picked by name, whose id the mapping keeps.

The filter a run of a query gives its root object is the query's WHERE clause, shown and not changed there. A change the run would be refused for is not kept, and the tab says why. **Simulate**, **Execute Forge**, the retry of what failed and a template saved from Review carry what is set; the plan's counts were read before it.

## Templates

**Save as Template**, on a run's results or under the **Gaps** tab — one form on both screens — keeps the run's record ID or query, its depth, caps and options, the objects it leaves out (`excludedObjects`), every decision taken on its gaps, the rows it holds back, its field exclusions, filters, owners and field mappings, its anonymization — the method per category, the preset, and the fields anonymized on each object — the choice to copy its files with the largest size, and its target org. It never keeps the acceptance that files are copied as they are, nor whether the run only simulated. Applied from the **Template** tab, a template sets the form's options, and the rest goes with the run it discovers: the objects it leaves out are unticked on the graph, its fields are selected after its preset, among the personal fields discovery finds, and its file copy is turned on, to be accepted again; **Clone directly** copies no file.

Templates are kept in the workspace's `.sandforge/forge-templates.json`, or in VS Code's storage with no folder open. **Export** on a template's row saves it as a JSON file of its own, and **Import a template** reads one back: a file that is not JSON, larger than 1 MB, or that the template schema refuses is refused, with the part it refused.

## Verify what a run wrote

The results of a run that created records offer **Verify what this run wrote**. It writes nothing: the extension reads back from the org the run wrote to every record the run's entry in **Recent runs** says it created, less those a removal took, and says what it finds once that org has settled — the first reading comes two seconds after you ask, and readings repeat, two seconds apart, until two in a row agree, three at most.

- **Is everything there.** Per object, the records read back, those in the org's recycle bin (read with `queryAll`), and those found in neither, out of your user's sight — hidden by sharing, or emptied from the bin — which are never counted as deleted.
- **Do the links hold.** On twenty records of each object, every lookup the run set from a record it mapped is read and compared with the id that record got in the target: the account a contact was cloned under, or an account the target already held that the run linked to. What each record pointed at is read in the org the run read from, which the run's entry keeps; a lookup the run was told to leave out, or wrote rows again without because the target refused it, is not judged. Two the target explains are counted apart, never as broken: a lookup a lookup filter of the target refused, which the run left empty and kept by record — **left empty by the target's lookup filter** — and one pointing at a record the user the run wrote as created during the run, which the run did not create — **set by the target's automation**. With only those left, the verdict is verified, and says how many. A run recorded before entries kept that org, or whose source org is no longer registered or cannot be reached, is verified without its lookups, and says so.
- **What changed since the run.** The records modified after the run's last stamp, by the org's clock, with who modified them: a removal keeps them unless you tick **Also remove the records changed since the run, and what was added to them since**. What a removal of the run left on a record is no change.
- **More than the run wrote.** Per object, the records the user the run wrote as created during the run, counted against the run's own read back: more of them — the target's automation, another session writing as that user, or a call written twice — are said with how many, and the verdict is partial. A run whose first write the target did not date is not counted.
- **The verdict.** **Verified** when every record is there, every lookup checked holds, and the run's user created no more records during the run than the run wrote; **Partial** when a record is not there, a lookup points elsewhere or is empty, a part could not be checked, or the target holds more records than the run wrote; **Unstable** when no two readings agreed — a flow or a trigger still writing to the records: verify again once it is done. A record changed since the run lowers nothing on its own. The verdict is kept with the run's entry, and the audit trail (Reports → Audit Trail) records each verification as a **Forge Verification**, with its verdict and its counts — records there, deleted, out of sight and changed, lookups checked and broken — never a record. A simulation wrote nothing, and offers no verification.

## Remove what a run created

The Forge page lists your recent runs under **Recent runs**. A run that created records offers **Remove the records this run created**: it deletes from the org the run wrote to the records that run created, and nothing else. That holds for a run that stopped part way too: one that failed, or that you cancelled, after it had written records is listed as **Failed** or **Cancelled** with the records it had created by then. The audit trail (Reports → Audit Trail) records a run you cancelled as **cancelled** once it had written records or the target had refused one, with its counts, and as **stopped**, under `RUN_CANCELLED`, when it had written none and nothing had failed yet. Its entry counts as **not sent**, per object, the records the cancel kept from the target: the rest of the object it was writing, and the emails that waited for their task. So does the entry of a run that failed before those emails. An object a run skipped whole is named in the entry too, as skipped — because a record it cannot be written without failed, or because the target takes no insert of it while the clone holds records of it: the records the run had read of it count as failed, as they do in its results, and one whose records it never counted is shown as skipped with its record count unknown.

- **What it takes.** The records the run created, as its history entry kept them, each object after the objects whose records point at it — the opportunity a run started from goes before its account and its price book — 200 per call, or, for an object of 10 000 records or more, by Bulk API 2.0 delete jobs of up to 50 000: into the recycle bin as a call sends them, never a hard delete, each record answered as a call answers it, and a job the org does not take, or fails before it deletes anything, sent in calls instead. Before they go, what hangs from them is read 200 records at a time, four reads at once, and a relationship no record of which points anywhere is asked once rather than read for each 200. An order past Draft is set to Draft first, as the org deletes neither an activated order nor its products otherwise; one the removal then keeps, or does not reach, gets its status back, and the result names any it could not give back. A contract past Draft is deleted as it is, and its item prices go with it: the org deletes an activated contract, and a sandbox would not set one back to Draft. A record the org refuses while other records still hang from it is tried again once the rest has gone. A record the run linked to because the target already held it is never taken, and neither is the standard price book or reference data the run matched by name.
- **What it keeps.** A record is kept while records that stay in the org depend on it, since deleting it would take them along: a record from before the run moved under it, or one of the run's records the removal keeps or the org refuses. So is one that a record staying in the org points at through a lookup the org will not let it lose: a price an order line that stays still uses, a standard price that a custom price of its product that stays needs, a selling model option that an active price that stays is sold under. An order past Draft that the removal keeps keeps its products and actions with it, as the org deletes neither under an activated order: they are counted as kept for the order, not sent to be refused. So does an activated contract that stays keep its item prices, which the org will not delete under it. A record modified after the run ended is kept too, and so is one that records added or changed since the run depend on — a task logged on it, a tracked change in its feed, a record a colleague adds while the removal runs — unless you tick **Also remove the records changed since the run, and what was added to them since**. What the org adds in answer to the removal itself, or to an earlier removal of the same run, as the user that removal ran as, holds nothing back. What was created while the run went and not touched since, such as the contact of a person account, goes with its parent, and so does what the platform adds to a cloned record on its own, whenever it adds it: a duplicate rule's report that the record matches others, and a copied file's links. A few objects cannot be read by the record they depend on (a member of a sales engagement list is one): the result names them as not checked, and they go with their parent.
- **Whose clock.** Every date compared is the org's own: the run's span runs from its first record's creation to the last stamp it left, read back from the org as the run ends — from their system stamps where your user may set audit fields in both orgs, as the clone then copies the source's creation dates — and the removal's start is the org's time when it begins. A clock on your machine a few seconds off the org's changes nothing. A run recorded before runs kept those dates, or whose dates could not all be read back, is dated by when it was recorded, read on the org's clock: it ends then, give or take ten seconds, and starts as long before as the run took, or with its first record if that came later.
- **Before it runs.** The confirmation names the target org and the records per object, and what the target runs as they go — per object, the flows, Apex triggers, processes and workflow rules that fire before or after a delete, and those that fire on update as an order past Draft is set back to Draft for its delete — read as it opens, with what could not be read and, for a bypass the user does not hold, the permission set and the command that would assign it, as on the **Automation** tab. You type the org's name to go on. Production Guard judges the delete as it judges every write, and refuses a production org. While it runs, the card that started it — under the run's results or in **Recent runs** — offers **Stop the removal**, also while Production Guard asks, which then starts nothing; the card waits an hour for its answer, and past that says the removal may still be under way rather than offering it again. The removal is listed in Live Operations on the Monitor page too, where **Cancel** stops it the same way: before its next call to the org or its next delete job — a job the org already has is finished first — except the ones that give an order back its status and the reads of what it left on the records it leaves, and it is recorded in the audit trail (Reports → Audit Trail) as a cleanup delete, with its counts per object.
- **Afterwards.** The result says, per object, how many records were deleted, were already gone, were not visible to your user, were kept and why, and were refused, with the org's reason; a refusal does not stop the rest. A removal you cancel part way says, in its result, on the command line and in its audit entry, how many records of each object it never reached, and names each object it never got to with all its records. For an object your user may not delete, a record already gone is counted gone, and only those still in the org refused. It also names, per object, the files attached to the records it deleted that stay in the org — a confirmation the org generated for an order, say: the removal takes only what the run created, and a file loses its link to the record, not its place in the org. Deleted records go to the org's recycle bin. Once records went, whether the removal ended or was cancelled, the run says when, how many every removal deleted or found gone, and what the last one left. A removal that left none of the run's records in the org is not offered again. One that left some — kept for a change since or for records that stay, refused by the org, or not reached before you cancelled it — is followed by **Remove what is left of this run's records**, with or without the records changed since: its confirmation names only the records left, and which removal left them; its result and its audit entry say it picked up where that removal left off; and the run's line then counts what every removal took, a cancelled one's included. A removal that took nothing is offered again too. What a removal wrote to the records it left does not count as a change since the run.
- **What the target's automation created.** A removal takes back what the run wrote, not what the target's flows and triggers created in answer, as the run's user: a task opened for each contact, a feed post, an asset a flow created for each case. The confirmation offers **Sweep first**, unticked: once ticked, it lists per object what the run's user created during the run — from a second before its first write to a minute after its last — that the run did not write, link to or match, in the objects the run wrote, tasks, events, feed items and comments, email messages, notes, case comments, and the objects the target's flows on the run's objects create, with a few names of each on demand; it says which flows it could not read and the Apex triggers on those objects, whose creations it cannot tell, and what it could not look at. The sweep runs before the run's records go: a record the automation created under one of them after the run's last write — a task an asynchronous path opened — would otherwise keep that record back as one that stays; it runs once the removal has read the run's records, so that one a roll-up summary restamps as the sweep deletes its child is not kept as changed since the run; Cancel during the sweep stops the removal too; Production Guard judges its deletes as the removal's; a record someone changed since the run stays unless you include what changed; children go before their parents, and **Cancel** stops it between two calls. It is refused, and deletes nothing, when the run's user created records in that window on objects neither the run nor the automation reaches — work done by hand, likely, which it could not tell from the automation's. A run whose records are all removed already offers **Take back what the target's automation created** on its own, when the target dated its writes; a run under **Older runs** keeps no id map, and offers no sweep. The result says what the sweep found, deleted, kept and had refused per object, the run says when it was swept and what it took, and the audit trail records it beside the removal, as a cleanup delete with a sweep detail.
- **Records out of reach.** A call whose answer never came back — a timeout, a connection cut once the request was out — may have written its records under ids the run never learned. They count as failed and are never sent again; the run's results and its audit entry count them per object as maybe in the target, and the removal's result says how many it cannot reach.
- **Records it cannot see.** A record of the run that no query finds when the removal begins is looked for in the org's recycle bin: there, it counts as already gone; nowhere, it counts as **not visible to this user**, never as removed — sharing or an owner whose records your user does not reach can hide it, and a record deleted for good, or emptied from the bin, is not there either. The removal then ends partial, and the run is offered again for those records, to a user who sees them.
- **Past the last twenty runs.** **Recent runs** lists the last twenty. A run past them whose records are still in the org is listed under **Older runs**, with the records left to remove and the org, and offers the same removal. What that takes is kept apart from the history, in the extension's own storage: per run, the ids of the records it created, its dates and what its removals left — never a value of a record — up to 4 MB, some 200 000 records; past that, the oldest runs' go first, and the latest run's is always kept. A run whose records were all removed is no longer kept there.
- **Runs of more than 2 000 records.** A run that maps more records keeps their ids in its journal (below), not in the history, which VS Code rewrites whole at every change: its entry, its plan under **Older runs** and its results count the records per object, and the removal, its confirmation, **Verify**, a retry and **Save Id map (CSV)** read the ids from the journal, which stays as long as the run is listed. Its results say where its ids are instead of listing them. A removal that leaves some of its records keeps what it left beside the journal. Should the journal be gone — the extension's storage cleared — the run says so, and offers none of them.
- **Runs a rewind took back.** A checkpoint's rewind that took back what a run created marks it under **Recent runs** and **Older runs**: rewound on a date to the checkpoint, in part when the run wrote as the checkpoint was taken or as the rewind ran, undone once an Undo brought its records back, and the objects it created records of that the checkpoint did not hold. Its removal then counts what the rewind deleted as already gone: see [Rewound runs in the histories](modules/checkpoint.md#rewound-runs-in-the-histories).
- **Runs from before.** A run recorded before runs kept what they created says so and offers no removal. `sandforge-cleanup` ([quickstart](forge-quickstart.md#from-the-command-line)) remains for those.
- **Said before the run.** Review's **Automation** tab says which objects the run writes may refuse a removal of its records: a record-triggered Flow that runs before a delete, an Apex trigger on a delete — one a managed package installed, which no one in the org can change, named apart — and the orders and contracts whose records, once activated, lock the records under them. When the run asks about what fires as it inserts, that question says it too; a run **Clone directly** started, which never shows Review, asks about them alone when nothing else is asked.

## Resume a run that stopped

Every clone that writes keeps a journal of what it writes as it goes — the
ids of the records it created and linked to, put on disk as each call's
answer comes back, where each object's read stood, the lookups and statuses
it still owed, and those it filled in; and, before each insert or upsert call
goes — a parent it copies from outside the clone and a file included — the
source ids of its rows with a fingerprint of what each writes, an upsert's
row with one of the external id value it matches on, a file's by its title, its
size and its checksum, which holds none of it, and the lookups each row goes
in without; never a value of a record — in the extension's own storage. One that stopped before its end — you cancelled it,
it failed past its first objects, or VS Code closed under it — offers
**Resume where it stopped** on its results, **Resume** under **Recent runs**,
and **Resume** in Live Operations while it is listed there: the clone runs
again as it was set up — a clone of whole tables reads each object after the
last record it wrote, a clone of one record reads its records again and
links to those it wrote — the lookups and statuses it still owed are filled
in, and nothing it wrote is written again. A call the journal names no answer
of — VS Code closed, or the process was killed, while it was under way — is
looked for in the target first: the records the run's user created as the run
stopped that the journal does not name, matched to the call's rows by their
fingerprints and the order the call sent them in. A row found is linked to,
given the lookups it went in without and nothing more — an account it went in
with is not written to again — and removed with the run's records; a row the target
may hold already — more records like it than rows, or a record left unmatched
beside it that the target's automation may have changed as it saved it — is
not written without your word: the confirmation before the run writes says how
many of each object, and **Execute** writes them all the same, each then
perhaps there twice. Its lines say the records it links to were written
before the run stopped. A run VS Code closed under is listed
under **Recent runs** as interrupted, with what it created, removable from
there: its removal looks for the call it had under way first, as a resume
does, and takes back what it finds; a row the target may hold that the
journal does not name stays, and the removal's result counts it among the
records it cannot reach. Only a run's first removal looks for such a call: a
later one says how many calls it did not look for again. An upsert call is
looked for the same way, by the value of the external id it matches on: a
record of the window carrying a row's value is the one the row created, linked
to and removed with the run's records; a row none carries wrote over a record
the target held before the run, which stays, or wrote nothing. Rows sent by
upsert in a journal kept before upsert calls were are not looked for, and the
result says how many of the records it cannot reach they are. Such a run is dated, for its removal and its
**Verify**, by when the target created the first and the last records its
journal names, not by when it began. Resume is refused, writing nothing, when the org the run wrote to was
refreshed or replaced since, or is no longer registered; when the clone on
the page, or `sandforge.forge.maxRecordsPerObject`, changed since it stopped;
and when its records were removed, or it was resumed already. Each part is a
run of the history of its own, with what it created and its own removal; what
one part's removal makes the org date anew among the other parts' records —
the opportunity a resumed part wrote a contact role under, once the role is
deleted — is kept on those parts, the history listing them or not (older runs
are found from the plans kept of them and from the run's journal), and their
removal takes it as the run's doing, not as a change since. A record someone
else changed stays a change.
The clone command does the same with `--resume`.

## The run's audit entry

Every run of the panel that writes, or that a check stops before it writes, is listed in Reports → Audit Trail; so is each rehearsal, under an entry of its own, `forge_rehearse` ([above](#rehearse-a-run)). Beside what it did per object, a Forge run's entry says how it was set up and let through, in words and counts, never a value of a record:

- whether it anonymized, and whether it neutralized email addresses and phone numbers or kept them as read — said of a run stopped before it wrote too;
- **Review skipped** for a run **Clone directly** sent;
- a simulation or a rehearsal of the same case — the same orgs, the same record or query, the same objects discovered, whatever was decided since — that ended in the half hour before the run, and how many minutes before;
- what fires as it inserts, and as it updates the records it inserted, as its confirmation put it to you, counted by kind (flows, Apex triggers, processes, workflow rules), with what of it could not be read;
- the questions of its gate you went on from: what fires on insert and update, and the records it was about to write;
- the decisions its configuration held, kind by kind, with the rows each kind changed;
- the user it wrote as: `sha256:` and the first twelve characters of the SHA-256 of that user's username in lower case, never the username. Whoever knows the username can tell it from the entry. The entries of the other modules name their user the same way.

**Export CSV** and **Export JSON**, beside the filters, save the trail as filtered — the module, the org and the action picked — every entry they match, not only the page on screen, up to the 2 000 entries the trail keeps. The CSV has a row per entry and a column per thing it says, every cell quoted, and a cell that would start a formula in a spreadsheet written after a quote mark; the JSON keeps each entry as the trail holds it, with the filters and when the file was made.

## Refusals the run answers itself

A record the target refuses on fields it names — a validation rule's refusal, a restricted picklist's refusal of the record's value, or the lookup filter of a lookup the target lets be empty refusing the record it names — is written again without them; refused again on other fields, it goes again without those too, three rounds at most. A restricted picklist can refuse a value the check before the write let through: a record type never given values of a field takes none of them, while the target's UI API, the one read that answers per record type, lists them all for it. Taken that time, the record counts as created and the records under it link to it; the object's line and the results page say which field it went without, what refused it and why, as does the command line's summary (under `writtenWithoutFields` with `--json`, each field with `refusedBy`), and the audit trail counts such records per object. Once the target has refused a picklist's value under a record type, the records after it holding that value under that record type are sent without it from the start, and counted the same way. A refusal that names no field leaves the record failed, and the Errors panel says so; a refusal of anything else, or a fourth one, leaves it failed too, which the Errors panel shows with what each refusal before it said. A lookup the target requires is never left out: without it, the record would be refused for want of it.

A write the target never got — no connection, no address for its host, the org unavailable — is sent again after a short wait, three times at most, and so is a record the target could not lock. One whose answer was lost once it was sent is never sent again, since the target may have written its records: the object stops there, and its sample says the target may hold them, and that removing the run's records does not reach them.

## The command line

The [quickstart](forge-quickstart.md#from-the-command-line) gives the checkout the clone and cleanup scripts run from, and a dry run, a run, its removal and a cleanup to copy. What follows is every other thing the clone command does; `--help` lists its flags, and [Command line & CI](../ci-examples/README.md) the eight other scripts.

`--object <ApiName>`, repeated, clones whole tables in place of a record, as the wizard runs a query: each `--where <condition>` (SOQL, written without `WHERE`) filters the `--object` before it, the first object is where discovery starts, and each other must be in its graph (`--depth`, `--max-nodes`) — a parent one of them points at, or a child that hangs from one. Every other object discovery reaches is left out, so no table you did not name is read. The executor is handed what the wizard's orchestrator hands it for the same configuration: each table is read with the org's cursor in the order of its ids and written a page at a time, parents first and their children's lookups given the records the run created, so the run holds one page of rows whatever a table holds, and its journal keeps what it wrote as it goes; `--resume` reads each table after the last record the run wrote. A lookup at a user or a queue the target holds no record of — the owner, between two orgs that do not share their users — goes empty and the platform fills it, the owner with the user the run writes as, which the object's line says; between two sandboxes of one production the owner is kept. With `--upsert`, every page of a table goes by one external id: before its first page the clone reads the id and the external ids of every row it reads of the table, and keeps the first whose value each row holds and no two share, as a clone of a record picks it over all the rows it writes; a page whose rows as written repeat a value an earlier page sent, or leave one empty, is inserted. A run that copies files reads each table whole. `--dry-run`, `--verify`, `--remove`, `--summary`, `--audit` and the gates go as for a record, and the summary names the tables (`objects`) where a clone of a record names it (`record`). `--object` does not go with `--record`, `--expand-orphans` or `--rehearse`; with `--template`, the template's choices go with the tables, its record or query aside, and one that brings orphan parents is refused as `--expand-orphans` is.

```bash
pnpm exec tsx packages/extension/cli/sandforge-clone.ts \
  --object Account --where "Industry = 'Energy'" \
  --object Contact --where "Account.Industry = 'Energy'" \
  --source MY-PARTIAL-COPY --target MY-DEV \
  --depth direct --max-total 20000 --dry-run
```

Before it reads a row, the clone prints what the target runs on the objects it writes, as the Review screen's **Automation** tab says it ([above](#what-the-target-runs-as-the-clone-writes)): per object and write, the active record-triggered flows, Apex triggers, processes and workflow rules, `SENDS MESSAGES` on what sends emails, notifications, outbound or text messages, and `then after commit:` before what runs once the save is committed; the assignment rule and whether the run applies it, the duplicate rules; the custom permissions and settings that keep a flow quiet, and whether the user the run writes as holds them; and what could not be read. When a flow, a trigger, a process or a workflow rule fires as the clone inserts its records, or as it updates those it writes a second time — as the wizard's confirmation counts them ([above](#before-the-run-writes)), and every object it writes under `--upsert`, which writes over a record the target holds — or one of them could not be read, a run that writes stops there, exits `1` and names them, unless you add `--accept-automation`, which covers both: the wizard asks, and the command has no one to ask. For a bypass the user does not hold, the lines and the refusal name the smallest permission set that holds it and print the `sf org assign permset` command that assigns it to the user the command writes as; the command never runs it. Its writes keep the target's assignment rules off unless `--apply-assignment-rules` is given. A `--dry-run` reads it too, says what a real run would need, and adds no other request; `--list-objects` stops before it. The read's requests — the parts and the start conditions and definitions above — are its own, not counted among the run's calls. A `reversibility:` line then says which objects the run writes may refuse a removal of its records (`--remove`), as the Automation tab says it ([above](#remove-what-a-run-created)): a flow before a delete, an Apex trigger on one, a managed package's apart, and records that lock once activated — or that none was found; with `--json`, under `removalRisks`.

Once every row is read and before the first is written, the clone prints the records it is about to write per object, the data storage they take by the sizes the wizard uses ([above](#before-the-run-writes)) and what the target has left. Past `--max-total` records in all (10 000 by default; `--max` caps each object) or past what the target has left, it writes nothing and exits `1`. A target that will not say what it has left is said, and the clone goes on. So are the emails the target's flows send as the records go in, against the daily limits they count against — on an org held to the 15 single emails a day of a Developer Edition, its email alerts count against the single emails too, as Seed counts them, and the line says so: past what is left the clone writes nothing and exits `1`, as a flow that sends in the save would refuse each record past it and the org's own emails would stop for the day. Emails that were not counted, because what sends them could not be read — a flow a package installed among them, which the target lets no one read — are said on an `emails: not counted, … could not be read` line, as `sandforge-sync` and `sandforge-autopilot` say them, and refuse nothing: what fires and could not be read already stops, as said above, a run without `--accept-automation`. A `--dry-run` prints the same, and what would stop a real run there; the read of the target's limits is one of the run's calls.

Then the clone prints what the target holds against the rows, read from its metadata as Review reads it ([above](#what-the-target-runs-as-the-clone-writes)): per object, each validation rule and what keeps it quiet, each duplicate rule and whether it blocks an insert, each field only the target requires that the run does not write, each lookup filter of a lookup it writes, with `BLOCKING`, `warning` or `info`; the daily API requests left against those the run takes; what could not be read, and the requests the read cost. It stops nothing, on a dry run as on a real one.

A line below it says what that automation will find in the records: their email addresses and phone numbers neutralized before writing, as in the wizard ([above](#emails-and-phone-numbers)), or written as read under `--keep-contact-points`. The summary says how many values of which fields went neutralized — on a `--dry-run`, would — and with `--json` it is under `result.contactPoints`: `neutralized`, the `fields` with their `values`, the `values` in all, and `numbersExhausted`, the phone numbers left out once the range was spent, when there were any. With `--upsert`, the external ids that hold an email address or a phone number are named before anything is written, under `upsert keys:` (`neutralizedUpsertKeys` with `--json`): written neutralized, such a key matches no record of the target holding the real address or number, and the run creates one beside it; `--keep-contact-points` matches them.

The target of a clone, and of a removal, must be a sandbox or a Developer Edition org — a Trailhead playground is one: the command reads the org's Organization record, `IsSandbox` and, for an org that is not a sandbox, its edition, and refuses any other org, one that does not say its edition included, before it writes or deletes anything. The wizard refuses such an org too, before it reads anything. `--dry-run` and `--list-objects` only read, and run against any org.

With `--json`, the clone prints its summary as JSON, and stdout carries the JSON alone: every other line goes to stderr, so `> clone-summary.json` or a pipe to `jq` reads it whole. `targetOrgId` names the org the run wrote to by its own id, and `finishedAt` says when the run ended. `targetAutomation` holds what the target runs on the objects the run writes, read before it: per object, its `flows` (each with its `timing`, the writes it `startsOn`, whether its start `condition` was read, the `permissions` it names — `bypass: true` for one that keeps the flow quiet, `held` for whether the user the run writes as holds it, `where: "decision"` for one its first Decision tests — its `switches`, the `paths` that run after commit and the `messages` it sends), its `triggers` with their `events`, its `processes` and `workflowRules` in the shape of a flow, its `assignmentRules` and its `duplicateRules`; `unread` names what could not be read and why, `conditionsNotRead` and `definitionsNotRead` what the bounds left unread, `conditionsNotReadOn` on which objects, and `requests` what the read cost. `targetGaps` holds what the target holds against the rows, read before the run: each of its `gaps` with its `kind`, `severity`, `objectApiName`, `field`, `detail` and the `decisions` it allows, `unread` with what could not be read and why, and `requests`. `applyAssignmentRules` says whether the run's writes let the target's assignment rules apply. `remapTable` maps each source Id to its target Id; `existingSourceIds` names the rows the target already held (linked to, or matched by name) and `updatedSourceIds` the rows `--upsert` wrote over, so every other row of the table is a record the run created. A `--dry-run` creates nothing: it goes through the write stage as the wizard's **Simulate** does ([above](#simulate-a-run)), what it would insert is counted in `wouldInsertCount`, `successCount` stays at 0, and `gaps` lists what the target would refuse or change, each with its `kind`, `severity`, `rows` and the decisions it takes, as the text summary's gap lines do. `decisionsApplied` says which decisions the run applied and to how many records, and `mayHaveBeenWritten` names, per object, the records of a call whose answer never came back: they may be in the target, and `--remove` cannot reach them, which its result says. `readByObject` gives, per object, the rows the run read to clone, where `--list-objects` counts each whole table. `cappedObjects` gives the cap of `--max` (`perObject`) and the `objects` whose read stopped at it with rows left in the source, which the run did not clone, as the text summary's `stopped at` lines name them; it is absent when no read reached the cap. `truncatedObjects` gives the ceiling of `--max-records-per-object` (`perObject`) and the `objects` whose read was cut at it with rows left in the source, as the text summary's `TRUNCATED at` lines name them; it is absent when no read was cut. With `--list-objects`, `--json` prints the objects of the graph instead, and nothing is read past discovery: `objects` gives each one's `recordCount`, its `depth` from the record and whether it is `included`, and `graph.truncated` says whether discovery stopped at its cap before it had walked everything, the cue to raise `--max-nodes`. `failedReads` names the objects whose read failed: the clone never learned how many of their rows it held, so `failedCount` does not count them, but each is a failure of the run, for the exit code below as for the text summary's `failed:` line, which names them. An entry of `errors` carries `referenceData: true` for the reference data the target holds no match for by name, counted neither written nor failed, and `skipped: true` for an object the run skipped whole, whose `failedCount` is none when it never learned how many rows it held. A `--dry-run` adds `adminChanges`, the list Review's **For the target's admin** gives ([above](#gaps-and-their-decisions)), from what the target's metadata says and what the simulation found row by row: per object and record type, each `change` with its field, value and rows, the gap it answers (`gapId`) and its step in Setup (`setup`); the clone makes none of them. A `--dry-run` adds `writePlan` too, what its gate counted as the write would have begun -- per object the `rows` and their `storageBytes`, the `emails` they send where they send some, and in all the `totalRows` that `--max-total` holds a run to, with `emailsUncounted`, why some emails were not counted, when what sends them could not be read -- and `wouldBeRefused`, each refusal a real run would meet: a pipeline that holds the run to its dry run gives it that count as `--max-total`, so a scope that widened since is refused, not written.

`--summary <file>` writes that summary to a file as the run goes: after each object it ends, with what the run has created so far and `"running": true`, then whole once the run ends. Ctrl-C stops a clone between two calls to the org, as **Abort** does in the wizard, through the same stop: it writes what the run had created by then, with `"interrupted": true` — to the `--summary` file, and on stdout with `--json` — prints it, and exits `130`; a second Ctrl-C ends the process at once. Pressed after discovery and before the run writes — as it reads what the target runs, its record types or its row counts — it stops the clone there: nothing written, no summary, a journal begun for it let go, exit `130`. A run that fails part way writes what it had created, with its `error`. A process killed outright leaves the file as the last object it ended wrote it, and the journal goes further: written call by call, it is what `--remove` and `--verify` read the summary's ids from whenever the summary names it and it is there, the summary's own ids standing when it is gone. `--remove` takes the run back from any of these. A `--summary` file already there is refused before anything runs, as it may be an earlier run's summary, and `--summary` does not go with `--list-objects` or `--rehearse`, which create nothing to take back.

Every clone that writes keeps a journal of it as it goes, in `~/.sandforge/forge-runs/` (`SANDFORGE_JOURNAL_DIR` names another directory), and says where as it starts: what the run created and linked to, where each object's read stood, the lookups and statuses it still owed — ids only. `--resume <journal>`, or the run id the journal is named by, takes up where it stopped a run that did not end — a Ctrl-C, a failure, a process killed outright: each record that run wrote is linked to and never written again, the lookups and statuses it still owed are given, and the rest is written. An insert call under way when the process was killed — the org committed it, its answer never reached the journal — is looked for in the target first, as the wizard's resume looks for it ([above](#resume-a-run-that-stopped)), and the command says what it found, what it writes and what may already be there; when rows may already be there, it stops before it writes anything (exit `2`), unless `--write-uncertain` tells it to write them all the same, each then perhaps there twice. `--remove` looks for such a call too before it plans the removal, and takes back what it finds; a row the target may hold that the journal does not name stays, and `--sweep-list` shows what the run's user created in the run's window. Give the same record or tables, orgs, depth, choices and flags it ran with: a run set up otherwise, one that wrote to another org, and one that ended are refused, writing nothing (exit `2`). The summary names the journal (`journal`) and the part of it the run is (`part`). `--remove <journal>` and `--verify <journal>` take every part of a run as one — the run and each time it was taken up, a part a killed process cut short included. Past 50 000 records, the summary counts them and keeps their ids in the journal (`result.remapInJournal`), which `--remove` and `--verify` read them from.

`--remove <file>` takes a run back from the summary it printed with `--json`, saved to a file, with the removal the wizard runs from **Recent runs**: the records the run created (`createdByObject`), each object after the objects whose records point at it, never a record the target already held, whether the run linked to it, matched it by name or wrote over it with `--upsert`, and a record kept while records that stay in the org depend on it. A record changed since the run, and one that records added since depend on, stays unless you add `--include-changed`. Every date compared is the target's: the run's span is the one it read back as it ended (`writtenBetween`), and a run the target did not date is dated by when it ended (`finishedAt`). Give `--target` the org the run wrote to, under any alias: the summary names it by its id, and another org is refused before anything is deleted. A dry run's summary is refused, as the dry run created nothing, and so is a file that is not a summary of the command, or whose ids are not Salesforce ids or whose object names are not API names, and one printed before the summary said which records the run created, for which `sandforge-cleanup` remains. Before it deletes, the removal says what it takes per object and what stays, and what the target runs as the records go — per object, what fires before or after a delete, and what fires on update as an order past Draft is set back to Draft for its delete — and deletes nothing when any of it fires, or could not be read, unless you add `--accept-automation`; for a bypass the user does not hold, it names the permission set and prints the command that would assign it. Afterwards, per object, how many records were deleted, were already gone, were not visible to the user it runs as — found neither in the org nor in its recycle bin, never counted as removed (`notVisible`) — were kept as changed since the run, were kept for the records that stay and which, and were refused, with the org's words, and the files attached to the deleted records that stay in the org. With `--json` that goes under `result.objects`, and every other line to stderr. Ctrl-C stops the removal before its next call to the org, and an order it had set to Draft gets its status back.

`--remove <file> --preview` says what that removal would do, and does nothing: it reads the run's records as the removal reads them before its first delete, and prints per object those it would delete, those gone already, those changed since the run and who changed them, those it could not see, and what a removal run now would be refused for -- a production org, the target's automation without `--accept-automation`, objects the user may not delete without `--leave-undeletable`. It writes nothing, to the org, to the run's journal or beside the summary, and asks nothing; with `--json` it prints that as JSON (`action: "remove-preview"`). It does not go with `--sweep`, `--sweep-list` or `--audit`. A removal takes no `--dry-run`: one that did not read it would delete for real.

A removal that wrote to the org keeps what it left on the records it did not delete, the records of the run it has not taken, and when it ran, in a file beside the summary — `clone-summary.removals.json` for `clone-summary.json` — and a second `--remove` of the same summary reads it, as the wizard reads a run's history: what the first removal wrote to a record it left, a status given back or an amount its deleted children changed, is no change since the run. Keep the file with the summary; with `--json` the removal names it under `removalsFile`. A removal that cannot write it says so, and the next one may then keep such a record as changed since the run, which `--include-changed` takes. A file of that name the command did not write is never overwritten: the removal refuses to start until it is moved, as it refuses one whose ids or dates are not what they should be, and it reads nothing from the file of another run saved there under the same name. A second removal sets out to take only what the earlier ones left, and says how many records they removed (`removedEarlier` with `--json`); with nothing left, it says so and exits `0` without contacting the org, unless it was asked to sweep. A file written before removals kept what they left has the second removal set out to take every record the run created, and find what the first deleted already gone.

`--sweep` precedes the removal with the sweep the wizard's confirmation offers ([above](#remove-what-a-run-created)): once the removal is said and what the target runs as its records go is accepted, and before the run's records go, it deletes what the run's user created during the run that the summary's id map does not hold, in the objects the run wrote, the objects the platform and its automation commonly fill beside a record, and the objects the target's flows create. It prints per object what it found, with a few names, before its first delete, then what became of it; with `--json`, under `result.sweep`. It runs alone when earlier removals took every record of the run, and is refused, deleting nothing, when the run's user created records in the run's window on objects neither the run nor the automation reaches; a summary taken from a journal alone is dated by the first and the last record the journal says the run created, as the target dated them, and a run whose summary has no `writtenBetween` and whose window cannot be read so is not swept, a Ctrl-C during the sweep stops the removal too, and the removal reads the run's records before the sweep deletes, so that one a roll-up summary restamps then is not kept as changed since the run. `--sweep-list` lists what `--sweep` would delete and deletes nothing, the run's records included; with `--json`, under `listing`. What the sweeps took is kept in the removals file (`sweep`), and `--audit` records each sweep as a cleanup delete with a sweep detail. A removal that leaves records of the run, or a sweep that is refused or leaves some of what it found, exits `3`. When the user it runs as may not delete the records of an object of the run, as the object's describe says, it names each before its first delete and stops, removing nothing (exit `1`); `--leave-undeletable` removes the rest instead, leaving those with the records they hang from.

`--verify <file>` verifies a run from the summary it printed with `--json`, as **Verify what this run wrote** does in the wizard ([above](#verify-what-a-run-wrote)): it reads back from `--target` every record the run created (`createdByObject`), after a pause and until two readings agree, checks the lookups of twenty records per object against the source records, read in the org the summary's `source` names or the one `--source` names, lists the records changed since the run, dated as `--remove` dates them, what an earlier removal kept beside the summary included, and counts per object the records the run's user created in the run's window: more than the run's own read back — the target's automation, another session writing as that user, or a call written twice — are said, and the verdict is partial. It only reads, from either org, and runs against any org; `--target` must be the org the run wrote to. It prints per object the records there, in the recycle bin and out of sight, the lookups checked and those that do not hold, each with the id it holds and the one the run set, those the target explains apart — left empty by its lookup filter, as the summary's `lookupsLeftEmptyByFilter` names them, or set by its automation during the run — and the records changed since the run; with `--json`, stdout carries `action: "verify"` and the verification under `result`. A lookup the clone left out with `--exclude` reads as one left empty: the summary does not keep that flag. It exits `0` when verified, `3` when partial, `4` when unstable and `1` when it could not run; `2` on a missing or invalid flag, a flag of the clone or of a removal beside it, or a summary it cannot read, a dry run's included.

`--audit <file>` adds the run's entry to an audit trail kept in that file, as the panel adds its own ([above](#the-runs-audit-entry)): a clone's `forge_execute`, with per object what it created, updated and lost, the two orgs by their own ids and their aliases, the user as `sha256:` and twelve characters, and how it was set up — its anonymization and contact points, **Review skipped** as no Review screen came before it, what fires as it inserts and updates, what `--accept-automation` let through, the decisions its choices held. A clone refused before it wrote is recorded as stopped, under `PRODUCTION_TARGET`, `AUTOMATION_NOT_ACCEPTED`, `MAX_TOTAL_EXCEEDED` or `STORAGE_EXCEEDED`; one Ctrl-C stopped as the panel records a run its Stop stopped: cancelled once it wrote, stopped under `ABORTED_BEFORE_START` before the executor had it, under `RUN_CANCELLED` once it had it and before it wrote. A removal adds a `cleanup_delete`, a verification a `forge_verify`. A dry run, `--list-objects` and `--rehearse` write nothing, and add nothing. The file is a JSON store each run adds to, which the panel's own trail is kept in; one there the command cannot add to is refused, exit `2`, before any org is contacted. Without the flag, the command keeps no entry.

`--config <file.json>` takes the run's choices from a file: a subset of a Forge configuration holding the decisions taken on Review's **Gaps** tab (`picklistValueMappings`, `recordTypeMappings`, `defaultValues`, `truncateFields`, `skippedRows`, `ignoredGaps`), the fields and objects left out (`fieldExclusions`, `excludedObjects`), the filters (`objectSoqlFilters`) and the mappings (`ownerMappings`, `fieldMappings`). It is checked as the wizard checks a run's configuration, and a key it does not take — a depth, a cap — is refused rather than ignored, as each has its flag. `--template <file.json>` takes a template the **Template** tab exported ([above](#templates)): the same choices, and its depth, record cap, object cap, anonymization — methods and fields — contact points, orphan parents and assignment rules, each unless its flag is given; its record is cloned when `--record` is not given, and a template of a query needs `--record`, or the tables of `--object`. The flags win over the file: their exclusions are added to its own, their filters and mappings replace its own for the same object, user or field. `--config` and `--template` do not go together. Before discovery the clone prints the choices it runs with and each decision, and its summary counts those it applied with the records each changed; with `--json` they are under `choices` and `result.decisionsApplied`. A `skippedRows` entry whose gap does not offer **Hold back these rows** — a dependent value's, a rule's, a gap of another object — holds back nothing, and its line says it is ignored, and why.

`--exclude-object <object>` leaves an object out of the clone, whether discovery reached it or the run would add it past `--max-nodes` — a line's price, an order's items. The records that cannot be written without one of its records are held back and named in the summary's errors, and an order past Draft left with no item stays a draft, said so.

`--rehearse` rehearses the clone instead of writing it, as Review's **Rehearse** does ([above](#rehearse-a-run)): it reads and prepares every row, prints the records it creates, the updates it makes of them and the composite calls it costs, creates them in the target in calls each rolled back whole, and prints each refusal — its status code, its field, its rows, an update's apart — and what it could not judge, then exits `0` whatever was refused; nothing stays in the target. With `--json`, stdout carries `action: "rehearse"`, the graph, `targetAutomation` and the verdicts under `rehearsal`: its `gaps`, `rows`, `sampled`, `judged`, `passed`, `notJudged` and `notJudgedWhy`, `updates`, `updatesJudged`, `updatesPassed` and `updatesNotRehearsed`, `calls` and `plannedCalls`. It is refused against a production org, and, like a real run, without `--accept-automation` when the target runs automation on insert: the target's automation runs inside each call. It does not go with `--dry-run`, `--upsert`, `--files`, `--remap-csv` or `--list-objects`.

`--files` copies the files of the cloned records, as the wizard's option does ([above](#copy-the-files-of-the-cloned-records)); `--max-file-size <MB>` sets the largest file copied, from 1 to 35 (default 10). With `--anonymize`, `--files` also needs `--files-as-is`, which accepts that the files are copied as they are. The summary counts the files per object, lists every file left out with why, and a `--dry-run` lists what it would copy and the size; with `--json` it is all under `files`. Whatever the flags, the summary names per object the fields left empty because they hold a file's content, under `fileContentFieldsLeftOut` with `--json`, the encrypted fields left out because the user the source is read as reads them masked, under `encryptedFieldsLeftOut`, and the picklist values replaced or left out because the target would refuse them, per object and field with why, under `picklistValuesChanged`.

The clone's exit code is `1` when the run produced **only** failures; when its files do not fit in the target's file storage, that storage could not be read or the files could not all be looked up in the source; when the target is a production org; when the target runs automation as the clone inserts, or could not say what it runs, and `--accept-automation` was not given; when the run would write more than `--max-total` records, more than the target's data storage has left, or more emails than the target has left today (nothing is written in any of these); or when it could not run at all, as with an alias the Salesforce CLI does not know. It is `0` otherwise, and after a `--rehearse` whatever it found refused; a rehearsal exits `1` too when a call was not rolled back. Wire it as a CI gate. A clone Ctrl-C stopped exits `130`, once it has said what it created; a SIGTERM — Jenkins aborting a build, or ending it at its timeout — stops it the same way and exits `143`, a SIGHUP `129`. Once every record is written, a `--remap-csv` file that could not be written — one made at its path during the run — exits `1`, the summary kept and printed first. A removal exits `0` when every record it set out to take went, deleted or already gone, `3` when some stayed in the org, kept or refused, or were not visible to the user it ran as, and `1` when it could not run: the target is a production org, or another org than the one the run wrote to, or the target runs automation as the records go, or could not say what it runs, and `--accept-automation` was not given. Both scripts exit `2` on a missing or invalid flag before any org is contacted: a flag they do not read, a misspelt `--dryrun` among them, and a flag given its value after `=` — `--dry-run=true` is no dry run — are refused, not dropped. For the clone that is a malformed record ID, a `--remap-csv` file outside the working directory, without the `.csv` extension or already there, an unknown `--depth`, a name that is not an API name, a `--max-nodes` or a `--max-total` that is not a whole number of 1 or more, `--files` with `--anonymize` and no `--files-as-is`, a `--max-file-size` outside 1 to 35, `--include-changed` without `--remove`, or `--rehearse` with a flag it does not go with, or a `--summary` file that is already there, or given with `--list-objects` or `--rehearse`, or a `--config` or `--template` file that cannot be read or that the schema refuses, a key `--config` does not take, both of them given, or a template of a query with no `--record`; `--object` with a flag it does not go with, a `--where` with no `--object` before it, a second `--where` for one table, an `--object` named twice, or a `--where` and a `--filter` on the same table; an `--exclude-object` of the record's own object, or of the first table, exits `2` too, once discovery has named that object, and so does an `--object` discovery did not reach from the first. For a removal it is a flag of the clone beside `--remove`, a summary it cannot take a run back from, or a file beside the summary that is not what a removal kept there. For the cleanup it is an alias or object name that is not valid, a `--since` outside the accepted forms, or a `--max` that is not a whole number above 0. The cleanup deletes the records created from the start of the `--since` period (an ISO date from its midnight UTC), refuses a production org as the clone does, exits `1` when an object could not be read or deleted, and `3` when the target refused some of its deletes; `--json` prints per object the records found, deleted and refused.
