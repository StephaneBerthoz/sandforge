# SandForge CI/CD Examples

Ready-to-use CI/CD pipeline configurations for automating what SandForge **actually ships**: no fictional CLI commands.

## What exists (and what doesn't)

SandForge is a **VSCode extension**: there is no `sandforge` binary and no `bin` entry in `package.json`. What runs headless is eleven TypeScript scripts in `packages/extension/cli/`, run with `tsx` from the **repository root** of a checkout of this repo; the other files there (`sfSession.ts`, `panelHost.ts`, `fileConfigStore.ts`, `commandLineGuard.ts`, `backupStore.ts`, `targetKind.ts`, `commandLine.ts`, `prompt.ts`, `stopSignals.ts`, `exitCodes.ts`) are what the scripts share, and `forgeHost.ts` hosts Forge's panel path headless for live checks. The pipelines run the clone; the cleanup deletes what a user created in a window of time; each of the other nine drives a module the way its page in the extension does:

Every script:

- is invoked as `pnpm exec tsx packages/extension/cli/sandforge-<name>.ts ...`, and lists its flags with `--help`
- delegates org authentication to the **Salesforce CLI**: `sf org display --target-org <alias>` for the username and the instance, then `sf org auth show-access-token`, which refreshes the stored session, for the token. So `sf` must be installed and the orgs must be authenticated (in CI: `sf org login jwt`, or `sf org login sfdxurl` with an `SFDX_AUTH_URL_*` secret; see [Configure credentials](#1-configure-credentials))
- requires `pnpm install` + `pnpm build:shared` to have run first (it imports `@sandforge/shared` and extension sources)
- refuses, with exit code `2` and before any org is reached, a flag it does not read, a flag given its value after `=`, and a flag given no value — another flag, or nothing, after it: `--dry-run=true` is not a dry run — give `--dry-run`, or leave it out — `--target=ci-target` is written `--target ci-target`, and `--target $TARGET --dry-run` with `TARGET` empty is refused, not taken for an org named `--dry-run`
- writes to, and deletes from, sandboxes, scratch orgs and Developer Edition orgs only: the clone, the cleanup, Sync, Seed, Autopilot, a backup restore, DataOps and a Frozen load or removal refuse a production target before anything is written or deleted, with exit code `1`, as the panel's Production Guard does when nobody confirms. No flag lifts it. What only reads runs against any org: `--dry-run`, Autopilot's `--plan-only`, a backup snapshot, Compare and Monitor. The checkpoint's refusal goes further: `take`, `preview`, `rewind` and `undo` refuse a production org before they read anything, with exit code `1`, and `list` and `delete` never contact an org
- asks before a write only where a terminal answers: without `--yes`, a backup restore, a DataOps run, a Frozen load or removal, and a checkpoint's `rewind`, `undo` or `delete` run with no terminal — a CI step — stop at their question with exit code `2`, having written nothing. A checkpoint's `rewind` and `undo` ask for the org's alias, typed, and with `--yes` need the checkpoint named by its id or its name: `latest` is refused, exit `2`
- prints its JSON alone on stdout with `--json`, every other line on stderr, an early end included: Frozen says `"ended": true` then, and `sandforge-backup --list --json` lists the snapshots with their ids and the org each was taken of, from the store alone, without contacting an org

The clone, the cleanup, Sync, Seed and DataOps take `--dry-run`, and so do Frozen's `load` step and the checkpoint's `rewind`: the pipelines default the clone to it, so nothing is written unless you opt in. Autopilot's `--plan-only` scans and plans, and writes nothing; so does the checkpoint's `preview`.

A run of the clone, of Sync or of Seed is taken back with `--remove` and the summary it printed with `--json`, saved to a file, or from what the run keeps as it writes, whatever became of it: the clone's journal, Sync's and Seed's run file, under the folder `SANDFORGE_JOURNAL_DIR` names (`~/.sandforge` by default), each named as the run begins (on stderr with `--json`). A Frozen load is taken back with its `remove` step. A checkpoint's `rewind` is taken back with `undo`, for 15 days, from the journal it keeps beside the checkpoint. An Autopilot run cannot be taken back: nothing keeps what it created. Every flag, exit code and file of the clone is in the [Forge reference](../docs/forge-reference.md#the-command-line).

Compare and Monitor keep their host's state in `compare/` and `monitor/` under the same folder, readable by you alone (`--store` names another). `--store` is not one thing across the scripts: the snapshot folder of the backup and DataOps, the folder a saved Sync configuration is kept in, the state file of Frozen (by default in the `sasDir` its configuration names, or `~/.sandforge-sas`), the host's folder of Compare and Monitor, the store of the checkpoints (by default `checkpoints/` under the same folder, shared with the panel). The org written to is `--org` for the backup, DataOps, Monitor and the checkpoint, and `--target` for the others.

One table for every script, the clone's:

| Code                | Meaning                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `0`                 | The run did what it was asked. A Seed, Sync or Autopilot run the target refused some records of is `0` too, as the clone's is, unless `--fail-on-partial`; a Compare diff is `0` whatever it found, unless `--fail-on-drift`; a checkpoint's `rewind` or `undo` is `0` when the org, read again, matches among the objects and fields compared, and a `preview` whatever it found, unless `--fail-on-change`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `1`                 | It could not start; it was refused before it wrote or deleted anything (a production target, automation without `--accept-automation`, `--max-total`, the target's data storage or daily emails); it produced only failures, or died; a Compare or Monitor request failed or was not answered; an object of the cleanup could not be read or deleted; a Frozen verification is FAILED; a checkpoint's `take`, `rewind` or `undo` was refused before it read or wrote (a user without View All Data and Modify All Data, automation without `--accept-automation`, deletions Undo could not bring back without `--accept-no-undo`, records to make again with new Ids without `--accept-recreate`, more API requests than the org has left today, a checkpoint of the org before a refresh or of an expired scratch org, a take, a rewind or an undo of the org under way), or a `rewind` or `undo` wrote nothing it set out to |

| `3`                 | Partial. A removal left records of the run in the org; `--verify` of the clone or Frozen's `verify` is PARTIAL; a Frozen load completed with errors; a DataOps run left records unmasked, their personal data still in the org; a restore left values as they are; a backup snapshot holds part of an object (`--max-records`); the target refused some of the cleanup's deletes; a Compare validation came back with no success, a component error or a failed test; with `--fail-on-partial`, a Seed, Sync or Autopilot run the target refused records of; with `--fail-on-drift`, a diff found differences; a checkpoint's `rewind` or `undo` left records that still differ, each said with why, fields set aside with `--ignore-field` not counted; with `--fail-on-change`, a checkpoint's `preview` found the org differs; a checkpoint's `delete` kept some of them                                                    |

## Available Examples

| File                  | Platform       | Jobs                                                                                                       |
| --------------------- | -------------- | ---------------------------------------------------------------------------------------------------------- |
| `github-actions.yml`  | GitHub Actions | quality gates → clone and its removal (gated) → VSIX package → Slack notify                                |
| `gitlab-ci.yml`       | GitLab CI      | quality → clone and its removal (rule-gated) → package → Slack notify on any failed job                    |
| `Jenkinsfile`         | Jenkins        | Quality gates → Clone and its removal → Package VSIX, artifact archiving, Slack notify                     |
| `azure-pipelines.yml` | Azure DevOps   | Quality → Clone and its removal (condition-gated) → Package; no Slack step, use Azure DevOps notifications |

Every pipeline implements the same four stages:

1. **Quality gates**: `pnpm validate` — chains `pnpm build:shared` → `pnpm typecheck` → `pnpm lint` → `pnpm test` → `pnpm check:i18n` → `pnpm build`. If you split it into separate stages for per-step reporting, keep `pnpm build:shared` first: the other packages import `@sandforge/shared` from its `dist/`, so a typecheck that runs before it fails on a fresh checkout.
2. **Clone**: `sandforge-clone.ts --dry-run --json --summary clone-summary.json --remap-csv --audit clone-audit.json` against sf-authenticated orgs, its stdout saved to `clone-output.json`, its journal kept in `sandforge-journal/` of the workspace (`SANDFORGE_JOURNAL_DIR`) (skipped unless org secrets and a record Id are configured)
3. **Removal**: `sandforge-clone.ts --remove clone-summary.json` on the target sandbox, off unless you ask for it, and only after a real clone (see [Removal](#removal)). It takes back what that clone created and nothing else: never a record the target already held, and not one changed since the clone.
4. **VSIX package**: `pnpm package`, uploaded/archived as an artifact

The clone's report is kept as an artifact whether the job passed or not:

- `clone-summary.json`, which `--summary` writes as the run goes, after each object it ends, and whole once it ends: what `--remove` takes the run back from. A clone that fails part way, or is stopped, keeps there what it created by then, where its stdout carries no summary
- `clone-output.json`, what the run printed on stdout
- `sandforge-journal/forge-runs/`, the clone's journal: what the run wrote, read and still owes, line by line, ids only. `--remove` takes a run back from it however it ended — killed at the job's timeout included — and `--resume` takes it up. In the runner's home, its default, it went away with a hosted runner
- `remap.csv`, the ids the run gave, and `clone-audit.json`, the audit trail entry of a real clone and of a removal, as the panel's Reports → Audit Trail keeps one (a dry run adds none)
- after a removal, `clone-removal.json` and `clone-summary.removals.json`, what the removal wrote to the records it left, which the next removal of the same summary reads

## Setup

### 1. Configure credentials

The clone stage authenticates via the Salesforce CLI, with an sfdx auth URL per org, as the example pipelines do, or with the JWT bearer flow, which is what to use for CI.

#### sfdx auth URL

Print an org's auth URL with `sf org auth show-sfdx-auth-url --target-org <alias> --json`, which gives it in `result.sfdxAuthUrl`, from an org you logged in to with `sf org login web`. `sf org display --verbose --json`, which this guide used to name, prints `[REDACTED] Use 'sf org auth show-sfdx-auth-url' to view` there in current CLIs: stored as the secret, that sentence fails every `sf org login sfdxurl`. An auth URL carries the refresh token of the person who logged in, and stops working when their session is revoked; a refreshed sandbox is a new org, so log in to it again and make a new one after each refresh.

Store them as secrets:

| Variable               | Description                                                                      |
| ---------------------- | -------------------------------------------------------------------------------- |
| `SFDX_AUTH_URL_SOURCE` | sfdx auth URL of the source org (secret)                                         |
| `SFDX_AUTH_URL_TARGET` | sfdx auth URL of the target sandbox (secret)                                     |
| `SANDFORGE_SF_ORGS`    | Set to `true` to enable the clone stage                                          |
| `SF_CLONE_RECORD_ID`   | Salesforce record Id to clone (15/18-char, e.g. `500...`)                        |
| `SLACK_WEBHOOK_URL`    | (Optional) Slack webhook for failure alerts (GitHub Actions, GitLab CI, Jenkins) |

If `SANDFORGE_SF_ORGS` or `SF_CLONE_RECORD_ID` is not set, the pipelines still run quality gates and the VSIX package; the org-touching stages are skipped.

The login step writes each auth URL to a private temporary directory (`umask 077`, `mktemp -d`) and a `trap` removes it when that shell exits, a failed login included. Keep the whole sequence in one shell step if you edit it: a trap does not outlive the shell that set it, and self-hosted runners and Jenkins agents keep `/tmp` between runs.

#### JWT bearer (recommended for CI)

SandForge's own canary logs in this way (`.github/workflows/canary.yml`), and nothing in it is one person's session. In each org: a connected app, or an External Client App, with OAuth and the JWT bearer flow on, the certificate of a key pair you made, and an integration user the app pre-authorizes (admin-approved users, through a profile or a permission set). Store the private key, the app's consumer key and the username as secrets, and replace the login step with:

```bash
umask 077
key_dir=$(mktemp -d)
trap 'rm -rf "$key_dir"' EXIT
printf '%s\n' "$SF_JWT_KEY" > "$key_dir/server.key"
sf org login jwt --client-id "$SF_TARGET_CLIENT_ID" --jwt-key-file "$key_dir/server.key" \
  --username "$SF_TARGET_USERNAME" --instance-url https://test.salesforce.com --alias ci-target
```

and the same for `ci-source`. The instance URL is `https://test.salesforce.com` for a sandbox, and `https://login.salesforce.com`, or the org's My Domain, for a Developer Edition. The key is written inside the same `umask 077` / `mktemp -d` / `trap` block as an auth URL, for the same reasons.

### 2. Platform-specific instructions

#### GitHub Actions

1. Repository **Settings > Secrets and variables > Actions**: add the two `SFDX_AUTH_URL_*` secrets (+ optional `SLACK_WEBHOOK_URL`)
2. Same page, **Variables** tab: `SANDFORGE_SF_ORGS=true`, `SF_CLONE_RECORD_ID=<id>`
3. Copy `github-actions.yml` to `.github/workflows/sandforge.yml`

#### GitLab CI

1. **Settings > CI/CD > Variables**: add the variables, marking the auth URLs as "Masked"
2. Copy `gitlab-ci.yml` to `.gitlab-ci.yml` in your project root

#### Jenkins

1. **Manage Jenkins > Tools** (Global Tool Configuration on older releases): a NodeJS installation named `Node-24`
2. **Manage Jenkins > Credentials**: create Secret text credentials `sfdx-auth-url-source`, `sfdx-auth-url-target` (+ optional `slack-webhook`)
3. Set `SANDFORGE_SF_ORGS=true` in folder/job environment
4. Copy `Jenkinsfile` to your project root and point a Pipeline job at it
5. Pass `SF_CLONE_RECORD_ID` as a build parameter: the Clone stage runs only when it is set, and the build logs the `ci-source` and `ci-target` aliases out when it ends

#### Azure DevOps

1. **Pipelines > Library > Variable Groups**: create `SandForge-Credentials` with all variables (auth URLs as secrets)
2. Copy `azure-pipelines.yml` to your project root and create a pipeline referencing it

## Customization

### Dry Run Mode

All pipelines default the clone to dry-run (no writes):

- **GitHub Actions**: `workflow_dispatch` input `dry_run` (default `true`)
- **GitLab CI**: `DRY_RUN` variable (default `"true"`)
- **Jenkins**: `DRY_RUN` parameter (default checked)
- **Azure DevOps**: `dryRun` parameter (default `true`)

### Removal

A real clone stays in the sandbox unless you ask for its removal at the end of the job: for test data your own checks use and nothing after them should keep. Put those checks between the clone and the removal, where each pipeline says so:

- **GitHub Actions**: `workflow_dispatch` input `remove_after` (default `false`)
- **GitLab CI**: `REMOVE_AFTER` variable (default `"false"`)
- **Jenkins**: `REMOVE_AFTER` parameter (default unchecked)
- **Azure DevOps**: `removeAfter` parameter (default `false`)

The removal runs only after a real clone: a dry run created nothing, and `--remove` refuses its summary. It is the removal the wizard runs from **Recent runs**: it deletes the records the clone created, children first, and keeps a record the target already held, one changed since the clone (add `--include-changed` when your checks change them), and one that records staying in the org depend on. It exits `3` when it left records of the clone in the org, which fails the job; `clone-removal.json` says per object what became of them.

It deletes nothing, and exits `1`, when the target runs a flow, an Apex trigger, a process or a workflow rule as the records are deleted — before or after a delete — or could not say what it runs: its output names each one. To remove all the same, ask for it:

- **GitHub Actions**: `workflow_dispatch` input `accept_removal_automation` (default `false`)
- **GitLab CI**: `ACCEPT_REMOVAL_AUTOMATION` variable (default `"false"`)
- **Jenkins**: `ACCEPT_REMOVAL_AUTOMATION` parameter (default unchecked)
- **Azure DevOps**: `acceptRemovalAutomation` parameter (default `false`)

To take a run back later, by hand: download the clone report, put `clone-summary.json` (and `clone-summary.removals.json`, if a removal ran) at the root of a checkout, and run `pnpm exec tsx packages/extension/cli/sandforge-clone.ts --remove clone-summary.json --target <alias>` against the org the run wrote to. A removal keeps in `clone-summary.removals.json` what it wrote to the records it left, which the next removal of the same summary reads: keep the two files together. A run of more than 50 000 records keeps their ids in its journal, which the removal reads them from: put the report's `sandforge-journal/` there too, and run the removal with `SANDFORGE_JOURNAL_DIR=sandforge-journal`. So does a run killed before it ended its summary: `--remove sandforge-journal/forge-runs/<journal>` takes it back from its journal.

`sandforge-cleanup.ts` remains for a run whose summary and journal you did not keep, or one printed before the summary said which records the run created. It knows nothing of the clone, and `--since today` selects every record the user created on the target since midnight, whether a clone wrote it or not: preview it with `--dry-run --json`, then narrow the delete with `--objects`. It exits `1` when an object could not be read or deleted, and `3` when the target refused some of its deletes.

### Automation on insert, and volume

A real clone writes nothing when the target runs a record-triggered flow or an Apex trigger as the records are inserted, or could not say what it runs: the job fails with exit code `1`, and the clone's output names each one. To clone all the same — after assigning the custom permission its output names to the CI user, say, or turning that automation off in the sandbox — ask for it:

- **GitHub Actions**: `workflow_dispatch` input `accept_automation` (default `false`)
- **GitLab CI**: `ACCEPT_AUTOMATION` variable (default `"false"`)
- **Jenkins**: `ACCEPT_AUTOMATION` parameter (default unchecked)
- **Azure DevOps**: `acceptAutomation` parameter (default `false`)

A dry run says what fires and goes on. Before its first write, a real clone also refuses a run of more than 10 000 records in all, one whose records take more data storage than the target has left, and one whose records would make the target's automation send more emails than it has left today — on a Developer Edition, 15 single emails a day, its email alerts counted among them — even when its automation is accepted: nothing is written, and the job fails with exit code `1`. Add `--max-total <n>` to the clone call to set another ceiling.

### Rewinding a scratch org between suites

No pipeline here runs `sandforge-checkpoint`; a step of your own does, against a scratch org or a sandbox the job may write to. Take a checkpoint once the org is seeded (`take --org <alias> --name baseline --keep-days 0`), and between two suites rewind it (`rewind --org <alias> --checkpoint baseline --yes`, with `--accept-automation` and `--accept-no-undo` when the org needs them): the org goes back to its seeded state without a new scratch org. Exit `3` marks the org dirty, and exit `4` says something still writes to it. Keep the checkpoints in a folder of the workspace with `SANDFORGE_JOURNAL_DIR`, in a cache only the pipeline reads: they hold the records' values unencrypted. The [Checkpoint & Rewind guide](../docs/modules/checkpoint.md#a-pool-of-scratch-orgs-rewound-between-suites) has the whole sequence.

### Scheduling

Pipelines are scheduled every Monday at 6 AM UTC. Adjust the cron expression to your needs.

### Branch

The triggers name `main`: read it as your repository's default branch and rename it if yours is `master` or anything else.

### pnpm version

No pipeline pins a pnpm version. GitHub Actions' `pnpm/action-setup` and `corepack enable` on the other platforms both take it from the `packageManager` field of the root `package.json`, so the pipelines follow the repository when it moves to a new pnpm release.

### Building only the VSIX

The `package` stage is independent of org credentials: it always runs `pnpm package` (build shared → extension → webview → `vsce package`) and publishes `sandforge.vsix`.

## Security Best Practices

1. **Never commit credentials**: use platform-native secrets management
2. **Rotate sfdx auth URLs** regularly, especially after team changes
3. **Use sandbox-only credentials**: never connect to production orgs in CI/CD
4. **Keep dry-run on by default**: flip it off only for deliberate, reviewed runs
5. **Keep auth URLs off shared disks**: write them only inside the `umask 077` / `mktemp -d` / `trap` block the examples use, never to a fixed path under `/tmp`
6. **Enable audit logging** in your Salesforce orgs to track CI/CD operations
