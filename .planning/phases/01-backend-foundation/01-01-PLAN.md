# Plan 1: Limits Cache + OrgInfo Verification + Job Trend Fix

## Objective

Add a handler-level /limits API cache to MonitorOpsHandler so that within a single 30-second refresh cycle, all three handlers (handleRefresh, handleHealthScore, handleApiUsage) share a single /limits response instead of each making their own API call. Verify that OrgInfoFetcher's existing 5-minute cache is shared across handler invocations (test-only, no code change to OrgInfoFetcher). Fix the single-point defect in OrgTrendAnalyzer.analyzeJobTrend by accumulating job stats history across calls.

## Context

**Limits Cache (PERF-01):** Currently, MonitorOpsHandler makes 3 independent `conn.request('/services/data/.../limits')` calls per refresh cycle: one in handleRefresh (line 104), one in handleHealthScore (line 228), and one in handleApiUsage (line 355). The webview auto-refreshes every 30 seconds. Each call consumes the user's DailyApiRequests limit. The fix is a private Map on MonitorOpsHandler with 30-second TTL that stores the raw response (keyed by orgId), so both handleRefresh (which runs transformLimitsResponse) and handleApiUsage (which reads raw keys) can share it.

**The cache pattern to follow** is exactly what OrgInfoFetcher uses at lines 9-24: `Map<string, { data: T; fetchedAt: number }>` with TTL check `Date.now() - fetchedAt < ttlMs`.

**OrgInfo Verification (PERF-02):** OrgInfoFetcher is instantiated once as a field on MonitorOpsHandler (line 39). Since all monitor messages route through the same handler instance, the 5-minute cache IS already shared. This requirement is verification only -- write a test that calls the handler twice within 5 minutes and asserts the OrgInfoConnection methods are called only once.

**Job Trend Fix (TREND-03):** `OrgTrendAnalyzer.analyzeJobTrend` (lines 74-93) creates a single `TrendDataPoint` from `jobMonitor.getJobStats(orgId).active`. Since `calculateTrend` requires MIN_TREND_POINTS=2, it always returns `{ trend: 'stable', changePercent: 0 }`. The fix: add a `private jobHistory: Map<string, TrendDataPoint[]>` inside OrgTrendAnalyzer that accumulates one data point on each call. After 2+ calls, calculateTrend will produce real trend data. Cap history at 50 entries per org to avoid memory leaks.

**Existing tests that will need updating:**
- `OrgTrendAnalyzer.test.ts` lines 101-113: tests expect single-point returns-stable behavior. After the fix, the first call still returns stable (1 point), but a second call should produce a real trend.
- `MonitorOpsHandler.test.ts`: existing tests mock at module level. New cache tests need more precise mocking of `getJsforceConnection` to return a controlled conn mock.

<action>
Add a private field to MonitorOpsHandler:
```typescript
private readonly limitsCache: Map<string, { data: RawLimitsResponse; fetchedAt: number }> = new Map();
private static readonly LIMITS_CACHE_TTL_MS = 30_000;
```

Create a private method `getOrFetchLimits`:
```typescript
private async getOrFetchLimits(orgId: string, conn: Connection): Promise<RawLimitsResponse> {
  const cached = this.limitsCache.get(orgId);
  if (cached && Date.now() - cached.fetchedAt < MonitorOpsHandler.LIMITS_CACHE_TTL_MS) {
    return cached.data;
  }
  const data = await conn.request(`/services/data/${SF_API_VERSION}/limits`) as RawLimitsResponse;
  this.limitsCache.set(orgId, { data, fetchedAt: Date.now() });
  return data;
}
```

The `conn` parameter type is whatever jsforce returns from `getJsforceConnection`. Use the same pattern as the existing `conn.request` call. If necessary, type the parameter as the return type of `getJsforceConnection` (inspect the import).

Replace the direct `conn.request` calls in these three methods:
1. `handleRefresh` (line 104): replace `const limitsRaw = await conn.request(...)` with `const limitsRaw = await this.getOrFetchLimits(payload.orgId, conn);`
2. `handleHealthScore` (line 228): same replacement
3. `handleApiUsage` (line 355): same replacement

Keep the existing `checkApiLimits` calls after each handler -- they check the conn.limitInfo header which is orthogonal to the cache.

Add JSDoc on `getOrFetchLimits` explaining the 30s TTL and orgId-keyed caching.
</action>
