# Plan 2: Unified Health Scorer with Trend Integration and Linear Interpolation

## Objective

Merge HealthScoreCalculator and OrgHealthScoreCalculator into a single UnifiedHealthScorer class that: (a) uses continuous linear interpolation instead of step-function scoring, (b) integrates real trend data from TrendStorage into each factor's `trend` field, and (c) outputs a `HealthReport` that serves both the HealthScoreCard (via `monitor:data`) and the OrgHealthPanel (via `monitor:health-score:response` after dimension projection). This eliminates the two-calculator redundancy and delivers HEALTH-01, HEALTH-02, and HEALTH-03 in a single coherent unit.

## Context

**Current state (two calculators):**
- `HealthScoreCalculator` (used by MonitorOpsHandler.handleRefresh and handleHealthScore): Takes `ApiLimit[]`, produces `HealthReport`. Covers 5 limits (DailyApiRequests, DataStorageMB, DailySoqlQueries, DailyDmlStatements, DailyAsyncApexExecutions) with step-function scoring. All factor trends are hardcoded to `'stable'`.
- `OrgHealthScoreCalculator` (currently unused in MonitorOpsHandler but tested): Takes limits + orgInfo + codeCoverage + metadataCounts + securitySettings, produces `OrgHealthScoreResult` with 5 dimensions (apiUsage, storageUsage, metadataComplexity, codeCoverage, securitySettings). Also uses step-function scoring.

**The unified scorer must:**
1. Accept limits + optional orgInfo + optional TrendStorage + optional codeCoverage + optional securitySettings
2. Produce `HealthReport` natively (factors, overallScore, overallStatus, summary, topRisks)
3. Use linear interpolation for usage-based scoring (HEALTH-03)
4. Call `TrendStorage.getTrendData(orgId, limitName)` for each limit factor and map `direction` ('up'/'down'/'stable') to `trend` ('degrading'/'improving'/'stable') (HEALTH-02)
5. When trend is 'degrading' (usage rising), apply a penalty to the factor score (e.g., -5 to -15 points depending on changePercent)
6. Include optional metadata/coverage/security dimensions when data is available, with category extensions
7. When optional data is unavailable, skip those dimensions and redistribute their weight (do NOT default to fake scores like 75 or 50)

**Type changes needed in monitor.types.ts:**
- Extend `HealthFactor.category` from `'limits' | 'jobs' | 'storage'` to `'limits' | 'jobs' | 'storage' | 'metadata' | 'coverage' | 'security'`

**Linear interpolation formula (HEALTH-03):**
Replace the step functions. For usage-based scoring (higher usage = worse score):
```
score = Math.max(0, Math.round(100 - usedPercent * 1.0))
```
This maps 0% -> 100, 50% -> 50, 100% -> 0 linearly. If desired, use a piecewise linear with two segments for gentler penalties below 50% and steeper above 70%:
- 0-50% usage: score = 100 - (usedPercent * 0.6)  [100 -> 70]
- 50-100% usage: score = 70 - ((usedPercent - 50) * 1.4)  [70 -> 0]
Either approach is acceptable as long as it is continuous (no point jumps > 5) and monotonically decreasing.

**Trend vocabulary mapping (HEALTH-02):**
TrendData.direction uses 'up' | 'down' | 'stable'. HealthFactor.trend uses 'improving' | 'stable' | 'degrading'. Mapping: up -> degrading (more usage = worse), down -> improving, stable -> stable.

**Trend penalty formula (HEALTH-02):**
When a factor's trend is 'degrading', subtract a penalty proportional to changePercent:
```
penalty = Math.min(15, Math.max(0, Math.abs(changePercent) * 0.5))
adjustedScore = Math.max(0, rawScore - penalty)
```
This caps the penalty at 15 points. A factor trending up 10% gets -5 points. A factor trending up 30%+ gets -15 points.

**MonitorOpsHandler wiring:**
After Plan 01 adds the limits cache, this plan:
1. Replaces `import { HealthScoreCalculator }` with `import { UnifiedHealthScorer }`
2. Changes the `healthCalculator` field type to `UnifiedHealthScorer`
3. Updates the constructor to pass `trendStorage` to `UnifiedHealthScorer`
4. Updates `handleRefresh` to call `this.healthCalculator.calculate(limits, payload.orgId, { orgInfo, trendStorage: this.trendStorage })`
5. Updates `handleHealthScore` to use the unified scorer and keep the existing factor-to-dimension projection at lines 232-238

**Backwards compatibility:**
The `handleHealthScore` method already projects `HealthFactor[]` into `OrgHealthDimension[]` at lines 232-238. This projection must continue to work. The new factors will include additional categories (metadata, coverage, security) when available, which naturally produce additional dimensions.

**Internal implementation:**

1. **Limit factors (weight totaling ~0.85 of the limits portion):**
   Define the same 5 core limit factors as HealthScoreCalculator:
   - DailyApiRequests (weight 0.20), DataStorageMB (weight 0.20), DailySoqlQueries (weight 0.15), DailyDmlStatements (weight 0.15), DailyAsyncApexExecutions (weight 0.15)
   - For each, compute the factor score using `linearUsageScore(usedPercent)` (see below)
   - If trendStorage is provided, call `trendStorage.getTrendData(input.orgId, limitName)` and map the direction to the factor's trend field. Apply trend penalty if degrading.
   - Remaining limits with usedPercent > 0 get equal share of remaining weight (0.15 total), same as current HealthScoreCalculator behavior.

2. **Optional dimensions (only included when data is provided):**
   - Metadata complexity (if metadataCounts or orgInfo with counts): use `complexityScore` function (same as OrgHealthScoreCalculator)
   - Code coverage (if codeCoverage is provided -- NOT defaulted): use `linearCoverageScore(coverage)` where higher coverage = higher score
   - Security settings (if securitySettings is provided -- NOT defaulted): use the same point-based scoring from OrgHealthScoreCalculator.scoreSecuritySettings

   When these optional dimensions are present, redistribute weights proportionally. Base limit weight is 1.0 when no optional dimensions exist. When all 3 optional dimensions are present, limits get 0.55 total weight, metadata 0.15, coverage 0.15, security 0.15. Use a dynamic weight calculation rather than hardcoded tables.

3. **Linear scoring functions (HEALTH-03):**

   `linearUsageScore(usedPercent: number): number` -- for limits where higher usage = worse:
   Use a two-segment piecewise linear function:
   - 0-50%: score = 100 - (usedPercent * 0.6)  => range [100, 70]
   - 50-100%: score = 70 - ((usedPercent - 50) * 1.4)  => range [70, 0]
   Always clamp to [0, 100] and round.

   `linearCoverageScore(coverage: number): number` -- for code coverage where higher = better:
   Use a two-segment piecewise linear function:
   - 0-75%: score = (coverage / 75) * 70  => range [0, 70]
   - 75-100%: score = 70 + ((coverage - 75) / 25) * 30  => range [70, 100]
   Always clamp to [0, 100] and round.

4. **Trend penalty (HEALTH-02):**
   After computing raw factor score, if trend is 'degrading':
   ```
   const penalty = Math.min(15, Math.max(0, Math.abs(trendData.changePercent) * 0.5));
   factor.score = Math.max(0, Math.round(rawScore - penalty));
   ```

5. **Status mapping:** Same as current: score >= 70 -> 'healthy', score >= 40 -> 'warning', else 'critical'

6. **Summary and topRisks:** Same logic as current HealthScoreCalculator.buildSummary. Sort factors by score ascending, take top 3 non-healthy as topRisks.

7. **Recommendation generation:** Reuse the same `generateRecommendation` logic from HealthScoreCalculator for limit factors. For optional dimensions, use recommendation text from OrgHealthScoreCalculator.

Add full JSDoc on the class and all public/private methods.
