# Plan 02: Conflict Resolution UI Components

## Objective

Build the complete conflict resolution UI on the WebView side: a Zustand store to manage conflict state, a "conflicts" tab on SyncPage with count badge, a paginated and filterable conflict list, a side-by-side diff viewer using ConflictDiffService from Plan 01, per-field resolution controls with bulk actions, and message-based execution that sends resolution decisions back to the extension. This delivers CONFLICT-01 through CONFLICT-05.

## Context

- **Plan 01 delivers:** `UIConflict` type, `ConflictDiffService` (diffFields, diffThreeWay), `FieldResolution` type, wired `realtime:conflict` messages from extension, `realtime:resolve-conflict` handler on extension side, `resolvePerField` on ConflictResolver.
- **SyncPage** currently has 4 tabs: `'sync' | 'history' | 'schedules' | 'realtime'` (type `SyncTab` at line 37 of SyncPage.tsx). Add `'conflicts'` as the 5th tab.
- **useCDCLiveStore** manages CDC events in a ring buffer but does NOT handle `realtime:conflict` messages. Add a case for conflict messages that forwards to the new `useConflictStore`.
- **Reuse from Phase 01:** `DataTable` + `Pagination` + `usePagination` for the conflict list.
- **Reuse from Compare module:** `DiffDetailModal` pattern (side-by-side, per-field highlighting, keyboard trap). Do NOT import it directly -- clone the pattern with `UIConflict` data model.
- **Reuse:** `SplitView` for master/detail layout (list left, diff right). `Badge` for count/type badges. `DangerConfirm` for bulk resolution confirmation.
- **i18n:** All new keys under `sync.conflictResolution.*`. Conflict strategy labels already exist at `sync.conflicts.source_wins` etc.
- **Message flow:** WebView sends `realtime:resolve-conflict` with `conflictId` + `fieldResolutions`. Extension resolves and responds. WebView marks conflict as resolved in store.
- The conflict list should be filterable by object API name and conflict type (edit/edit, delete/edit, etc.).

   - Define `ConflictStoreState` interface:
     ```
     conflicts: UIConflict[];
     selectedConflictId: string | null;
     filterObject: string | null;
     filterType: string | null;
     ```
   - Define actions:
     - `addConflict(conflict: UIConflict): void` -- adds to array, deduplicates by id
     - `addConflicts(conflicts: UIConflict[]): void` -- batch add
     - `selectConflict(id: string | null): void` -- sets selectedConflictId
     - `setFilterObject(objectApiName: string | null): void`
     - `setFilterType(type: string | null): void`
     - `resolveConflict(id: string, resolution: ConflictStrategy, fieldResolutions?: Record<string, FieldResolution>): void` -- marks conflict as resolved in local state, sends `realtime:resolve-conflict` message to extension via postMessage
     - `resolveAllSource(): void` -- resolves all unresolved conflicts with strategy 'source_wins', sends one message per conflict
     - `resolveAllTarget(): void` -- same with 'target_wins'
     - `clearResolved(): void` -- removes all resolved conflicts from the array
   - Derived selectors (exported as standalone functions or computed in component):
     - `unresolvedCount` -- computed from `conflicts.filter(c => !c.resolved).length`
     - `filteredConflicts` -- apply filterObject and filterType to conflicts array
   - Max capacity: 500 conflicts (FIFO eviction like SyncHistoryStore).

     - `id`: `${payload.objectApiName}:${payload.recordIds[0]}:${payload.replayId}`
     - `objectApiName`: payload.objectApiName
     - `recordId`: payload.recordIds[0] (first record)
     - `conflictType`: map from payload.changeType (UPDATE -> 'edit/edit', DELETE -> 'delete/edit', etc.)
     - `sourceValues`: payload.sourceValues
     - `targetValues`: payload.targetValues
     - `baseValues`: undefined (CDC conflicts don't have base values by default)
     - `conflictFields`: keys where sourceValues[k] !== targetValues[k]
     - `timestamp`: payload.targetLastModified
     - `resolved`: false
   - Call `useConflictStore.getState().addConflict(uiConflict)` to add to the conflict store.
   - Do NOT store conflicts in useCDCLiveStore itself -- it only forwards.
