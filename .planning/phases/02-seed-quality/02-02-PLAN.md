# Plan 2: Picklist-aware Smart Suggest and VR-aware Generation

## Objective

Ensure SmartFieldGenerator uses ALL active picklist values when suggesting picklist_random mode (SQUAL-03), and build a VRAutoAdjuster that reads VRPreChecker results to auto-fix field generation configs so seeded data satisfies high-risk validation rules (SQUAL-04). This prevents seed failures caused by missing picklist values or validation rule violations.

## Context

**Current state of picklists:** SmartFieldGenerator (line 58-62) already detects picklist fields and sets mode to `picklist_random`, passing `field.picklistValues` into constraints. However, `SeedFieldInfo.picklistValues` is typed as `string[] | undefined` and may only contain a subset of values (whatever the describe call returns). The fix is to ensure the full active picklist values are passed through and that the config explicitly uses ALL of them.

**Current state of VR handling:** VRPreChecker analyzes validation rules and returns `VRCheckResult[]` with risk levels and `potentialConflicts` (field names). But there is NO component that takes these results and adjusts the field generation configs. The VR results are informational only. We need a `VRAutoAdjuster` that bridges VR analysis to field config adjustment.

**Key patterns to handle in VRAutoAdjuster:**
- `ISBLANK(FieldName)` or `ISNULL(FieldName)` with `NOT(...)` wrapper -> field is required, ensure non-null generation
- `ISPICKVAL(Status, 'Closed')` -> field must use specific picklist value or include it in the random set
- `LEN(FieldName) > N` or `LEN(FieldName) < N` -> field has length constraints
- `REGEX(FieldName, 'pattern')` -> field must match regex pattern (set ruleType to 'regex' if feasible)
- Cross-field dependencies like `IF(Type = 'X', ISBLANK(SubType))` -> harder, flag as warning rather than auto-fix

**Constraints:** TypeScript strict, no `any`, JSDoc, Winston logger, co-located tests. VRAutoAdjuster must not modify the original configs -- return new adjusted copies.

   ```
   interface VRFieldConstraint {
     fieldName: string;
     constraintType: 'required' | 'picklist_value' | 'length' | 'regex' | 'cross_field';
     expectedValue?: string;        // for picklist_value: the expected value
     minLength?: number;            // for length constraints
     maxLength?: number;            // for length constraints

   }
   ```

   - `ISBLANK(FieldName)` or `ISNULL(FieldName)` -> `{ fieldName, constraintType: 'required' }`

   - `LEN(FieldName) > N` -> `{ fieldName, constraintType: 'length', minLength: N+1 }`
   - `LEN(FieldName) < N` -> `{ fieldName, constraintType: 'length', maxLength: N-1 }`
   - `REGEX(FieldName, 'pattern')` -> `{ fieldName, constraintType: 'regex', regexPattern: 'pattern' }`
   - For complex cross-field patterns: `{ fieldName, constraintType: 'cross_field', relatedField }` -- best effort

3. Add `fieldConstraints: VRFieldConstraint[]` to `VRCheckResult` type in `packages/shared/src/types/seed.types.ts`.

4. Update `analyzeRule` to call `extractConstraints` and include the result in the returned `VRCheckResult`.

<action>
Create `VRAutoAdjuster.ts` that exports:

1. An `AdjustmentResult` interface:
   ```
   interface AdjustmentResult {
     adjustedConfigs: FieldGenerationConfig[];
     adjustments: AdjustmentLog[];
     unresolvedRules: string[];    // rule names that couldn't be auto-fixed
   }
   ```

2. An `AdjustmentLog` interface:
   ```
   interface AdjustmentLog {
     fieldName: string;
     ruleName: string;
     action: string;               // human-readable description of what was changed
     previousMode: FieldGenerationMode;
     newMode: FieldGenerationMode;
   }
   ```

3. A `VRAutoAdjuster` class with:
   - `adjust(configs: FieldGenerationConfig[], vrResults: VRCheckResult[]): AdjustmentResult`

   The method processes only `high` and `medium` risk VR results. For each VRCheckResult:

   a. For each `VRFieldConstraint` with `constraintType: 'required'`:
      - Find the matching FieldGenerationConfig by fieldName
      - If config exists and generationMode is `'null'`, change it to `'auto'` (or `'faker'` with method `'lorem'` for string fields)
      - Log the adjustment

   b. For each `VRFieldConstraint` with `constraintType: 'picklist_value'`:
      - Find the matching config
      - If config has picklistValues in constraints, ensure the expectedValue is included
      - If config mode is `'null'`, change to `'picklist_random'` and set picklistValues to `[expectedValue]`
      - If config mode is already `'picklist_random'`, verify expectedValue is in the list (it should be if SQUAL-03 is done correctly)
      - Log the adjustment

   c. For each `VRFieldConstraint` with `constraintType: 'length'`:
      - Update constraints.maxLength if the VR requires a shorter length
      - Update a minLength constraint (add `minLength?: number` to FieldGenerationConstraints if not present)
      - Log the adjustment

   d. For each `VRFieldConstraint` with `constraintType: 'regex'`:
      - If the regex is simple enough, change generationMode to appropriate faker method
      - Otherwise, add to unresolvedRules with explanation
      - Log the adjustment or the skip

   e. For `constraintType: 'cross_field'`:
      - Add to unresolvedRules (too complex for auto-fix)

   The method MUST NOT mutate the input configs. Create new objects via spread.

4. JSDoc on all public methods and interfaces.

Create `VRAutoAdjuster.test.ts`:
- High-risk ISBLANK rule -> null field adjusted to auto/faker mode
- ISPICKVAL rule -> field gets picklist_random with the expected value
- Length constraint -> constraints updated with min/max length
- Low-risk rules are ignored (not adjusted)
- Original configs are not mutated (test with Object.freeze)
- Multiple VR results on same field -> last adjustment wins
- Unresolvable rules (cross_field, complex regex) appear in unresolvedRules
- adjustments log contains correct before/after modes
