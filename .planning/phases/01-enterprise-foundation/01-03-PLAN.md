# Plan 01-03: Execution Progress -- Bulk API Progress, Per-Object Bars, Error Recovery UI

## Objective

Deliver real per-object progress tracking during sync/seed execution by parsing Bulk API 2.0 job progress (SCALE-06, POLISH-05) and an error recovery UI with retry/backoff controls (POLISH-01). This depends on Plan 01-01 for cache infrastructure (the progress events flow through the same MessageBroker pattern). The BulkJobProgressTracker polls real job status instead of the current placeholder percentages.

## Context

**Existing Bulk API infrastructure:**
- `BulkApiManager` (packages/extension/src/core/engine/BulkApiManager.ts) tracks jobs with `registerJob()`, `updateJobState()`, `updateJobCounts()`. It has `BulkJobInfo` with `numberRecordsProcessed` and `numberRecordsFailed` but does NOT emit progress events -- callers must poll.
- `BulkApiExecutor` (packages/extension/src/core/engine/BulkApiExecutor.ts) creates and runs bulk jobs.
- `SyncOpsHandler` and `SeedOpsHandler` handle execution messages and post results back to webview.
- `ProgressBar` component exists (packages/webview/src/components/ui/ProgressBar.tsx) with value/max/label/showPercent/variant props.

**Existing retry infrastructure:**
- `RetryStrategy` (packages/extension/src/core/engine/RetryStrategy.ts) implements exponential backoff with jitter.
- `RetryableOperation` (packages/extension/src/core/engine/RetryableOperation.ts) combines RetryStrategy + ErrorClassifier.
- `ErrorClassifier` classifies SF errors as retryable/non-retryable.
- The retry logic is backend-only. There is NO UI showing retry state, attempt count, or next attempt time.

**Progress placeholder problem:**
- Several pages show hardcoded "50%" or estimated percentages. The real Bulk API 2.0 GET /jobs/ingest/{jobId} returns `numberRecordsProcessed` and `numberRecordsFailed` that can be polled every 2-5 seconds during `InProgress` state.

**New shared types** (packages/shared/src/types/execution.types.ts):
```typescript
export interface ObjectProgress {
  objectName: string;
  jobId: string;
  operation: string;
  recordsProcessed: number;
  recordsFailed: number;
  totalRecords: number;
  state: 'queued' | 'processing' | 'complete' | 'failed' | 'aborted';
  startedAt: number;
  estimatedCompletionMs?: number;
}

export interface ExecutionProgress {
  executionId: string;
  objects: ObjectProgress[];
  overallPercent: number;
  elapsedMs: number;
}

export interface RetryStatus {
  executionId: string;
  objectName: string;
  attemptNumber: number;
  maxAttempts: number;
  nextRetryAt: number | null;
  lastError: string;
  canRetry: boolean;
  canAbort: boolean;
}
```

**Add message types** to messages.types.ts:
- `execution:progress` with `ExecutionProgress` payload
- `execution:retry-status` with `RetryStatus` payload
- `execution:manual-retry` with `{ executionId: string; objectName: string }` payload
- `execution:abort` with `{ executionId: string; objectName?: string }` payload

**BulkJobProgressTracker** (packages/extension/src/core/engine/BulkJobProgressTracker.ts):
- Constructor: `(bulkApiManager: BulkApiManager, pollIntervalMs?: number)` -- default 3000ms
- `startTracking(executionId: string, jobs: Array<{ jobId: string; objectName: string; totalRecords: number }>): void` -- begins polling all jobs
- `stopTracking(executionId: string): void` -- stops polling for an execution
- `onProgress(callback: (progress: ExecutionProgress) => void): () => void` -- subscribe to progress updates, returns unsubscribe
- Internal: uses `setInterval` to poll `BulkApiManager.getJob(jobId)` for each tracked job, computes `overallPercent` as weighted average by totalRecords, emits via callback
- When all jobs are terminal (JobComplete/Failed/Aborted), auto-stops tracking
- `dispose(): void` -- clears all intervals

**BulkApiManager updates:**
- Add `totalRecords` field to `BulkJobInfo` interface (optional, set when known)
- Add `updateTotalRecords(jobId: string, total: number): boolean` method

**Wire into handlers:**
- In SyncOpsHandler: after bulk jobs are created, call `progressTracker.startTracking()` and subscribe to onProgress, forwarding `execution:progress` messages to webview via `postToWebview`
- In SeedOpsHandler: same pattern
- Both handlers should call `stopTracking` on completion/abort

Tests for BulkJobProgressTracker: start/stop tracking, progress emission, auto-stop on terminal state, dispose cleanup, weighted percentage calculation.

<action>
**useRetryManager** hook:
- Subscribes to `execution:retry-status` messages via window message listener
- Maintains state: `Map<string, RetryStatus[]>` keyed by executionId (array of per-object retry statuses)
- Provides `manualRetry(executionId: string, objectName: string): void` -- sends `execution:manual-retry` message via postMessage
- Provides `abort(executionId: string, objectName?: string): void` -- sends `execution:abort` message
- Computes countdown timer: `nextRetryIn` seconds for each retry status (updates every second via setInterval)
- Returns `{ getRetryStatuses(executionId: string): RetryStatus[]; manualRetry; abort; getCountdown(nextRetryAt: number): number }`

**ErrorRecoveryPanel** component:
- Props: `{ executionId: string; className? }`
- Uses `useRetryManager` to get retry statuses
- Renders a list of failed/retrying operations:
  - Object name + last error message (truncated, expandable on click)
  - "Attempt {N} of {max}" text
  - If nextRetryAt is set: countdown display "Retrying in {N}s" with animated countdown
  - If no more retries: "All retries exhausted" in red
  - "Retry Now" button (calls manualRetry) -- only enabled when canRetry is true
  - "Abort" button (calls abort) -- always enabled when canAbort is true
  - Status indicator: spinning icon during retry, warning icon for waiting, error icon for exhausted
- Empty state: "No failed operations" with a check icon
- Collapsible error details with full error text

**i18n keys** under `retry.*`:
- `retry.title`: "Error Recovery"
- `retry.attemptOf`: "Attempt {current} of {max}"
- `retry.retryingIn`: "Retrying in {seconds}s"
- `retry.exhausted`: "All retries exhausted"
- `retry.retryNow`: "Retry Now"
- `retry.abort`: "Abort"
- `retry.noFailures`: "No failed operations"
- `retry.errorDetails`: "Error Details"
- `retry.manualRetryTriggered`: "Manual retry triggered"

Tests: renders retry statuses, countdown updates, retry button fires manualRetry, abort button fires abort, disabled states, empty state, error details expand/collapse.
