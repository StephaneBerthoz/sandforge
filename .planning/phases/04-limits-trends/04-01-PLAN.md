# Plan 01: Limits Coverage + Reset Countdown

## Objective

Add 3 new limit groups (email, platform events, file storage) to the Monitor dashboard and add a reset countdown timer in the header. This fulfills LIMITS-01 through LIMITS-04. The existing `/limits` API response already returns all these fields; the work is pure wiring and UI.

## Context

- **MonitorOpsHandler.handleApiUsage** (line 391-397) has a hardcoded `apiCategories` array of 11 entries. Email and platform event keys must be appended to this list. No backend API changes needed --- the Salesforce `/limits` endpoint already returns DailyWorkflowEmails, MassEmail, SingleEmail, HourlyPublishedPlatformEvents, DailyStandardVolumePlatformMessages.
- **MonitorPage.tsx** (lines 475-487) renders a `KPIStat` for DataStorageMB using `storageLimit`. A second KPIStat must be added for FileStorageMB. The `useMonitorPageData` hook already has a `findLimit` helper; a `fileStorageLimit` must be derived similarly.
- **MONITOR_KEY_LIMITS** in `packages/shared/src/constants/monitor.ts` has 5 entries. FileStorageMB must be added so trend computation covers file storage.
- **Reset countdown**: Salesforce daily limits reset at midnight Pacific (America/Los_Angeles). A new `ResetCountdown` component should display HH:MM:SS until reset. It must be rendered in the MonitorPage header bar, next to the lastUpdatedStr.
- **ApiUsagePanel.tsx** needs grouped section headers for the new categories (Email, Platform Events) since the panel will grow from 11 to 16 categories.
- **TrendData interface** currently only has `sparklineData: number[]` with no timestamps. For TREND-01 (Plan 02), TrendData needs a `timestamps` field. This plan adds the optional `timestamps?: string[]` field now so Plan 02 can populate it without a shared-types conflict.
- All text must use `t('key', 'default')` i18n pattern. No hardcoded strings.
