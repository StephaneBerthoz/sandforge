# Plan 02: Backend Features

## Objective

Deliver three backend feature improvements: (1) enrich the preview response with record count, field count, and estimated size so the ForgeInput estimated-graph panel shows real data; (2) wire the compliance framework dropdown to actually trigger a backend request; (3) replace synthetic `bulk-N` IDs with real Salesforce record IDs from Bulk API 2.0 results.

## Context

- **Preview enrichment (BE-02):** ForgeHandler.handleForgePreview already calls `describeGlobal` and queries the record. Need to add a `conn.describe(objectName)` call for field count and a `SELECT COUNT()` query for record count. Use `MB_PER_RECORD = 0.001` heuristic (same as GraphDiscoveryService) for size estimate.
- **Compliance wiring (BE-06):** ReviewComplianceTab.tsx has the dropdown but does not send any message on change. The backend handler (ForgeHandler.handleComplianceRequest) already works. Need to add `useSendMessage`/`useMessageListener` and call `forge:compliance:request` with graph+config from the store.
- **Real Bulk IDs (BE-07):** In SeedOpsHandler line 203, the bulk path returns `Array.from({ length: bulkResult.successCount }, (_, i) => 'bulk-${i}')`. The `BulkApiExecutor.executeBulk` returns `BulkExecutionResult` which has `successCount` but no `successIds`. Need to add `successIds` to the result and populate from `job.getAllResults()`. The `BulkJobRecordResult` interface needs an optional `id` field to match jsforce's actual response.

**IMPORTANT -- File conflict avoidance with Plan 04-01:** Plan 04-01 also modifies ForgeHandler.ts and HandlerTypes.ts. To avoid conflicts:
- This plan modifies ONLY `handleForgePreview` in ForgeHandler.ts (adding describe + count queries). Plan 04-01 modifies the other handler methods. If both run in parallel, merge is straightforward since they touch different methods.
- This plan does NOT modify HandlerTypes.ts at all.
