# Plan 4: Performance Optimizations

## Objective

Apply six performance optimizations to the Forge UI: separate Dagre layout computation from node status overlays (PERF-01), stabilize callbacks to prevent useMemo busting (PERF-02), memoize KPI calculations in ForgeExecution (PERF-03), debounce auto-scroll with requestAnimationFrame (PERF-04), avoid unnecessary array copies in LogStream filtering (PERF-05), and replace hardcoded pixel heights with flex-based adaptive sizing (PERF-06). These changes reduce CPU work during high-frequency execution updates.

## Context

- **LiveGraph.tsx** runs Dagre layout inside a `useMemo` that depends on `[graph, onNodeClick, onIncludeToggle]`. Since `graph` is a new object on every `updateNodeStatus` call, Dagre runs ~2 times/second during execution. The layout (positions) only depends on which nodes and edges exist — NOT on status/progress. Splitting the memo eliminates ~99% of Dagre calls during execution.
- **ForgeExecution.tsx** computes KPIs (doneCount, runningCount, etc.) on every render with inline `.filter()` calls on `nodes`. During execution, renders happen every 500ms-1s. Wrapping in useMemo keyed on `nodes` prevents redundant computation.
- **LogStream.tsx** (modified by Plan 03 for copy/export and pause scroll) has `filterEntries` that spreads the array for the 'all' case. It also uses a simple `scrollTop = scrollHeight` without requestAnimationFrame, which can cause layout thrashing.
- **ForgeDiscovery.tsx** has `h-[480px]` on the SplitView container. ForgeExecution has `h-[400px]`. LogStream has `max-h-64`. These should use flex-grow or CSS calc() to fill available space.
- **All Wave 1 plans (01, 02, 03) complete before this plan.** Files may have additional state/handlers/UI from those plans. Read each file fresh before modifying.
- **Key constraint:** All existing tests must continue to pass. Performance changes are internal refactors that preserve the same observable behavior.

**PERF-01: Separate layout from data overlay**

The key insight: `buildFlowNodes` does TWO things — (1) compute Dagre positions and (2) create React Flow node objects with data. Step 1 only depends on the set of node names and edges. Step 2 depends on the full node data (status, progress, etc.).

Split `buildFlowNodes` into two functions:

1. `computeLayout(graph: ForgeGraph): Map<string, { x: number; y: number }>` — runs Dagre, returns a Map of positions by objectApiName. This only needs `graph.nodes[].objectApiName` and `graph.edges`.

```typescript
/**
 * Compute Dagre layout positions based on graph topology.
 * Only depends on node names and edge connections — NOT on node status/progress.
 */
function computeLayout(graph: ForgeGraph): Map<string, { x: number; y: number }> {
  const positions = new Map<string, { x: number; y: number }>();
  if (graph.nodes.length === 0) return positions;

  const g = new dagre.graphlib.Graph();
  g.setDefaultEdgeLabel(() => ({}));
  g.setGraph({ rankdir: 'TB', nodesep: 80, ranksep: 120 });

  for (const node of graph.nodes) {
    g.setNode(node.objectApiName, { width: NODE_WIDTH, height: NODE_HEIGHT });
  }
  for (const edge of graph.edges) {
    g.setEdge(edge.sourceObject, edge.targetObject);
  }

  dagre.layout(g);

  for (const node of graph.nodes) {
    const pos = g.node(node.objectApiName);
    positions.set(node.objectApiName, {
      x: pos.x - NODE_WIDTH / 2,
      y: pos.y - NODE_HEIGHT / 2,
    });
  }
  return positions;
}
```

2. `buildFlowNodesFromLayout(graph, positions, onNodeClick, onIncludeToggle)` — creates the React Flow nodes using pre-computed positions.

```typescript
/**
 * Build React Flow nodes from pre-computed layout positions and current graph data.
 */
function buildFlowNodesFromLayout(
  graph: ForgeGraph,
  positions: Map<string, { x: number; y: number }>,
  onNodeClick?: (objectName: string) => void,
  onIncludeToggle?: (objectName: string) => void,
): Node<ProgressNodeData>[] {
  return graph.nodes.map((n) => {
    const pos = positions.get(n.objectApiName) ?? { x: 0, y: 0 };
    return {
      id: n.objectApiName,
      type: 'progressNode',
      position: pos,
      data: {
        objectApiName: n.objectApiName,
        recordCount: n.recordCount,
        fieldCount: n.fieldCount,
        createableFieldCount: n.createableFieldCount,
        estimatedSizeMB: n.estimatedSizeMB,
        status: n.status,
        progress: n.progress,
        included: n.included,
        hasPII: n.piiFields.length > 0,
        piiCount: n.piiFields.length,
        errorCount: n.errors.length,
        edgeType: getEdgeTypeForNode(n.objectApiName, graph.edges),
        onSelect: onNodeClick,
        onIncludeToggle,
      },
    };
  });
}
```

**PERF-02: Stable layout key**

In the LiveGraph component, create a topology key that changes only when nodes/edges change structurally:

```typescript
/** Stable key that changes only when graph topology changes. */
const topologyKey = useMemo(() => {
  const nodeNames = graph.nodes.map((n) => n.objectApiName).sort().join(',');
  const edgeKeys = graph.edges.map((e) => `${e.sourceObject}->${e.targetObject}`).sort().join(',');
  return `${nodeNames}|${edgeKeys}`;
}, [graph.nodes, graph.edges]);
```

Use two separate memos:
```typescript
// Layout: only recomputes when topology changes
const positions = useMemo(() => computeLayout(graph), [topologyKey]); // eslint-disable-line react-hooks/exhaustive-deps

// Nodes: recomputes when graph data changes (status, progress) BUT uses cached positions
const nodes = useMemo(
  () => buildFlowNodesFromLayout(graph, positions, onNodeClick, onIncludeToggle),
  [graph, positions, onNodeClick, onIncludeToggle],
);
```

The `positions` memo only recomputes when `topologyKey` changes (new nodes added or removed). During execution, when only status/progress changes, positions stay cached and only the node data overlay rebuilds — which is cheap (no Dagre).

**PERF-02: Stable handleNodeClick callback**

The `handleNodeClick` inside LiveGraph is already stable (depends only on `onNodeClick`). No change needed there.

The instability comes from the PARENT (ForgeDiscovery). In ForgeDiscovery, `handleToggleIncluded` changes identity when `selectedNodeName` changes. This is passed as `onIncludeToggle` to LiveGraph, busting the nodes memo.

However, since Plan 04 does NOT modify ForgeDiscovery's callback structure (that was Plan 01's territory), the fix here is to make LiveGraph resilient: the `nodes` memo already depends on `onIncludeToggle`, so when it changes, nodes rebuild — but positions don't. This is acceptable because the node rebuild is cheap. No further action needed for PERF-02 beyond the layout separation.

Remove the old `buildFlowNodes` function entirely.

**PERF-04: Auto-scroll debounce with requestAnimationFrame**

Find the auto-scroll `useEffect` (modified by Plan 03 to check `userScrolledUpRef`). Replace the direct `scrollTop` assignment with a requestAnimationFrame call:

```typescript
const rafRef = useRef<number | null>(null);

useEffect(() => {
  if (autoScroll && scrollRef.current && !userScrolledUpRef.current) {
    if (rafRef.current) cancelAnimationFrame(rafRef.current);
    rafRef.current = requestAnimationFrame(() => {
      if (scrollRef.current) {
        scrollRef.current.scrollTop = scrollRef.current.scrollHeight;
      }
      rafRef.current = null;
    });
  }
  return () => {
    if (rafRef.current) cancelAnimationFrame(rafRef.current);
  };
}, [visibleEntries, autoScroll]);
```

This ensures scroll updates are batched with the browser's paint cycle instead of triggering immediate synchronous layout.

**PERF-05: Avoid array copy for "All" filter**

Find the `filterEntries` function. Replace the `default` case:

Before (Plan 03 may have kept the same structure):
```typescript
default:
  return [...entries];
```

After:
```typescript
default:
  return entries as LogEntry[];
```

Since `entries` is `readonly LogEntry[]` in the parameter type, casting to `LogEntry[]` is safe because the returned array is only used for rendering (read-only). The `readonly` qualifier on the parameter prevents mutation at the call site. If the parameter type is not `readonly`, change the parameter to accept `readonly LogEntry[]`:

```typescript
function filterEntries(entries: readonly LogEntry[], filter: LogFilter): readonly LogEntry[] {
  switch (filter) {
    case 'error':
      return entries.filter((e) => e.level === 'error');
    case 'warn':
      return entries.filter((e) => e.level === 'warn' || e.level === 'error');
    default:
      return entries;
  }
}
```

Update the `visibleEntries` memo return type annotation if needed. The `visibleEntries.map(...)` calls in the JSX work the same on `readonly` arrays.
