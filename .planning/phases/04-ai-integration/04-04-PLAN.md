# Plan 04-04: Diagnose flow + inline ActionCard (Approve / Reject / Modify)

**Requirements covered:** AI-02 full (failed job → structured context → diagnosis → user-approve gate). Closes the inline action card UX decision from CONTEXT.

## Goal

Wire the user-facing diagnose vertical slice. A failed bulk job in Monitor exposes a "Diagnose with AI" command; clicking it dispatches `ai:diagnose` to the new `AIDiagnoseHandler`; the handler builds structured context via `ErrorResolver`, calls `aiClient.runTools(...)` with the read-only diagnose subset, returns a Zod-validated `DiagnoseResult`; the chat panel renders an inline `ActionCard` with up to 5 suggested actions; read-only ones execute silently, org-mutating ones gate behind Approve / Reject / Modify per the CONTEXT lock.

## Context

CONTEXT decisions locked: inline action card with Approve / Reject / Modify, approve fires ONLY for org-mutating actions, NO approve memory (each action re-asks). RESEARCH §"Recommended Approach" mandates a NEW `AIDiagnoseHandler` (don't modify the shipped `AIChatHandler` / `AIToolsHandler` / `AIAnalysisHandler` — defensive). RESEARCH §"Existing Patterns" → reuse `ErrorResolver` for context building, reuse the existing webview chat panel renderer, NEVER bypass `ConnectionPool`.

Phase 02 already shipped a placeholder `AIDiagnosePlaceholder.tsx` that seeds the testid contract for the Playwright spec `ai-diagnose-apply-fix.spec.ts`. This plan replaces the placeholder with the real component while keeping the SAME testids so the existing E2E spec continues to pass (and gets a few new assertions).

The `AIDiagnoseHandler` writes go through one of two paths:
1. Read-only auto-execute (`requiresApproval: false`): the handler calls the matching read-only tool inline (e.g., `kind: 'open-file'` opens the editor; `kind: 'copy-soql'` puts text on the clipboard). No bridge round trip.
2. Org-mutating gated (`requiresApproval: true`): the webview renders Approve / Reject / Modify; on Approve, the webview sends `ai:approve-action`; the handler dispatches to the matching EXISTING bridge handler (e.g., `seed:execute`, `compare:apply-deploy`). Plan 04-04 does NOT add any new mutating endpoint — it only routes through what already exists.

`autonomous: false` because the inline ActionCard is a live UI surface that requires a visual smoke before merge — verify-phase will require Stéphane to confirm one diagnose flow renders correctly in dev.

## Pitfalls mitigated (RESEARCH §"Common Pitfalls")

- **P-04.4 (Mutations sneak in as tools)** — diagnose tools are read-only only; mutations are routed via Approve gate to existing handlers.
- **P-04.6 (Token-budget counter drifts)** — handler increments the per-panel-session counter (Plan 04-05 owns the counter; this plan only emits the increment).
- **P-04.9 (Conversation memory lost across calls)** — diagnose is one-shot by design; do NOT thread tool history across calls (RESEARCH P-04.9 explicit: defer to v2).

public async buildDiagnoseContext(args: {

  jobId?: string;
  apexLogId?: string;

  let debugLogTail: string | undefined;
  if (args.apexLogId) {
    try {
      const log = await this.salesforce.getApexLogTail(args.orgId, args.apexLogId, 100); // last 100 lines
