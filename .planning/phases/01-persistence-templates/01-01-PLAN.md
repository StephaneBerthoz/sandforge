# Plan 01-01: Backend Persistence Stores + Bridge Handlers

## Objective

Create two thin persistence facades (`SyncConfigStore` and `SeedTemplateStore`) following the established `AlertStateStore` pattern, backed by `ConfigStore` with namespaced keys and dedicated categories. Wire CRUD bridge message handling into existing `SyncOpsHandler` and `SeedOpsHandler`. Refactor `SeedTemplateManager` to delegate persistence to `SeedTemplateStore` instead of its in-memory `Map`. This delivers SWIZ-01 (sync config persistence) and STPL-06 (seed template persistence).

## Context

**Pattern to follow:** `AlertStateStore` (`packages/extension/src/modules/monitor/AlertStateStore.ts`) -- thin facade, constructor takes `ConfigStore`, dedicated key prefix + category, simple save/load methods.

**Key naming from RESEARCH.md:**
- Sync configs: key prefix `sync:config:{id}`, category `syncConfigs`
- Seed templates: key prefix `seed:template:{id}`, category `seedTemplates`

**ConfigStore API:** `get<T>(key)`, `set(key, value, category)`, `delete(key)`, `getByCategory(category)`, `getKeysByPrefix(prefix)`. Already injected into all handlers via `HandlerDeps.configStore`.

**Bridge message convention:** Handler has a `_TYPES` Set of handled message types. Each type dispatches to a private `handle*` method. Responses use `buildResponse(deps, request, type, payload)`. Errors use `sendHandlerError(deps, context, type, err)`.

**SeedTemplateManager refactor:** Currently stores templates in `Map<string, SeedTemplate>`. Refactor to accept an optional `SeedTemplateStore` in its constructor. When store is provided, all CRUD operations read/write through it. When store is absent (tests), falls back to in-memory Map. This preserves backward compat.

**Message types to add to `packages/shared/src/types/messages.types.ts`:** Add the 8 new message type string literals to the `MessageType` union (or equivalent). Check the existing file structure first -- it may use a union type, enum, or just string constants.

**Existing types:** `SyncConfig` (sync.types.ts) and `SeedTemplate` (seed.types.ts) are already fully defined with all needed fields. No schema changes.

**SeedTemplateManager refactor:** Modify the constructor to accept an optional third parameter `store?: SeedTemplateStore`. When `store` is provided:
- `create()` calls `store.save()` after building the template
- `get()` calls `store.load()` instead of Map lookup
- `list()` calls `store.list()` instead of Map iteration
- `update()` calls `store.save()` after building updated template
- `delete()` calls `store.delete()` instead of Map delete
- `duplicate()` calls `store.save()` after building duplicated template

When `store` is undefined, keep current Map behavior (backward compat for tests that don't need persistence).

**Important:** The in-memory Map should still be maintained as a write-through cache when store is present -- write to both Map and store on mutations, read from Map first (faster). This ensures the existing `list()` sort behavior works without re-parsing JSON each time.

- `seed:template:save`, `seed:template:load`, `seed:template:list`, `seed:template:delete`

**SyncOpsHandler:**
1. Add the 4 new types to the `SYNC_TYPES` Set
2. Add a `private syncConfigStore: SyncConfigStore` field, instantiated in the constructor from `deps.configStore`
3. Add switch cases in `handle()` dispatching to private methods:
   - `handleConfigSave(msg)`: extract `SyncConfig` from `msg.payload.config`, call `syncConfigStore.save(config)`, respond with `buildResponse(deps, msg, 'sync:config:save:response', { success: true, id: config.id })`
   - `handleConfigLoad(msg)`: extract `id` from `msg.payload.id`, call `syncConfigStore.load(id)`, respond with config or error if not found
   - `handleConfigList(msg)`: call `syncConfigStore.list()`, respond with `{ configs: [...] }` (return summary: id, name, description, updatedAt -- NOT full config with all objects/mappings)
   - `handleConfigDelete(msg)`: extract `id`, call `syncConfigStore.delete(id)`, respond with `{ success: boolean }`
4. Wrap each handler in try/catch using `sendHandlerError`

**SeedOpsHandler:**
1. Add 4 new types to `SEED_TYPES` Set
2. Add `private seedTemplateStore: SeedTemplateStore` instantiated from `deps.configStore`
3. Same pattern as sync: save/load/list/delete handlers
   - `handleTemplateSave(msg)`: save template, respond with success + id
   - `handleTemplateLoad(msg)`: load by id, respond with template or error
   - `handleTemplateList(msg)`: list all, respond with summaries (id, name, description, tags, updatedAt, objectCount = objects.length, totalRecords = sum of recordCounts)
   - `handleTemplateDelete(msg)`: delete by id, respond with success boolean

**Note on SeedOpsHandler + SeedTemplateManager integration:** The handler should instantiate `SeedTemplateStore` from `deps.configStore`, then create a `SeedTemplateManager` backed by this store. For the `save` handler, use `SeedTemplateManager.create()` for new templates (no id in payload) and `SeedTemplateManager.update()` for existing ones (id present in payload).

Ensure existing handler tests still pass. Add at least 2 integration-style tests per handler verifying the CRUD message flow (send message, check response type and payload).
