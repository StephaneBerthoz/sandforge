# Plan 01-02: Pre-built Seed Templates + Wizard Draft Auto-Save

## Objective

Define three pre-built seed templates (Sales Cloud Starter, Service Cloud Starter, Minimal Demo) as static constants in shared, with correct insertOrder, realistic faker-based field rules, and proper reference rules for parent-child relationships. Implement a `useWebviewPersistedState` hook wrapping `vscode.getState()/setState()` with key-based merging, and integrate it into both wizard state hooks for draft auto-save on step change. This delivers STPL-01, STPL-02, STPL-03, and SWIZ-02.

## Context

**Template data shape:** `SeedTemplate` from `seed.types.ts`. Each object in `objects[]` has `objectApiName`, `recordCount`, `fieldRules[]`, `excludedFields[]`, `insertOrder`, `batchSize`. Field rules use `FieldRule` with `fieldApiName`, `ruleType`, and `config: FieldRuleConfig`.

**Insertion order pitfalls (from RESEARCH.md):**
- Sales Cloud: Pricebook2(0) -> Product2(1) -> Account(2) -> Contact(3) -> Opportunity(4) -> OpportunityLineItem(5). PricebookEntry may be needed between Product2 and OLI -- include it as a 7th object at insertOrder 2 (shift others) or handle via reference rules. The requirements list 6 objects + record counts; include PricebookEntry implicitly if needed for referential integrity.
- Opportunity.Pricebook2Id must reference the Pricebook2 record. OpportunityLineItem.PricebookEntryId must reference a PricebookEntry.
- Knowledge__kav needs `PublishStatus='Online'`, `Language='en_US'`, unique `UrlName` via sequence rule.

**Draft auto-save (from RESEARCH.md):**
- Use `vscode.getState()/setState()` via existing `useVSCodeApi` hook
- `setState()` replaces entire state -- always spread existing state: `setState({ ...getState(), [key]: newDraft })`
- Do NOT persist org credentials or access tokens. Org IDs are fine.
- Do NOT use localStorage/sessionStorage (unreliable in webview)

**Webview state hooks:**
- `useSyncPageData` (`packages/webview/src/pages/Sync/useSyncPageData.ts`): has `currentStep`, `setCurrentStep`, plus all form state (direction, mode, conflictStrategy, objectEntries, mappings, transforms, sourceOrgId, targetOrgId)
- `useSeedWizardState` (`packages/webview/src/pages/Seed/useSeedWizardState.ts`): composite hook with `currentStep`, `setCurrentStep`, plus sub-hooks for org, objects, fields, relations, execution

**i18n:** Template names and descriptions must use i18n keys. Define keys like `seedTemplates.salesCloudStarter.name`, `seedTemplates.salesCloudStarter.description`, etc. The static template constants can store the i18n key as the `name`/`description` value, or store English text and let the UI layer translate. Prefer storing i18n keys since templates are shared constants consumed by the webview which has access to `t()`.

**Record counts from requirements:**
- Sales Cloud Starter: Account(500) + Contact(1000) + Opportunity(2000) + OpportunityLineItem(4000) + Product2(50) + Pricebook2(1)
- Service Cloud Starter: Account(200) + Contact(500) + Case(1000) + CaseComment(2000) + Knowledge__kav(100)
- Minimal Demo: Account(50) + Contact(100) + Opportunity(200)

**useWebviewPersistedState hook:**

Create a generic hook that provides key-scoped persistence via `vscode.getState()/setState()`:

```typescript
/**
 * Persist and restore a piece of webview state across panel reloads.
 * Uses vscode.getState/setState with key-based merging to avoid
 * overwriting other persisted keys.
 *
 * @param key - Unique key for this piece of state (e.g., 'syncDraft', 'seedDraft')
 * @param initialValue - Default value when no persisted state exists
 * @returns [value, setValue] tuple similar to useState
 */
export function useWebviewPersistedState<T>(key: string, initialValue: T): [T, (value: T) => void]
```

Implementation:
1. On mount, read `vscode.getState()`, extract `state[key]` if it exists, otherwise use `initialValue`
2. `setValue` merges into existing state: `vscode.setState({ ...vscode.getState(), [key]: newValue })`
3. Use `useVSCodeApi()` to get the API
4. Use `useState` internally for the React state, and sync to vscode on every change
5. Use `useCallback` for the setter to keep stable references

**Test file:** Mock `useVSCodeApi` to return a fake API with in-memory state. Test:
- Initial value used when no persisted state
- Persisted value restored on mount
- setValue updates both React state and vscode state
- Multiple keys don't interfere with each other
- Handles undefined/null getState() return gracefully

**useSyncPageData integration:**

1. Import `useWebviewPersistedState`
2. Define a `SyncDraftState` interface containing only the safe-to-persist fields:
   - `currentStep`, `direction`, `mode`, `conflictStrategy`, `sourceOrgId`, `targetOrgId`, `objectEntries`, `mappings`, `transforms`
   - Do NOT include: execution results, loading states, error states, field metadata
3. Use `useWebviewPersistedState<SyncDraftState>('syncDraft', defaultDraft)` to initialize state
4. On `setCurrentStep`, save the current draft state. The simplest approach: use a `useEffect` that watches the form state values and persists on change. Or: wrap `setCurrentStep` to persist the draft before navigating. Prefer the `useEffect` approach -- persist whenever any form field changes (debounce is not needed since setState is synchronous and cheap).
5. On mount, if a persisted draft exists, restore all form fields from it.

**useSeedWizardState integration:**

Same pattern but with `SeedDraftState` interface:
- `currentStep`, `selectedOrgId`, `selectedObjects`, `volumes`, `fieldConfigs`, `relations`, `nl2soqlQuery`
- Do NOT include: execution results, progress, PII results, loading states
- Use `useWebviewPersistedState<SeedDraftState>('seedDraft', defaultDraft)`
- Restore on mount, save on form state changes via useEffect

**Important security note from RESEARCH.md:** Only persist form-level state. Org IDs are fine (just UUID identifiers). Do NOT persist access tokens, session IDs, or connection objects.
