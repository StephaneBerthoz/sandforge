# Plan 02: Sync Schedule Executor Backend

## Objective

Build the cron-based sync scheduling engine that persists schedules to ConfigStore, computes next-run times with `cron-parser`, survives extension restarts, handles sleep-wake gracefully (execute once per missed schedule, not once per missed interval), and integrates with NotificationCenter for SCHED-05 notifications. This replaces the broken `SyncScheduler` class entirely.

## Context

**Why replace SyncScheduler:**
The existing `SyncScheduler` (packages/extension/src/modules/sync/SyncScheduler.ts) is in-memory only (no persistence), its cron parsing ignores dayOfMonth and dayOfWeek, and it is not wired to any execution pipeline. Research recommends full replacement.

**Patterns to follow:**
- `OperationScheduler` (packages/extension/src/modules/automation/OperationScheduler.ts) -- the tick-loop architecture. Copy the `start()/stop()/tick()` pattern with 60s interval. Copy the `upsert/delete/toggle/getSchedules` API surface. But replace `computeNextRunAt` with `cron-parser`.
- `SyncConfigStore` -- thin ConfigStore facade pattern for schedule persistence.
- `AlertStateStore` -- FIFO pattern (not needed here, but the ConfigStore facade approach is the same).

**Key decisions from research:**
- Install `cron-parser` in `packages/extension` only (not shared or webview). Use its `parseExpression(cron, { tz })` for timezone-aware cron and `.next().toDate()` for next-run.
- Do NOT modify `OperationScheduler` -- it serves the automation module. Create a separate `SyncScheduleExecutor`.
- Sleep-wake detection: if `Date.now() - lastTickTime > 2 * TICK_INTERVAL_MS`, execute each overdue schedule exactly ONCE, then recompute nextRunAt to the next FUTURE occurrence via `cron-parser.parseExpression(cron).next()`.
- The `SyncScheduleEntry` type (defined in Plan 01's shared types task) has: `id, name, configId, cron, timezone, enabled, maxRetries, notifyOnComplete, notifyOnFailure, nextRunAt, lastRunAt, lastResult, createdAt, updatedAt, version`.
- Schedules persist with `schedule:sync:{id}` prefix in ConfigStore.
- On `activate()`, reload schedules from ConfigStore and restart the tick loop.
- NotificationCenter methods: `notify({ level, title, message })` -- use `success` for completions, `error` for failures, `info` for starts.

**Existing types used:**
- `SyncScheduleEntry` from `@sandforge/shared` (added by Plan 01 task 01)
- `SyncConfig` from `@sandforge/shared`
- `SyncExecutionResult` from `@sandforge/shared`
- `NotificationCenter` from `packages/extension/src/core/notifications/NotificationCenter.ts`

**Note:** This plan depends on `SyncScheduleEntry` type being defined in shared types. Since Plan 01 task 01 adds it and both plans are Wave 1, the executor must be careful: if types are not yet available, mock them locally in tests. The actual wiring happens at build time when both plans are complete.

Create `SyncScheduleExecutor` following `OperationScheduler`'s architecture:

Constructor dependencies (injected, for testability):
```typescript
interface SyncScheduleExecutorDeps {
  scheduleStore: SyncScheduleStore;
  configStore: { load(id: string): SyncConfig | undefined }; // SyncConfigStore.load
  onExecute: (config: SyncConfig) => Promise<SyncExecutionResult>;
  notificationCenter: {
    notify(notification: { level: string; title: string; message: string }): void;
  };
  log: (msg: string) => void;
  now?: () => number; // for testing time control, defaults to Date.now
}
```

Internal state:
- `schedules: Map<string, SyncScheduleEntry>` -- in-memory cache
- `checkInterval: ReturnType<typeof setInterval> | undefined`
- `lastTickTime: number` -- for sleep-wake detection
- `TICK_INTERVAL_MS = 60_000`

Methods:

- `start(): void` -- Load all schedules from `scheduleStore.loadAll()` into the Map. Start 60s interval calling `tick()`. Set `lastTickTime = now()`. Idempotent (if already started, no-op).
- `stop(): void` -- Clear interval, set to undefined. Log stop.
- `async tick(): Promise<void>` -- Core scheduling loop:
  1. Compute `elapsed = now() - lastTickTime`. If `elapsed > 2 * TICK_INTERVAL_MS`, log sleep-wake detected.
  2. Update `lastTickTime = now()`.
  3. For each enabled schedule where `nextRunAt` is in the past (or missing):
     a. Load `SyncConfig` from `configStore.load(schedule.configId)`. If not found, log error, skip.
     b. Notify start (if `notifyOnComplete` is true): `notificationCenter.notify({ level: 'info', title: t('sync.schedule.started'), message: schedule.name })`.
     c. Execute via `onExecute(config)`. Wrap in try/catch.
     d. Update schedule: `lastRunAt = now ISO`, `lastResult = result.status`, recompute `nextRunAt` using `cron-parser.parseExpression(schedule.cron, { tz: schedule.timezone }).next().toISOString()`.
     e. Persist updated schedule via `scheduleStore.save(schedule)`.
     f. On success: if `notifyOnComplete`, notify success.
     g. On failure: if `notifyOnFailure`, notify error.
     h. **Critical:** Even if multiple runs were missed (sleep-wake), only execute ONCE per schedule per tick. The `nextRunAt` recomputation via `cron-parser.next()` ensures it jumps to the next future time.
  4. After processing all schedules, no further action needed.

- `upsert(input: Omit<SyncScheduleEntry, 'nextRunAt' | 'lastRunAt' | 'lastResult'>): SyncScheduleEntry` -- Compute `nextRunAt` via cron-parser. Set `lastRunAt`/`lastResult` from existing if updating. Save to store and Map. Return full entry.
- `delete(scheduleId: string): boolean` -- Remove from Map and store.
- `toggle(scheduleId: string, enabled: boolean): SyncScheduleEntry | undefined` -- Update enabled state. If re-enabling, recompute nextRunAt. Save.
- `getSchedules(): SyncScheduleEntry[]` -- Return Map values as array.
- `getSchedule(id: string): SyncScheduleEntry | undefined` -- Map lookup.

Private helpers:
- `computeNextRunAt(cron: string, timezone: string): string` -- Use `cron-parser.parseExpression(cron, { tz: timezone, currentDate: new Date() }).next().toISOString()`. Wrap in try/catch, return empty string on invalid cron (log error).
