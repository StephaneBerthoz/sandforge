# Plan 01: Sync History Backend

## Objective

Build the persistence layer for sync execution history. Every sync execution must be captured as a full snapshot (config + result) and stored in ConfigStore with FIFO capping at 500 entries. This is the foundation for HIST-01 through HIST-05 and is also needed by the scheduling system (Phase 02, Plan 02) to log scheduled execution results.

## Context

**Patterns to follow:**
- `SyncConfigStore` (packages/extension/src/modules/sync/SyncConfigStore.ts) -- thin facade over ConfigStore with dedicated prefix and category. Copy this pattern exactly.
- `AlertStateStore` (packages/extension/src/modules/monitor/AlertStateStore.ts) -- FIFO history with `MAX_HISTORY_SIZE = 500`, deduplication by ID, trim oldest. Use `saveHistory` method as template.
- `SyncOrchestrator.execute()` returns `SyncExecutionResult` with `configId`, `operationId`, `status`, `objectResults`, `totalProcessed/Success/Failed/Skipped`, `duration`, `timestamp`.

**Key decisions from research:**
- Store all history entries under a SINGLE key (`sync:history:all`) as an array, not one key per entry. This avoids polluting the ConfigStore key namespace.
- History entries must store a FULL COPY of the `SyncConfig` used at execution time (for re-run support in HIST-04), not just a configId reference.
- Cap at 500 entries with FIFO eviction.
- Export supports CSV and JSON formats (HIST-05). CSV is flat: just header + rows with `.join(',')`. JSON is `JSON.stringify`.

**Existing types to extend:**
- `SyncExecutionResult` in `packages/shared/src/types/sync.types.ts` -- already has the right shape for result data
- `SyncSchedule` in same file -- has `cron`, `timezone`, `maxRetries`, `notifyOnFailure`
- `SyncConfig` -- the full config to snapshot

**Message protocol:** No existing `sync:history:*` or `sync:schedule:*` messages exist. The existing `scheduler:*` messages are for the automation module's `OperationScheduler`. Create new sync-specific message types to avoid conflating the two systems.

<action>
Create `SyncHistoryStore` following the `AlertStateStore` pattern exactly:

```
const SYNC_HISTORY_PREFIX = 'sync:history:';
const SYNC_HISTORY_CATEGORY = 'syncHistory';
const MAX_HISTORY_SIZE = 500;
```

Constructor takes `ConfigStore` as dependency (same as `SyncConfigStore`).

Methods:
- `save(entry: SyncHistoryEntry): void` -- Append entry to the stored array. Deduplicate by `entry.id`. If total exceeds `MAX_HISTORY_SIZE`, trim oldest (FIFO). Store under single key `sync:history:all` with category `syncHistory`.
- `load(id: string): SyncHistoryEntry | undefined` -- Load the full array, find by id.
- `list(): SyncHistoryEntry[]` -- Return all entries sorted by `startTime` descending (newest first).
- `delete(id: string): boolean` -- Remove entry by id from the array, re-persist.
- `exportAsJson(entryIds?: string[]): string` -- If entryIds provided, filter to those; otherwise use all. Return `JSON.stringify(entries, null, 2)`.
- `exportAsCsv(entryIds?: string[]): string` -- Flatten each entry to a row: id, configSnapshot.name (or configId), status, totalProcessed, totalSuccess, totalFailed, totalSkipped, startTime, endTime, duration, triggeredBy. Header row + data rows joined by newlines. Values with commas wrapped in double quotes.
- `clear(): void` -- Remove the key entirely.

All methods have JSDoc. Use `ConfigStore.get<SyncHistoryEntry[]>` and `ConfigStore.set<SyncHistoryEntry[]>`.

Test file must cover:
1. save + list returns entries sorted by startTime descending
2. save deduplicates by id (saving same id twice does not create duplicate)
3. FIFO eviction: save 501 entries, verify list returns exactly 500 and the oldest entry is gone
4. load by id returns correct entry or undefined
5. delete removes entry and persists
6. exportAsCsv produces correct header and row count
7. exportAsJson produces valid JSON with correct entry count

Use a mock ConfigStore (in-memory Map) for tests, following the test pattern used in `SyncConfigStore.test.ts`.
