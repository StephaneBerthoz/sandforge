# Plan 01: Alert System Backend Wiring

## Objective

Wire the existing AlertEngine into the live monitor refresh cycle so that alerts actually fire when Salesforce org limits cross thresholds. This plan delivers: (1) default alert definitions for 5 critical limits, (2) evaluate() calls on every refresh, (3) persistence of alert state across restarts via ConfigStore, and (4) VSCode-side notifications for critical/warning alerts. These are the backend prerequisites before the alert history UI can be built (Plan 03).

## Context

- `AlertEngine` at `packages/extension/src/modules/monitor/AlertEngine.ts` is fully implemented (cooldown, lifecycle, severity, ack/dismiss) but its `definitions` map starts empty and `evaluate()` is never called from anywhere.
- `MonitorOpsHandler.handleRefresh()` already fetches limits via `getOrFetchLimits()` and transforms them with `transformLimitsResponse()` into an `ApiLimit[]` array where each entry has `name`, `max`, `remaining`, `usedPercent`.
- The webview `AlertsPanel.tsx` already sends `monitor:alerts`, `monitor:alert:acknowledge`, `monitor:alert:dismiss` messages but no handler responds to them.
- `useMonitorPageData.ts` queries `monitor:alerts` with response type `monitor:alerts:result` -- the handler must respond with `{ alerts: AlertInstance[] }`.
- `ConfigStore` is the standard persistence mechanism. Pattern: use a dedicated store class (like `GovernancePolicyStore`) that wraps ConfigStore with a prefix.
- `HandlerDeps` does not have `vscode.window` access. For VSCode native notifications, use the existing `sendNotification()` helper from HandlerTypes.ts which posts a `notification` message to the webview. The webview's NotificationStore already displays these. For true VSCode-native notifications (showWarningMessage/showErrorMessage), the AlertEngine's `onNotify` callback should be configured in the handler constructor to call `sendNotification(deps, ...)` which is sufficient for this milestone.
- Alert metric names must match the `ApiLimit.name` field from the limits response (e.g., `DailyApiRequests`, `DataStorageMB`, `DailyAsyncApexExecutions`, etc.). The `usedPercent` field is what gets evaluated.
- The `AlertDefinition.notificationChannels` field exists in the shared type but is not used by AlertEngine -- it can be set to `['vscode_notification']` for defaults.
