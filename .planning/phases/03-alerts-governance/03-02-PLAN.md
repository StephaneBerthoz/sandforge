# Plan 02: Governance Bridge Handler + Alert Pipeline

## Objective

Create a new `GovernanceOpsHandler` DomainHandler that wires the existing `GovernancePolicyStore` CRUD methods and `GovernanceEngine.evaluatePolicy()` to bridge message handlers. This also implements GOV-03: when governance evaluation produces `fail` results, those violations are converted into alert evaluations fed into AlertEngine, creating a unified threshold-to-alert pipeline. This is a standalone handler (not added to MonitorOpsHandler) because governance is a separate domain concern.

## Context

- `GovernancePolicyStore` at `packages/extension/src/modules/monitor/GovernancePolicyStore.ts` already has: `getAll()`, `getById(id)`, `save(policy)`, `delete(id)`, `exportPolicies()`, `importPolicies(json)`, `getDefaultTemplates()`.
- `GovernanceEngine` at `packages/extension/src/modules/monitor/GovernanceEngine.ts` already has: `evaluateRule(rule, metrics)`, `evaluatePolicy(policy, metrics)`, `computeComplianceScore(results)`.
- The webview `GovernancePanel.tsx` expects props: `policies`, `ruleResults`, `complianceScore`, `remediations`, `loading`, `onEvaluate`, `onDeletePolicy`, `onAddPolicy`. These will be wired via bridge queries in Plan 03.
- `GovernanceEngine.evaluatePolicy()` takes a `GovernancePolicy` and `MetricValues` (Record<string, number>). The handler must construct MetricValues from the cached /limits response by converting each limit to `usedPercent`.
- For GOV-03, when `evaluatePolicy` produces rule results with `status === 'fail'`, each failing rule should be fed into AlertEngine. The handler needs a reference to AlertEngine -- pass it as a constructor parameter (`alertEngine?: AlertEngine`). If no AlertEngine is provided, skip the alert feed (allows standalone testing).
- This handler does NOT need a Salesforce connection for CRUD operations (policies are local). Only the `governance:evaluate` endpoint needs limits data, which requires a connection.
- The handler must be registered in the bridge handler chain. Add a note in must-haves that the handler registration must be verified, but the actual registration point (activate.ts or MessageRouter) can be handled by the executor.
- `HandlerDeps` provides `configStore` which is what GovernancePolicyStore wraps.
- The GovernanceEngine types (`GovernancePolicy`, `GovernanceRule`, `GovernanceRuleResult`, `GovernanceEvaluationResult`, `MetricValues`, `ComplianceStatus`) are all defined and exported from GovernanceEngine.ts, NOT from @sandforge/shared. The handler will import from the engine file directly.

<action>
Create `GovernanceOpsHandler` implementing `DomainHandler`:

**Constructor:** `(deps: HandlerDeps, alertEngine?: AlertEngine)`
- Create `GovernancePolicyStore` from `deps.configStore`.
- Create `GovernanceEngine` instance.
- Store optional `alertEngine` reference for GOV-03 pipeline.

**Message types (add to a GOVERNANCE_TYPES Set):**

1. `governance:policies:list` -- No payload needed. Returns `governance:policies:result` with `{ policies: GovernancePolicySummary[] }` where GovernancePolicySummary includes `id, name, description, ruleCount, createdAt, updatedAt` (matches webview interface).

2. `governance:policy:get` -- Payload: `{ policyId: string }`. Returns `governance:policy:result` with `{ policy: GovernancePolicy | null }`.

3. `governance:policy:save` -- Payload: `{ policy: GovernancePolicy }`. Validates with Zod (`GovernancePolicySchema.safeParse`). Calls `store.save()`. Returns `governance:policy:save:response` with `{ success: true }`.

4. `governance:policy:delete` -- Payload: `{ policyId: string }`. Calls `store.delete()`. Returns `governance:policy:delete:response` with `{ success: boolean }`.

5. `governance:policies:export` -- No payload. Calls `store.exportPolicies()`. Returns `governance:policies:export:response` with `{ json: string }`.

6. `governance:policies:import` -- Payload: `{ json: string }`. Calls `store.importPolicies()` in try/catch. Returns `governance:policies:import:response` with `{ success: boolean, count: number }`.

7. `governance:evaluate` -- Payload: `{ policyId: string, orgId: string }`. This is the complex one:
   - Get policy from store by ID. If not found, send error response.
   - Get a jsforce connection via `getJsforceConnection(payload.orgId, deps.orgRegistry, deps.orgManager)`.
   - Fetch limits via `conn.request('/services/data/.../limits')` (or share the same getOrFetchLimits pattern -- but since this is a separate handler, just fetch directly, the 30s cache is at MonitorOpsHandler level).
   - Build `MetricValues` from the raw limits: for each key in the limits response, compute `usedPercent = (Max - Remaining) / Max * 100`.
   - Call `governanceEngine.evaluatePolicy(policy, metrics)`.
   - **GOV-03 pipeline:** For each rule result with `status === 'fail'`, if `alertEngine` is provided, call `alertEngine.evaluate('governance:' + result.ruleId, result.actualValue, payload.orgId)`. The metric name prefix `governance:` distinguishes governance-sourced alerts from limit-sourced alerts.
   - Return `governance:evaluate:response` with `{ success: true, result: GovernanceEvaluationResult }`.

8. `governance:templates` -- No payload. Returns `governance:templates:response` with `{ templates: GovernancePolicy[] }` from `GovernancePolicyStore.getDefaultTemplates()`.

**Error handling:** Use `sendHandlerError` for all catch blocks.

**Test file:** Create comprehensive tests:
- Test `handle()` returns false for unknown types.
- Test `governance:policies:list` returns empty array then populated array after save.
- Test `governance:policy:save` + `governance:policy:get` round-trip.
- Test `governance:policy:delete` returns success.
- Test `governance:policies:export` returns valid JSON.
- Test `governance:policies:import` with valid and invalid JSON.
- Test `governance:evaluate` with mock connection, verify it returns compliance score and rule results.
- Test GOV-03: verify that when evaluate produces `fail` results and alertEngine is provided, alertEngine.evaluate is called for each failing rule.
- Test `governance:templates` returns default templates.

For tests, mock `getJsforceConnection` using the same `vi.hoisted` pattern as MonitorOpsHandler.test.ts. Mock ConfigStore with `get`, `set`, `delete`, `getKeysByPrefix`, `has` methods.
