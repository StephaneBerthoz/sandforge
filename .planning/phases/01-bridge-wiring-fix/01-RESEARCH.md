# Phase 1: Bridge Wiring Fix - Research

**Completed:** 2026-03-17

## Key Finding

The bridge architecture is **well-designed**. `useBridgeQuery` and `useBridgeMutation` do their own response listening via `window.addEventListener('message', ...)` in `useMessageResponse.ts`. BridgeProvider does NOT need to relay module responses — it only handles global state (org list, loading, notifications, grappe).

The initial audit claiming "70+ responses unlistened" was WRONG about the mechanism — BridgeProvider doesn't need to listen for module responses. The hooks handle that.

**The real issues are:**
1. Response type mismatches (hooks expect type X, handler sends type Y)
2. Missing correlationId (type-only matching can collide)
3. Ghost message types in messages.types.ts with zero implementation
4. Handlers that may not exist for some request types (PENDING verification needed)

- **Settings update**: hook expects `settings:updated`, handler sends `settings:response`

## Don't Hand-Roll

- **correlationId**: Use the existing `msg.id` field already generated by `buildMessage()`. Don't add a new field — just have extension copy `msg.id` to response and have `useMessageResponse` match on it.
- **Type registry**: Don't build a runtime registry. Fix the types statically in TypeScript — the existing `{requestType}:response` convention works when followed consistently.

## Common Pitfalls

1. **Over-scoping BridgeProvider**: Adding 70+ listeners to BridgeProvider is WRONG — hooks already listen. Only add global state listeners there.
2. **Breaking existing working hooks**: Many hooks already work. Only touch hooks with confirmed mismatches.
3. **Removing ghost types that have UI consumers**: Some types like `realtime:*` have UI components (RealTimeSyncPanel) but no handler. These need handlers, not type removal.
4. **correlationId matching without fallback**: Old messages in flight won't have correlationId. Need type-based fallback.
